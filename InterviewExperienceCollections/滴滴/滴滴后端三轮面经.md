### 2. 完成迷宫可达性编程题，并解释为什么使用 BFS。（一面第 2 题）

**结论：**如果题目只问无权网格中起点能否到达终点，BFS 和 DFS 都能判断可达；选择 BFS 的额外好处是，它按距离逐层扩展，在每步代价相同的前提下还能直接得到最短步数，并且可以在第一次到达终点时结束。

由于原录音没有完整题面，下面按常见版本处理：`0` 表示可走，`1` 表示障碍，只能上下左右移动，返回从左上角到右下角的最短步数，不可达返回 `-1`。

```java
import java.util.ArrayDeque;
import java.util.Queue;

class Solution {
    public int shortestPath(int[][] grid) {
        if (grid == null || grid.length == 0 || grid[0].length == 0) {
            return -1;
        }
        int m = grid.length, n = grid[0].length;
        if (grid[0][0] == 1 || grid[m - 1][n - 1] == 1) {
            return -1;
        }

        int[][] directions = {{1, 0}, {-1, 0}, {0, 1}, {0, -1}};
        boolean[][] visited = new boolean[m][n];
        Queue<int[]> queue = new ArrayDeque<>();
        queue.offer(new int[]{0, 0, 0});
        visited[0][0] = true;

        while (!queue.isEmpty()) {
            int[] current = queue.poll();
            int row = current[0], col = current[1], distance = current[2];
            if (row == m - 1 && col == n - 1) {
                return distance;
            }
            for (int[] direction : directions) {
                int nextRow = row + direction[0];
                int nextCol = col + direction[1];
                if (nextRow >= 0 && nextRow < m && nextCol >= 0 && nextCol < n
                        && grid[nextRow][nextCol] == 0 && !visited[nextRow][nextCol]) {
                    visited[nextRow][nextCol] = true;
                    queue.offer(new int[]{nextRow, nextCol, distance + 1});
                }
            }
        }
        return -1;
    }
}
```

`visited` 要在入队时标记，而不是出队时标记，否则同一个位置可能被多个相邻位置重复入队。时间复杂度是 `O(mn)`，空间复杂度也是 `O(mn)`。如果原题带权、允许传送或要求路径本身，需要分别改用 Dijkstra、补充状态维度或记录前驱，不能机械套用这段代码。

### 5. 简历中的图式 Agent 工作流如何构建；Checkpoint 做什么？（一面第 5 题）

图式工作流一般先定义统一状态，例如 `taskId`、用户目标、计划、当前节点、工具结果、错误、预算和最终产物；再把规划、检索、工具执行、校验、人工审核等步骤做成节点，用条件边决定继续、重试、回退还是结束。执行层还要限制最大步数、Token/费用预算和 Tool 白名单，避免无限循环或越权调用。

Checkpoint 是某一执行时刻的持久化状态快照。它通常绑定 `threadId/runId + step/version`，保存恢复所需的状态和已完成节点，使进程重启、人工暂停或暂时失败后能够从确定位置继续，也便于查看历史状态和调试。

但 Checkpoint 不等于业务操作天然“恰好一次”。如果节点已经调用外部接口，写入快照前进程崩溃，恢复后仍可能重复调用，所以 Tool 还要使用 `operationId`、幂等键、条件更新或结果表去重。面试时要把“状态恢复”和“外部副作用幂等”分开讲。

### 6. JVM 双亲委派是什么；Tomcat 类加载有什么特殊点？（一面第 6 题）

双亲委派的基本过程是：一个类加载器收到加载请求后，通常先把请求交给父加载器；父加载器无法加载时，子加载器再尝试。JDK 中常见层次是 Bootstrap、Platform 和 Application ClassLoader。它的价值是避免核心类被应用重复或恶意替换，并让相同核心类尽量由同一个加载器加载。

Tomcat 要同时运行多个 Web 应用，因此还需要应用隔离。每个 Web 应用通常有自己的 `WebappClassLoader`，`WEB-INF/classes` 和 `WEB-INF/lib` 中的类可以彼此隔离，并在很多应用类场景采用“本地优先”的查找方式；但 Java 平台类以及 Servlet 等容器 API 仍优先委派，防止应用覆盖核心或容器规范类。Tomcat 还存在 Bootstrap、System、Common 等层次，具体层级与配置有关。

边界是：双亲委派是常见模型，不是 JVM 强制所有自定义加载器都只能这样实现；Java SPI、容器和模块化系统都可能采用不同的加载策略。判断两个 `Class` 是否相同，还要同时看全限定名和定义它的类加载器。

### 7. ThreadLocal 为什么可能泄漏；是否任何场景不 remove 都必然泄漏？（一面第 7 题）

`Thread` 内部持有一个 `ThreadLocalMap`。其中 Entry 的 Key 是对 `ThreadLocal` 对象的弱引用，但 Value 是强引用。外部不再引用某个 `ThreadLocal` 后，Key 可能被 GC 清成 `null`，Value 仍沿着 `Thread -> ThreadLocalMap -> Entry -> Value` 可达。在线程池中线程长期存活，这个 Value 就可能长时间不能回收，还可能把上一个请求的数据带到下一个请求。

不 `remove()` 不代表每次都必然形成永久泄漏：线程很快结束时整张 Map 会随线程回收；后续 `get/set/remove` 也可能顺带清理过期 Entry；如果 ThreadLocal 本身和线程生命周期一致，也未必出现悬空 Key。但服务端线程池生命周期长，不能依赖这些偶然清理。

标准写法是在 `finally` 中调用 `remove()`：

```java
try {
    CONTEXT.set(context);
    handleRequest();
} finally {
    CONTEXT.remove();
}
```

### 8. Redis ZSet 的底层结构是什么？（一面第 8 题）

ZSet 同时维护 member 唯一性和按 score 排序。经典实现有两种编码：新版本中，元素较少、成员较短时使用紧凑的 `listpack`，旧版本常称为 `ziplist`；规模超过配置阈值后，使用“哈希表 + 跳表”。哈希表让按 member 查询 score 接近 `O(1)`，跳表按 `score` 排序，支持 `O(log n)` 的插入、删除、排名和范围定位。

score 相同时，再按 member 的字典序确定顺序。跳表比平衡树更容易实现范围遍历和更新，但会付出多级前向指针的空间。面试中不要只回答“跳表”，因为字典和紧凑编码分别解决了按 member 定位和小集合节省内存的问题；具体转换阈值由 Redis 版本及配置决定。

### 9. CAS 的 ABA 问题是什么，怎样解决？（一面第 9 题）

CAS 只比较“当前值是否等于我之前看到的值”。假设线程 1 读取到 A，线程 2 把它从 A 改成 B，又改回 A；线程 1 再做 CAS 时会成功，却不知道中间发生过变化。如果业务只关心最终值，这未必是问题；如果中间变化代表节点被移除重用、余额经过一次操作或状态版本改变，就可能出错。

常见办法是把版本号和业务值一起比较，每次修改都递增版本。例如 Java 可以使用 `AtomicStampedReference`；也可以使用不可重复的对象引用、单调版本号，或在链表场景配合内存回收方案，防止地址复用。核心不是“禁止 A 再出现”，而是让 CAS 比较 `(value, version)`，从而识别 A 是否还是原来的 A。

### 10. MySQL 常见锁有哪些？（一面第 10 题）

可以从粒度和模式两条线回答。粒度上有全局锁、表级锁和 InnoDB 行级锁；表级还常见元数据锁 MDL、意向锁和自增相关锁。模式上有共享锁 S 和排他锁 X，意向锁用于让表级锁快速判断表内是否存在行锁。

InnoDB 的所谓“行锁”实际加在索引记录或索引区间上，常见有 Record Lock、Gap Lock 和 Next-Key Lock。Record Lock 锁索引记录，Gap Lock 锁记录之间的间隙，Next-Key Lock 是记录锁加前面的间隙锁，主要用于当前读的范围保护。唯一索引等值命中等情况下可能退化成记录锁；具体锁范围取决于隔离级别、索引、查询条件和是否命中，不能只看 SQL 表面猜测。

### 11. 事务 ACID 分别怎样保证？（一面第 11 题）

- **Atomicity，原子性：**事务中的修改要么全部提交，要么全部回滚。InnoDB 通过事务状态、Undo Log 等机制支持回滚。
- **Consistency，一致性：**事务把数据库从满足约束的状态带到另一个满足约束的状态。它是最终目标，需要数据库的原子性、隔离性、持久性以及主键、唯一键、外键、业务校验共同保证，不是一种单独日志直接“保证”的。
- **Isolation，隔离性：**并发事务之间的影响受到控制。InnoDB 结合锁和 MVCC 实现不同隔离级别。
- **Durability，持久性：**提交成功后的修改即使进程或机器异常也能恢复。InnoDB 主要依靠 Redo Log 和刷盘策略；涉及主从复制或 Binlog 时，还要结合两阶段提交和相应持久化配置理解边界。

一句话总结：Undo 更直接服务于回滚和 MVCC，Redo 更直接服务于崩溃恢复，锁与 MVCC 服务于隔离，而一致性是这些机制与业务约束共同达到的结果。

### 12. 实习项目中的数据库使用什么隔离级别？（一面第 12 题）

这是一道事实题，不能直接用“MySQL 默认是 RR”代替项目答案。建议回答：“我会先核对线上数据源配置和数据库实例配置。MySQL/InnoDB 常见默认值是 `REPEATABLE READ`，但团队也可能为了减少间隙锁或与框架规范一致而使用 `READ COMMITTED`。我参与的具体服务是 **[请填真实隔离级别]**，通过 **[配置文件/数据源参数/查询结果]** 确认。”

然后说明业务影响：如果是 RC，每条一致性读通常建立新的 Read View，读到已提交的新版本；如果是 RR，同一事务中的一致性读通常复用 Read View。无论哪种级别，转账、库存等不变量都不能只依赖“隔离级别名称”，还需要条件更新、唯一约束或显式锁。

### 13. RR 下怎样处理幻读？（一面第 13 题）

先区分两类读。普通 `SELECT` 的一致性读通过 MVCC 和 Read View 读取适合该事务的版本，同一事务后续一致性读通常不会看到其他事务后来提交的新行，因此在快照语义下避免了幻读现象。

`SELECT ... FOR UPDATE/FOR SHARE`、`UPDATE`、`DELETE` 属于当前读或锁定读，要读取较新的已提交版本，并通过 Record/Gap/Next-Key Lock 保护索引记录和范围，阻止其他事务向受保护间隙插入，从而处理幻读。若条件没有合适索引，锁定范围可能扩大；唯一索引等值命中时也可能只需要记录锁。

需要补充的边界是：RR 不是让事务看到一个永远不变的物理世界。比如先做快照读、自己再更新某行，后续读取行为需要结合当前读和自身修改分析。遇到关键业务不变量，应通过唯一约束、条件更新或显式锁验证，而不是只背“RR 完全解决幻读”。

### 14. 联合索引 ABC，WHERE 中写 A、C、B 等值条件能否完整使用？（一面第 14 题）

如果索引是 `(A, B, C)`，查询写成 `WHERE A = ? AND C = ? AND B = ?`，三个条件都是等值比较且类型、排序规则等可兼容，那么条件在 SQL 文本中的书写顺序通常不影响结果。优化器可以规范化和重排条件，仍可利用 `(A, B, C)` 的连续前缀进行定位。

最左前缀原则约束的是索引键顺序，不是 `WHERE` 的书写顺序。如果缺少 B，只有 `A = ? AND C = ?`，通常先用 A 定位，C 是否可借助索引条件下推减少回表，要看执行计划，但它不能像完整的 A、B、C 前缀那样继续缩小 B+ 树搜索区间。最终应结合表结构、数据分布以及 `EXPLAIN ANALYZE`，不能仅凭题面断言扫描行数。

### 15. 常见索引不能高效使用的情况有哪些？（一面第 15 题）

常见情况包括：联合索引缺失最左前缀；在可索引列上做函数或表达式运算；字符串列与数字等发生不合适的隐式类型转换；`LIKE '%keyword'` 以前导通配符开头；范围条件之后的列无法继续用于精确定位；`OR` 的分支缺少可用索引；排序方向或列顺序与索引不匹配；条件选择性太低，优化器估算全表扫描更便宜；返回列很多导致大量回表。

但“不能高效使用”不等于“一定完全不用索引”。例如范围后的列可能通过 Index Condition Pushdown 在存储引擎层过滤，`IS NULL`、`!=`、`OR` 也不是绝对无法用索引。实际排查要看慢日志、`EXPLAIN ANALYZE` 的实际行数、回表次数、排序和临时表，并检查统计信息，而不是背一份绝对化清单。

### 16. 什么是回表？（一面第 16 题）

在 InnoDB 中，聚簇索引叶子节点保存整行数据，二级索引叶子节点通常保存二级索引列和主键。当查询通过二级索引找到主键，但需要的其他列不在该二级索引中时，还要用主键再查一次聚簇索引，这一步叫回表。

例如表的主键是 `id`，索引是 `(user_id)`，查询 `SELECT name FROM user WHERE user_id = ?` 时，如果 `name` 不在二级索引中就需要回表；查询只返回 `id` 和 `user_id` 时通常可以直接由二级索引覆盖。覆盖索引能减少回表，但会增加索引体积和写放大，是否值得要结合查询频率、选择性、字段宽度和执行计划判断。

### 17. Spring `@Transactional` 的底层实现是什么？（一面第 17 题）

Spring 声明式事务主要基于 AOP 代理。容器创建 Bean 时识别事务元数据，为目标对象生成 JDK 动态代理或 CGLIB 代理；外部调用经过代理后，`TransactionInterceptor` 根据传播属性、隔离级别、只读和回滚规则，通过 `PlatformTransactionManager` 开启或加入事务，再调用目标方法，最后根据返回或异常提交、回滚。

以 JDBC 为例，同一事务中的连接等资源通常通过线程绑定机制关联到当前线程，所以同一线程内的 DAO 操作可以复用事务上下文。底层真正执行事务的是数据库连接和事务管理器，注解本身只是声明元数据。也正因为依赖代理和线程上下文，自调用、跨线程等场景容易出现事务没有覆盖到的情况。

### 18. 哪些场景会导致 `@Transactional` 不生效？（一面第 18 题）

高频场景有：对象不是 Spring Bean；同一个类内部用 `this.method()` 自调用，绕过代理；方法无法被当前代理方式覆盖或拦截，例如 `private`、`final` 等不合适的方法；异常在方法内部被捕获后没有继续抛出；默认只对 `RuntimeException` 和 `Error` 回滚，而实际抛出受检异常却没有配置 `rollbackFor`；新建线程或异步任务后事务上下文没有自动传播；选错事务管理器或访问了不受它管理的数据源；传播属性让内部方法挂起、另起或根本不开事务。

另外，数据库表不支持事务、方法实际上没有发生数据库操作、异常发生在提交之后等，也可能让现象与预期不同。排查时应确认调用是否经过代理、事务日志和连接是否一致、异常类型与回滚规则、传播属性以及最终数据库提交，而不是只看有没有注解。

### 19. Spring 事务传播属性有哪些？（一面第 19 题）

Spring 定义了七种常见传播行为：

- `REQUIRED`：有事务就加入，没有就新建，是默认值。
- `REQUIRES_NEW`：始终新建事务，外层事务暂时挂起，内外可以独立提交或回滚。
- `SUPPORTS`：有事务就加入，没有就以非事务方式执行。
- `NOT_SUPPORTED`：以非事务方式执行，并挂起现有事务。
- `MANDATORY`：必须在现有事务中执行，否则抛异常。
- `NEVER`：必须在无事务环境执行，存在事务就抛异常。
- `NESTED`：有事务时基于保存点形成嵌套回滚范围；没有事务时通常类似 `REQUIRED`，是否支持取决于事务管理器和底层资源。

容易混淆的是 `REQUIRES_NEW` 与 `NESTED`：前者是独立物理事务，可能需要额外连接；后者通常共享外层物理事务，只用保存点局部回滚，外层最终回滚时它也不能独立保住结果。传播同样依赖代理调用，自调用时配置可能根本没有机会生效。

### 20. 使用 Claude Code/Codex 时会用什么插件或工具？（一面第 20 题）

我不会把回答变成插件名称清单，而是按开发闭环说明用途。理解仓库时，我会用文件搜索、代码检索和依赖分析定位调用链；实现时让工具做小范围补丁；验证时运行单测、静态检查、构建并查看 Git Diff；查时效性强的 API 时只参考官方文档；需要接外部系统时，可以通过 MCP 或受控插件提供结构化工具；重复性流程再沉淀成 Skill 或项目规则。

我使用这类工具的原则是：先明确任务和验收条件，只给必要权限，涉及删除、部署、发送消息等外部副作用时人工确认；生成代码后必须自己审查边界、异常处理、安全和测试结果。工具提高的是检索与执行效率，不替代需求判断和最终责任。面试时只说自己确实使用过的能力；Codex 当前的 Skills、MCP、插件等术语可参考 OpenAI 官方文档，Claude Code 的具体插件也应按实际配置回答。

### 21. 最近在学习什么新知识？（一面第 21 题）

可以选择一条与岗位和项目能形成闭环的主线。例如：“我最近在系统学习 Agent 的上下文工程和可恢复执行，同时补 Go 并发、JVM、MySQL 与缓存基础。学习方式不是只看文章，而是先理解状态管理、检查点、幂等和评测原理，再在小项目或代码实验中验证，最后整理失败场景和监控指标。”

接着给一个具体例子：“例如学习并发调用时，我会同时考虑结果映射、超时取消、部分失败、panic 恢复和并发上限；学习上下文压缩时，也会同时测 Token、任务成功率和延迟。”这样能体现学习不是追热点，而是能转化成工程判断。具体主题请换成最近确实学习、能够继续追问十分钟的内容。

## 二面逐题解答（第 22～54 题）

### 22. 请做自我介绍。（二面第 1 题）

二面的自我介绍可以更快进入项目。建议口述：“面试官您好，我是吉林大学计算机相关专业的 2027 届本科生，求职方向是服务端开发。我有后端和 Agent 工程相关经历，主要使用 Go、Java、MySQL、Redis。最近一段经历中，我重点接触了 Agent 上下文管理和并发执行；另一段项目中，我参与过搜索链路的 RPC 编排与缓存优化。我的优势是愿意把业务问题拆到数据结构、并发、容错和评测指标上，而不是只完成正常路径。今天我可以重点介绍上下文优化或搜索链路性能优化。”

> 边界：公司、项目和“参与/主导”用词必须按真实经历修改。二面介绍只抛出自己能够接受连续追问的两条主线。

### 23. 字节是否主要做 AI？所谓 Agent 基建、内部框架和个人职责分别是什么？（二面第 2 题）

回答时分三层，不要把它们混在一起。第一层是团队业务：字节整体业务很多，我所在团队是否主要做 AI，要按实际组织说明，不能把公司或大部门概括成只做 AI。第二层是 Agent 基建：它通常包括模型接入、会话和上下文、Tool 注册与调用、执行编排、评测、监控以及权限治理。第三层是个人职责：明确自己负责的是其中哪些模块、写了哪些代码、参与了哪些方案和验证。

可直接套用的口径是：“团队在 **[业务场景]** 中使用 Agent，内部框架提供 **[真实能力]**。我没有从零开发整个框架，个人主要负责 **[模块 A]** 和 **[模块 B]**，包括需求分析、实现、测试或指标验证；模型训练、底层推理服务和其他平台能力由相应团队负责。”这样既说明全貌，也不会把平台成果全部归到自己名下。

### 24. 挑一个最能体现能力、难点或分析过程的项目。（二面第 3 题）

可以选择上下文优化项目，用 STAR 加决策链回答。背景是多轮 Agent 把完整历史反复塞入提示词，导致输入 Token、延迟和噪声随轮次增长；任务不是简单截断，而是在减少输入的同时保留完成任务所需证据。

我的分析过程可以按四步讲：先通过调用链和日志确认 Token 主要花在什么类型的历史内容；再建立原始全量、滑动窗口、摘要和分层检索等基线；随后把原文保存在可靠存储中，把索引、摘要和指针放进可检索层，按任务相关性和预算加载；最后用固定任务集做成对回放，比较任务质量、输入 Token、延迟和失败率，并对遗漏案例分类迭代。

真正体现能力的不是“用了向量库”，而是能说明为什么选该方案、丢失信息时如何回退、索引怎样重建、指标分母是什么，以及自己具体负责哪几步。具体结果数字和职责请只使用可由实验记录或代码证明的内容。

### 25. 上下文的数据结构怎样组织，完整内容存在哪里？（二面第 4 题）

我会把“事实源”和“送给模型的工作集”分开。事实源保存完整消息、Tool 请求与结果、制品引用和版本，使用稳定的 `conversationId/runId/messageId/stepId` 关联，放在可持久化的数据库或对象存储中；运行时状态只保存当前目标、计划、节点状态、最近若干轮、摘要、检索结果引用和预算。

一条可检索记录至少要有：稳定 ID、所属会话和步骤、角色/内容类型、时间、原文位置、权限范围、摘要或关键词、向量/倒排索引字段以及版本。大对象和 Tool 产物不应整块复制进每轮上下文，而是保存 URI、摘要、校验信息和按需读取方式。

这样做的好处是索引和摘要都是可重建的派生数据，丢失时原文仍在；模型上下文也只是带预算的视图，不等于系统全部历史。至于具体使用 MySQL、文档库、对象存储还是向量库，要按真实架构回答。

### 26. 按需取回历史内容后会不会再次造成上下文膨胀，加载策略是什么？（二面第 5 题）

会，所以“能检索”不等于“全部加载”。加载策略需要同时限制候选数、内容长度和总 Token。一次典型流程是：先用会话、时间、任务阶段和权限做元数据过滤，再用关键词/向量召回候选，必要时重排；随后按相关性、时效性、信息类型和去重结果选取最小证据片段，并设置每类内容和整轮的 Token 预算。

对于超长命中，可以先放结构化摘要和原文指针，只有模型或工作流明确需要细节时再展开局部；连续重复引用要去重，旧检索结果不应无条件累积到后续每轮。超过预算时按规则淘汰低价值内容，而不是截断系统约束、用户最新请求或关键事实。

最终还要监控“召回了多少、实际注入多少、哪些被使用、哪些导致失败”。如果总是把 Top K 原文永久追加到对话，检索只会把一次性的全量膨胀变成逐轮累积膨胀。

### 27. 摘要压缩会丢失细节，有什么弊端？（二面第 6 题）

主要风险有四类：第一，实体、数字、否定词、条件和异常栈等细节被省略；第二，多轮因果关系、时间顺序和“谁说了什么”被扁平化；第三，不确定信息被摘要成肯定结论；第四，摘要错误在后续轮次被反复引用，形成信息漂移。对于代码和 Tool 输出，摘要还可能丢失精确字段、引用位置和可复现证据。

缓解方式不是要求一个摘要包办所有内容，而是做分层保存：原文永远作为事实源，摘要带来源 ID、版本和时间；关键约束、决策、未解决问题使用结构化字段单独保存；高风险任务允许回查原文；新信息与旧摘要冲突时重新生成或局部更新。评测中还要专门构造数字、否定、跨轮引用和长期依赖案例，观察摘要是否造成任务失败。

### 28. 怎样评测上下文压缩与检索方案？（二面第 7 题）

我会采用离线成对评测加小流量在线验证。先从真实任务分布中脱敏抽样，补充长对话、跨轮引用、数字和异常等挑战集，并定义任务级期望结果。然后固定模型版本、参数、Tool 和最大步数，让“完整上下文基线”和“压缩/检索方案”运行同一批任务；随机性较强时重复多次，记录均值、分位数和失败样本。

离线比较任务成功率或可验证答案、关键事实召回、输入 Token、端到端延迟、费用、Tool 错调和恢复成功率，再做消融实验区分摘要、召回、重排和预算分别带来的影响。通过离线门槛后才灰度上线，观察真实分布下的质量投诉、回退率、P95/P99 延迟和成本，并保留快速回滚开关。

人工评分必须有评分标准和盲测，避免评审者知道方案后产生偏差。不能只拿几个“看起来成功”的案例算平均 Token，就宣称方案有效。

### 29. 评测主要看哪些维度？（二面第 8 题）

至少看四组指标：

- **任务质量：**任务完成率、答案正确性、关键事实召回率、引用或证据一致性、Tool 参数正确率。
- **效率成本：**每个完成任务的输入/输出 Token、模型调用次数、端到端 P50/P95/P99 延迟和费用。
- **稳定性：**超时、重试、空召回、错误上下文、降级和恢复成功率，以及不同轮次长度下的波动。
- **安全与工程性：**权限过滤是否正确、敏感内容是否越界、索引新鲜度、可重建性和可观测性。

主指标要根据业务确定，例如客服场景可能优先正确性和合规，交互式助手还重视延迟，批处理更关注成本。Token 下降只能作为效率指标，不能代替任务质量。

### 30. 某个维度不达预期时，怎样决定优化哪个点、如何迭代？（二面第 9 题）

先对失败样本分桶，再定位链路阶段，不直接调一个全局 Top K。比如关键事实根本没进入候选集，优先改切分、查询改写、过滤或混合召回；候选中有正确内容但排序靠后，改重排特征；命中内容正确却被 Token 预算截掉，改预算分配和去重；上下文正确但回答仍错，则看 Prompt、Tool 设计或模型能力。

每次只改一个主要变量，使用同一评测集做回归和消融，并同时看副作用。例如提高 K 可能提升 Recall，却增加 Token、延迟和噪声；更激进摘要可能降成本，却损害数字准确性。达到离线门槛后再灰度，设质量护栏和回滚条件，避免平均值变好但长尾任务恶化。

### 31. 上下文索引丢失/损坏、DB 未取到、抖动或性能异常时怎么办？（二面第 10 题）

设计原则是：原始上下文是事实源，索引和摘要是可重建的派生数据。索引记录要有版本、校验和、构建状态和原文指针；发现缺失或版本不一致时，把重建任务幂等地放入队列，期间可以退化到最近窗口、关键词查询或直接按 ID 读取原文。大规模重建可使用新旧索引双写/双读和别名切换，避免原地覆盖。

DB 超时或抖动时，先使用短超时、有限重试和指数退避加随机抖动；重试必须在总请求 Deadline 内，并限制并发，避免把故障放大。持续异常时通过熔断、隔离和降级返回“信息可能不完整”的结果，对强依赖任务则明确失败，不伪造上下文。缓存只能作为有版本和有效期的加速层，不能悄悄覆盖事实源。

观测上记录召回空结果率、索引版本差、重建积压、存储延迟、超时和降级比例，并保留 requestId/runId 便于追踪。安全优先：权限过滤失败时应拒绝读取，而不是为了可用性返回越权内容。

### 32. 当前历史上下文检索效果怎么样？（二面第 11 题）

不要只回答“效果挺好”。正确结构是：“当前在 **[数据集/灰度范围]** 上，相对 **[完整历史或旧方案]**，关键任务成功率是 **[真实值]**，关键事实 Recall@K 是 **[真实值]**，每个完成任务的输入 Token 和 P95 延迟分别变化 **[真实值]**。主要失败仍集中在 **[跨轮指代/数字/极长 Tool 输出等]**，所以目前是 **[实验/灰度/上线]** 状态。”

如果没有正式指标，可以诚实说：“现在只有功能验证和少量案例观察，还不能给出稳定的线上效果结论。下一步会建立固定任务集和基线，至少补质量、Token、延迟和失败分类。”没有评测时说“目前无法量化”，比用主观感受或单个案例冒充效果更可信。

### 33. 为什么面服务端岗位？Agent 与传统后端有何差异，职业方向怎样选择？（二面第 12 题）

我的主线仍是服务端工程。Agent 应用最后也要落到 API、状态、数据库、缓存、队列、权限、监控和稳定性上，这些正是后端能力；我学习 Agent 是在扩展后端解决问题的边界，而不是放弃后端去做自己没有训练经验的模型算法岗位。

传统后端的接口和状态转移通常更确定，输入相同更容易得到可预期结果；Agent 中模型输出具有概率性，执行路径可能动态变化，还会引入 Token 预算、上下文污染、Tool 越权、评测和人工审核等问题。因此 Agent 工程需要在传统后端基础上增加受控编排、可恢复状态、护栏和评测。

职业选择上，我希望先把服务端基本功做深，同时选择有 AI 应用场景的团队，把二者结合。这样回答能形成稳定方向，而不是给面试官“哪个热门就投哪个”的感觉。

### 34. Go 并发模块是参与还是主要开发，个人参与度多少？（二面第 13 题）

这道题必须给职责边界，建议用“设计、编码、测试、上线、指标”五项拆开说。例如：“整体方案由 **[谁]** 负责，我主要承担 **[具体模块]**；我独立实现了 **[文件/接口/机制]**，参与了 **[评审或联调]**，测试覆盖了 **[场景]**，上线和指标观察由 **[角色]** 共同完成。因此我把自己的参与定义为 **[主开发/共同开发/局部参与]**，不是整个并发框架的负责人。”

参与度不要只给“70%”一类无法验证的数字。面试官真正想知道的是：哪些关键决策是你做的，哪段代码你能从数据结构讲到失败路径，哪些是 mentor 或平台提供。准备时最好能指出一个请求从父 goroutine 到子任务、结果汇总、取消和异常处理的完整调用链。

### 35. goroutine 乱序完成时，怎样保证结果与调用一一对应？（二面第 14 题）

并发完成顺序和业务结果顺序要解耦。最直接的方法是在启动任务时固定索引，预先分配结果数组，每个 goroutine 只写自己下标的位置；或者通过 channel 返回带 `index/requestID` 的结果，汇总协程按标识放回对应位置。不能把“channel 收到的先后顺序”误当成原调用顺序。

```go
type result struct {
	index int
	value Item
	err   error
}

results := make([]Item, len(requests))
ch := make(chan result, len(requests))
for i, req := range requests {
	go func(index int, request Request) {
		value, err := call(request)
		ch <- result{index: index, value: value, err: err}
	}(i, req)
}
for range requests {
	r := <-ch
	if r.err == nil {
		results[r.index] = r.value
	}
}
```

每个下标只有一个写者时，不会发生同一槽位的并发写冲突；如果还要收集错误，也应按相同索引保存。生产代码还要加入 `context` Deadline、并发上限和 panic 保护，不能为每个不受控输入无限创建 goroutine。

### 36. 并发调用部分成功、部分失败怎么办？（二面第 15 题）

先按业务依赖分类，而不是统一“失败就重试”。强依赖结果缺失会让整体结果错误，应取消剩余任务并返回失败，或执行明确的兜底；弱依赖可以保留成功结果，对失败分支有限重试、使用缓存/默认值并标记降级；如果各分支可以独立展示，也可以返回部分成功及每项状态。

重试要判断错误是否可重试，设置单次超时、总 Deadline、最大次数、指数退避和随机抖动，同时限制并发，避免重试风暴。写操作还必须有幂等键或条件更新。汇总层要保存每个分支的成功、失败、超时和降级原因，并监控部分失败率；不能把空值静默当成正常结果，也不能因一个非关键 RPC 失败就无条件拖垮整条链路。

### 37. 子 goroutine 发生 panic 怎样捕获，会怎样影响主进程，如何保证 recover？（二面第 16 题）

`recover` 只能在发生 panic 的同一个 goroutine 中、通过延迟执行的函数直接调用才有意义，父 goroutine 不能替子 goroutine 捕获。因此要在每个任务的入口统一包一层：

```go
func safeRun(ch chan<- error, task func() error) {
	defer func() {
		if value := recover(); value != nil {
			ch <- fmt.Errorf("panic: %v\n%s", value, debug.Stack())
		}
	}()
	ch <- task()
}
```

如果某个 goroutine 的 panic 一直没有被 recover，Go 进程通常会打印堆栈并退出，并不是只结束那一个 goroutine。`recover` 也不能捕获致命运行时错误或另一个进程的崩溃。

“保证 recover”应靠统一 goroutine 启动器或任务池封装，而不是要求每个业务开发者手写；恢复后还要带 requestId 记录堆栈、上报指标并把该分支标记为失败。recover 只是防止进程被意外 panic 带崩，不能假装任务成功，也不应掩盖应当尽快修复的程序错误。

### 38. WaitGroup 的核心方法是什么？只 Add 不 Wait 会怎样？（二面第 17 题）

核心方法是 `Add(delta)`、`Done()` 和 `Wait()`。父 goroutine 在启动子任务前调用 `Add(n)`；每个子 goroutine 通常进入后立刻 `defer wg.Done()`；父 goroutine 调用 `Wait()`，直到计数归零。`Done()` 等价于 `Add(-1)`。

只 `Add` 不 `Wait` 不会产生任何等待效果。若 `main` 或请求处理提前返回，子 goroutine 可能还没执行完，进程甚至可能直接退出；如果其他逻辑也不读取结果，还可能造成资源浪费或 goroutine 泄漏。反过来，如果调用了 `Wait` 却漏掉 `Done`，会永久阻塞；`Done` 次数多于 `Add` 会触发负计数 panic。

还要注意时序：应在启动 goroutine 前完成对应的 `Add`，不要让 `Wait` 与“为新一批任务执行 Add”发生不受控竞态。新代码也可以根据 Go 版本和团队规范使用更高层的任务组封装，但异常传播、取消和结果收集仍需另外设计。

### 39. 使用过 errgroup 吗？（二面第 18 题）

如果真实项目中用过，可以回答：`errgroup` 适合管理一组属于同一任务的 goroutine。`group.Go` 启动任务，`Wait` 等待并返回首个非空错误；`errgroup.WithContext` 会提供可取消的派生 `context`，某个任务失败后，其他任务应监听 `ctx.Done()` 尽快停止；`SetLimit` 可以限制同时运行的任务数。

它比裸 `WaitGroup` 多解决了错误传播、取消和并发限制，但不是完整业务方案。它不负责按原顺序存结果，不替业务判断部分失败是否可接受，也不能替代超时、重试、幂等；任务内部 panic 仍应在同一 goroutine 的统一入口处理。若没有在生产项目使用过，应说“了解并做过实验/阅读过源码”，不要把学习经历说成线上经验。

### 40. Go 服务中什么会导致 panic？讲一个实际遇到的案例。（二面第 19 题）

常见原因包括 nil 指针解引用、数组或切片越界、关闭已关闭的 channel、向已关闭的 channel 发送、错误的类型断言、重复解锁，以及代码显式调用 `panic`。并发写普通 map 可能触发运行时致命错误，不能指望普通 `recover` 把所有这类错误都安全兜住。

实际案例必须使用本人真实经历，可按下面结构组织：“一次在 **[场景]** 中，**[输入或并发条件]** 触发了 **[具体 panic]**。我通过请求 ID 和堆栈定位到 **[代码位置]**，先通过 **[校验/降级/回滚]** 止损，再修复 **[根因]**，补了 **[单测、竞态测试或监控]**，并检查相同模式是否在其他调用点存在。”

如果没有真实线上 panic，可以明确说没有处理过线上事故，再讲本地遇到的 nil、切片越界或 channel 关闭问题及复现过程。面试官考察的是定位和复盘能力，编造一个线上事故风险更大。

### 41. Go 使用了多久，是否主要用于字节 Agent 项目？（二面第 20 题）

时间必须按真实起点回答，并区分“开始学习”“实际写项目”和“持续用于实习”。建议说：“我从 **[年月]** 开始学习 Go，累计约 **[真实时长]**；主要在 **[真实项目]** 中使用，负责过 **[接口/并发/存储等]**。字节 Agent 项目是重要使用场景之一，但如果还有其他 Go 项目，我会分别说明；如果主要只在这一段使用，也会如实讲。”

随后用能力证明时间：能解释 goroutine、channel、context、错误处理、`defer/panic/recover`、WaitGroup/errgroup、并发安全和 profiling，并能展示一个真实模块的调用链。语言熟练度不应只由月份包装，也不要把“看过语法”累计成生产使用年限。

### 42. 美团为什么把串行召回改成并行，问题如何发现，效果怎样？（二面第 21 题）

先讲证据：通过 Trace 把端到端延迟拆到各阶段，发现两个或多个相互独立的远程召回在同一请求中串行等待，整体耗时近似为各分支耗时之和，而且它们之间没有数据依赖。这时并行化才可能把该段关键路径从“求和”降为“取较慢分支”，但仍受调度、汇总和下游排队影响。

方案上要保留总 Deadline，为每个 RPC 分配子超时，使用有界并发和隔离的资源池，按请求 ID/下标汇总结果，并根据强弱依赖设计部分失败策略。上线前做压测，确认下游 QPS、连接池和线程池能承受瞬时并发增加；上线时灰度并观察主链路与下游的 P50/P95/P99、超时率、错误率、线程池队列和熔断情况。

效果必须说真实基线、样本窗口和分位数：“在 **[流量和时间窗口]** 下，主链路 **[P95/P99]** 从 **[A]** 到 **[B]**，下游错误率和资源水位没有超过 **[护栏]**。”如果只能确认“约 10ms”或其他均值，必须说明它是哪个统计口径，不能从公式直接推导成线上收益。

### 43. 两个 RPC 对整体流程是强依赖还是弱依赖？并行后部分失败怎样处理？（二面第 22 题）

强弱依赖由业务正确性决定。强依赖是缺少结果就无法得到合法答案，例如权限校验或最终价格；失败时应快速失败、取消其他分支，或者切换到经过验证的强一致兜底。弱依赖只影响丰富度或排序，可以保留成功分支，对失败分支使用有版本和时效要求的缓存、默认策略或降级结果，并显式记录降级。

如果两个 RPC 一个强、一个弱，汇总层要分别处理，不能用同一 `allOf` 异常策略一刀切。所有分支都要有子超时且受总 Deadline 约束；可重试错误做有限重试，写操作保证幂等；持续失败触发熔断和告警。面试时应给出这两个真实 RPC 的业务含义，然后说明缺失各自结果会不会造成错误，而不是仅凭“召回”二字认定都是弱依赖。

### 44. 实际并行了几个 RPC，它们与其他召回链路是什么关系？（二面第 23 题）

这是事实核验题，直接给出真实拓扑。推荐画成：“主请求完成 **[前置步骤]** 后，同时启动 **[RPC A]** 和 **[RPC B]**；**[RPC C]** 依赖 A 的结果，因此仍在 A 后执行；本地规则与远程分支 **[并行或串行]**；最后由汇总节点合并、去重和排序。”

如果实际只并行两个 RPC，就明确说“并行的是两个，不是整条召回链路全部并行”。还要说明为什么其他分支没有并行，例如存在数据依赖、调用成本低、下游容量不足或并行收益小。可以用 DAG 表达依赖，但不要为了显得复杂而扩大 RPC 数量或把 Client 的一次调用拆成多个虚构服务。

### 45. POI 品类数据模块解决什么业务问题，怎样实现？（二面第 24 题）

POI 是 Point of Interest，即门店、景点等地点实体。品类模块通常是把 POI 或其属性映射到标准品类体系，让召回、过滤、排序、展示或运营规则使用统一口径，避免各业务自己维护不一致的判断。面试时要明确缓存的是“POI 到品类的映射”“品类树/基础属性”，还是两者都有，它们的数据量和更新方式完全不同。

一个完整实现包括：上游事实源维护带版本的品类数据；服务启动或定时任务加载快照；增量变更通过配置、消息或版本轮询传播；读路径按 `poiId/categoryId` 查询不可变内存快照，更新时构建新快照并原子替换；加载失败保留旧版本，并监控版本差、加载耗时和命中率。若数据量不适合全量内存，应按访问模式使用本地有界缓存加远端存储，而不是无上限加载。

具体业务规则、数据源、更新链路和个人负责部分必须按真实项目替换，不能把这套通用设计当成已上线事实。

### 46. 本地缓存遇到热 Key/冷启动有什么影响，怎样解决？（二面第 25 题）

热 Key 在本地缓存中不一定是坏事：如果数据只读或可安全缓存，它能把远程热流量分散到每个实例；但过期或失效瞬间，大量请求可能同时回源，形成击穿。可以使用请求合并/单飞、互斥重建、逻辑过期、TTL 随机化和必要的限流，更新后还要通过版本或失效通知保证各实例不会长期读旧值。

冷启动时缓存为空，新实例可能瞬间把压力打到 Tair/Redis 或数据库。可以根据真实热点做预热，使用就绪探针让实例在关键数据加载后再接流量，逐步放量，并限制回源并发。若数据全集不大且版本明确，可加载完整不可变快照；若数据很大，只预热高频集合，避免启动时间和内存不可控。

本地缓存还要设置最大容量、淘汰策略、TTL/版本、命中率和内存监控。多实例各自复制热点会消耗总内存，但也避免所有请求集中到一个远端节点，取舍要由数据大小、更新频率和一致性要求决定。

### 47. Tair 是什么，与 Redis 有何区别或增强？（二面第 26 题）

Tair 这个名称可能指阿里云的兼容 Redis 的内存数据库产品，也可能指公司内部封装或历史系统，面试时先确认语境。一般可回答：它向业务提供类似 Redis 的 Key-Value/数据结构访问，客户端仍通过网络协议调用服务端；在兼容常用 Redis 能力的基础上，具体产品版本可能增强持久化、可用性、容量、性能或扩展数据结构，并提供云上的监控和运维能力。

不能笼统说“Tair 一定比 Redis 快”或“Tair 就是 Redis”。开源 Redis 是具体软件及生态，Tair 的兼容范围、模块、部署形态和一致性边界取决于所用版本。项目回答应落到真实使用能力：用了哪些命令/数据结构、SDK 和超时，是否集群、故障切换怎样、数据是否可丢，而不是罗列没有用过的增强特性。

### 48. 还使用过哪些数据库？主从延迟会怎样影响业务，如何处理？（二面第 27 题）

先只列真实使用层级，例如“生产使用过 MySQL 和 Redis，MongoDB/Elasticsearch 只在学习或项目中使用”，并说明每种存储解决什么问题，避免把“听说过”当成使用过。

MySQL 异步复制存在延迟时，刚在主库提交的数据可能尚未到从库，随后读从会出现读不到、读到旧状态、重复创建或状态回退等问题。处理方式按一致性要求选择：写后读场景在短时间内路由主库或携带一致性标记；关键校验、扣减和状态机在主库事务中完成；弱一致查询允许从库延迟并在 UI 上说明；异步链路使用版本号、幂等和对账；监控复制位点、延迟和积压，延迟过高时摘除从库或降级。

不要用固定 `sleep` 等待复制，也不能默认“所有读都强制主库”。前者不可靠，后者会失去读扩展能力并可能压垮主库。

### 49. 强制读主有什么风险，怎样分散主库压力？（二面第 28 题）

风险是读流量与写流量争抢主库 CPU、Buffer Pool、磁盘 I/O、连接和锁资源，峰值时既拖慢查询，也可能影响写入和复制。主库一旦成为所有读写的单点容量瓶颈，故障切换后的新主库还可能承受不了原有总流量。

分散压力要先按一致性分级：只有写后读、权限/余额等关键查询走主库；列表、历史和可容忍延迟的数据走从库；使用会话级“读己之写”标记，只在必要窗口粘主；热点只读数据使用有版本和失效机制的缓存；离线分析走数仓或搜索系统。再通过索引和 SQL 优化、分页、批处理、连接池限流减少无效负载。

若单库仍不够，再评估分库分表等架构升级，但它会带来路由、跨分片事务、扩容和运维成本。所有路由都要根据复制延迟和健康状态动态摘除异常副本，不能把陈旧从库继续当正常服务。

### 50. 遇到过哪些 MySQL 性能问题？（二面第 29 题）

这是经历题，应讲一个能给出 SQL、数据规模、执行计划和验证过程的真实案例。推荐结构：“监控或慢日志发现 **[接口]** 的 **[P95/P99]** 异常；用 Trace 确认耗时在 SQL；`EXPLAIN ANALYZE` 看到 **[扫描行数、回表、filesort、临时表]**；根因是 **[联合索引不匹配/深分页/N+1/锁等待/统计信息等]**；通过 **[改 SQL、联合/覆盖索引、游标分页、批量查询]** 修复；在同一数据集和流量下对比延迟、扫描行数、CPU、写入开销并灰度。”

如果没有真实线上慢查询，可以坦白说主要在实验或代码评审中处理过，再演示分析方法。不能只回答“加了索引，从 500ms 到 10ms”，因为面试官会继续问数据量、索引列顺序、执行计划、缓存冷热、统计口径和写放大。

### 51. 完成最长公共子序列题并解释状态转移。（二面第 30 题）

按对话推断，题目是求两个字符串的最长公共子序列长度。子序列不要求连续。定义 `dp[i][j]` 表示 `text1` 前 `i` 个字符与 `text2` 前 `j` 个字符的 LCS 长度。

- 若 `text1[i - 1] == text2[j - 1]`，这两个相同字符可以接在前缀答案后，`dp[i][j] = dp[i - 1][j - 1] + 1`。
- 否则最后两个字符不能同时作为同一个新增匹配，至少舍弃其中一个，`dp[i][j] = max(dp[i - 1][j], dp[i][j - 1])`。

```java
class Solution {
    public int longestCommonSubsequence(String text1, String text2) {
        int m = text1.length(), n = text2.length();
        int[][] dp = new int[m + 1][n + 1];
        for (int i = 1; i <= m; i++) {
            for (int j = 1; j <= n; j++) {
                if (text1.charAt(i - 1) == text2.charAt(j - 1)) {
                    dp[i][j] = dp[i - 1][j - 1] + 1;
                } else {
                    dp[i][j] = Math.max(dp[i - 1][j], dp[i][j - 1]);
                }
            }
        }
        return dp[m][n];
    }
}
```

时间复杂度是 `O(mn)`，空间复杂度是 `O(mn)`；只求长度时可压缩到 `O(min(m,n))`。例如 `abcde` 与 `ace` 的答案是 3。若题目要求输出具体序列，需要从 `dp[m][n]` 反向回溯，不能只返回长度。

### 52. 传统 RAG 有什么作用、局限，怎样改进？（二面第 31 题）

传统 RAG 先从外部知识库检索与问题相关的片段，再把片段交给模型生成答案。它能补充模型训练后或私有领域知识，提供证据，也比把整个知识库塞进上下文更节省 Token。

局限主要来自整条链路：文档解析和切分可能破坏语义；只做向量相似度会漏掉精确关键词、数字和时间；用户问题可能需要改写或多跳检索；Top K 会引入噪声；知识可能过期或权限过滤错误；即使命中了证据，模型仍可能不遵循它或错误归纳。

改进要对应问题：使用结构化解析和合适粒度的父子块；结合 BM25/关键词与向量做混合召回；增加元数据和权限过滤、查询改写、重排、去重和动态 K；复杂问题做分解或多步检索；要求答案引用来源并允许“证据不足”；建立 Recall@K、答案正确性、时效性、延迟和成本评测。对于稳定结构化数据，直接查数据库或调用 Tool 往往比先转文本做 RAG 更可靠。

### 53. 幻觉通常为什么产生，怎样减少？（二面第 32 题）

大模型的目标是根据上下文生成高概率的后续 Token，不是天然执行事实校验。训练数据缺失、冲突或过时，问题含糊，上下文证据不足或带噪声，检索召回错误，以及采样随机性和错误指令，都可能让模型生成语言流畅但事实不成立的内容。Agent 中还会出现 Tool 结果解析错误或把旧状态当新状态等工程性“幻觉”。

减少方法包括：对时效或私有事实使用可靠检索、数据库和 Tool；提供清晰任务、结构化输入和来源；要求证据不足时拒答或澄清；用 Schema 校验结构化输出，对金额、状态等关键字段由确定性代码复核；降低不必要的随机性；对高风险操作设置权限、人工审批和可回滚机制；用针对性评测统计错误类型。

RAG 只能降低知识缺失导致的错误，不保证零幻觉；Tool 调用也可能失败或返回旧数据。最终要靠“可靠数据源 + 约束生成 + 验证 + 业务护栏”共同降低风险。

### 54. 大模型怎样预测下一个 Token？（二面第 33 题）

文本先由 Tokenizer 切成 Token ID，再映射成向量，并加入位置信息。Transformer 的多层自注意力和前馈网络让当前位置综合前文信息；由于使用因果掩码，生成当前位置时不能看到未来 Token。最后一层隐状态经过线性映射得到词表中每个 Token 的 logits，再经 softmax 形成条件概率分布 `P(token_t | token_<t)`。

解码时可以贪心选概率最高的 Token，也可以使用 temperature、top-k、top-p 等采样策略选一个 Token。选出后把它加入上下文，继续预测下一个，直到结束标记或达到限制。推理时 KV Cache 会复用此前注意力的 Key/Value，避免每一步从头计算全部历史。

训练阶段常用教师强制：给定真实前缀，让模型预测下一个真实 Token，通过交叉熵损失更新参数。模型学到的是数据中的统计规律和表示能力，因此“下一个 Token 预测”能够表现出推理和知识，但它本身不等于事实数据库，也解释了为什么仍需要检索、Tool 和校验。

## 三面逐题解答（第 55～79 题）

### 55. 从项目中选一个最有挑战、最复杂的项目展开。（三面第 1 题）

可以继续讲上下文优化，但三面要突出复杂性和取舍。建议开场：“我选择 **[真实项目名]**。它的难点不是接一次模型 API，而是长任务中历史信息持续增长，同时要兼顾质量、Token、延迟、故障恢复和权限。我的个人职责是 **[真实职责]**。”

然后按决策链展开：先用日志和 Trace 确认问题发生在哪些任务和轮次；把完整历史作为事实源持久化，设计分层索引、摘要和按需加载；为每轮设置 Token 预算并保留原文回查；处理索引损坏、存储超时、重复 Tool 调用和恢复幂等；建立固定任务集，与全量上下文基线做成对评测，再灰度观察线上质量和成本。

最后主动讲一个失败或反例，例如摘要丢失否定条件，或 Top K 增大后 Token 降幅消失，并说明怎样通过失败分桶修正。复杂项目的说服力来自问题、选择、代价、证据和个人边界，而不是组件数量。

### 56. 常见的上下文优化有哪些思路？（三面第 2 题）

可以分为六类：

- **减少无效输入：**去掉重复模板、无用日志和重复 Tool 结果，使用结构化状态代替整段自然语言。
- **保留近期窗口：**完整保留最近若干轮，对更早历史采用其他表示；窗口应按 Token/信息价值，而不只是固定消息数。
- **摘要压缩：**按阶段生成摘要，并单独保存事实、决策、约束和未解决问题，同时保留原文指针。
- **检索式加载：**历史完整存储，按当前任务通过关键词、向量、元数据过滤和重排取回必要片段。
- **外置大对象：**代码、文件和 Tool 大结果保存到对象存储或制品库，上下文中只放描述、URI 和按需读取接口。
- **工作流拆分：**让不同节点只看到最小必要状态；必要时用子任务隔离上下文，再把结构化结果汇总。

还可以使用 Prompt/前缀缓存降低重复计算成本，但它不等于减少逻辑上的上下文，也不能解决噪声。任何优化都要同时测任务质量、Token、延迟和稳定性，不能只追求压得更短。

### 57. 四层索引具体怎样划分和检索？（三面第 3 题）

“四层”必须与真实实现一致。若当前简历只写了概念而没有固定定义，可以采用下面这套清晰口径，但面试前要和代码核对：

1. **会话/任务层：**按用户、会话、任务类型、时间和权限快速筛掉无关会话，得到候选 `conversationId/runId`。
2. **阶段/主题层：**保存每个任务阶段或对话片段的摘要、关键词和时间范围，用于定位相关 episode。
3. **消息/事件层：**对消息、Tool 调用、决策和错误等细粒度记录建立倒排/向量及元数据索引，召回并重排证据片段。
4. **原文/制品层：**通过稳定 ID 读取完整消息、代码、文件或 Tool 结果，作为最终事实源。

检索时自上而下缩小范围：先做权限和任务过滤，再选阶段，随后混合召回并重排消息，最后只展开必要原文；若上层摘要不确定，可直接沿指针回查。每层都保存来源 ID、版本和校验信息，索引可由原文重建。

如果实际的四层是“关键词、摘要、向量、原文”或其他定义，应换成真实层次。面试官关心的是每层的数据、查找方式、解决的问题和失败回退，而不是数字“四”本身。

### 58. 四层分层是自己设计，还是参考开源方案？（三面第 4 题）

最稳妥的回答是把“思想来源”和“项目落地”分开：“分层检索、摘要记忆、向量召回并不是我原创的学术概念，我参考了 **[确实阅读过的论文/框架/内部设计]**。我个人完成或参与的是把这些思路映射到当前业务的数据模型、预算、恢复和评测上，例如 **[真实设计点]**；方案经过 **[谁]** 评审，最终由 **[真实人员]** 共同落地。”

如果只是看过 LangGraph 等方案，就说“参考其状态图/持久化思路”，不要声称复刻或基于它实现；如果公司内部框架已经提供基础能力，要明确自己是在其上设计业务分层。所谓“自己设计”不意味着从未参考他人，而是能指出哪些需求分析、取舍和实现由自己负责。

### 59. 多轮调用不可控，为什么能说输入 Token 降低约 21%？（三面第 5 题）

不能比较两次随机运行的总 Token 后直接下结论。合理口径是把统计单位定义为“完成同一个任务所消耗的累计输入 Token”，再做成对实验：使用同一批初始会话和用户请求，固定模型版本、参数、Prompt、Tool 集、最大步数和终止条件；基线使用原上下文策略，实验组使用新策略。随机性无法完全消除时，每个任务重复运行，并同时记录调用轮数、成功与否和输入 Token。

`21%` 应是测试集或灰度窗口上的经验结果，不是对任意多轮调用的理论保证。只有在两组任务质量达到同一门槛、任务完成率没有下降时，Token 比较才有意义；失败任务、重试和额外 Tool 轮次也要按预先规则计入，不能只挑成功且轮数较少的实验组样本。

如果当时没有固定模型和成对任务，只能把“约 21%”改称初步观测，并承认无法排除任务分布与随机性的影响，不能继续把它包装成严谨结论。

### 60. 约 21% 的输入 Token 降幅怎样验证？（三面第 6 题）

先定义公式。对同一组完成且质量达标的任务，分别汇总每一次模型调用的 `input_tokens`：

`降幅 = (基线累计输入 Token - 新方案累计输入 Token) / 基线累计输入 Token`

除了总体加权降幅，还应报告“逐任务降幅”的中位数、P25/P75 或置信区间，避免少数超长任务支配平均值。按任务轮数、类型和上下文长度分桶，检查收益是否只出现在某个子集。模型返回的 usage 字段或网关计量应作为统一数据源，并保留 runId，使每个数字能追溯到调用。

质量护栏至少包括任务成功率、关键事实正确率/召回率、Tool 错调和人工盲评；性能还看端到端延迟和模型调用次数。做摘要、分层检索、去重等消融实验，确认收益来源。最后小流量灰度并监控分布变化。文中的 `21%` 只有在这些证据存在时才能作为项目结果；否则面试前应改成真实可验证表述。

### 61. 输入 Token 是这个场景的主要评价指标吗？（三面第 7 题）

不是唯一指标，通常也不是最高优先级。上下文优化的第一约束是任务质量不能不可接受地下降，包括关键事实、业务规则、Tool 选择和最终结果正确；在质量护栏通过后，输入 Token 才是成本和部分延迟的重要指标。

我会根据业务确定一个主指标，例如任务成功率或证据一致性，再把输入 Token、端到端延迟、费用和调用轮数作为效率指标，把超时、降级、索引错误和越权作为稳定性/安全指标。一个方案即使 Token 降低 50%，如果任务成功率下降或 P99 因检索链路增加而恶化，也不能算成功。

相反，在离线批处理且质量持平时，Token 成本可能成为主要优化目标。因此“是否主要”取决于场景 SLO，但都要用多指标护栏避免单目标优化。

### 62. 这套 Agent 主要在什么场景使用？是不是推理轮次多才需要？（三面第 8 题）

它更适合长会话、多步骤 Tool 调用、需要跨阶段引用历史以及可以暂停恢复的任务，例如代码修改、调查分析、客服工单处理或复杂运营流程。此时完整历史会随步骤累积，分层状态和检索才有明显价值。

但是否需要不能只看轮数。少量轮次如果包含超长文件或 Tool 输出，同样需要外置和按需读取；很多很短且彼此独立的轮次，简单滑动窗口可能已经足够。应同时看累计 Token、历史复用距离、任务依赖、延迟预算和错误成本。

对于一次模型调用或固定两三步流程，不必上复杂四层检索，因为额外存储、索引和召回本身会增加延迟与维护成本。先使用最简单可满足 SLO 的方案，再由数据证明是否升级。

### 63. 已经有哪些实际使用场景？请举例。（三面第 9 题）

这里只能举真实已使用场景，并区分“线上使用、内部试用、离线评测和概念演示”。可按如下方式回答：“当前在 **[真实状态]** 的 **[真实场景]** 中使用。比如用户发起 **[任务]** 后，Agent 先读取最近状态，按需找回 **[历史决策/工具结果]**，调用 **[真实 Tool]**，校验后输出 **[结果]**。一次跨多轮的追问需要引用早期的 **[具体事实]**，这能体现上下文方案的价值。”

还要说明不用它的场景：“单轮 FAQ 或确定性查询直接用检索/接口，不经过复杂 Agent。”如果目前只有评测环境，应明确说“还没有生产用户”，再举一个已跑通的测试案例。不要把计划中的代码 Agent、风控 Agent 或客服 Agent 说成已经落地。

### 64. 这个例子中团队做的 Agent 在哪一层？是否不只做上下文？（三面第 10 题）

可以把系统分成四层说明：底层是模型和推理服务；中间是 Agent 运行时，包括会话状态、上下文、编排、Tool 调用、检查点和观测；再上面是业务 Workflow 与领域 Tool；最上层是产品入口和人工流程。然后指出团队和个人分别负责哪一层。

推荐口径：“团队做的不只上下文，还覆盖 **[真实能力]**；上下文只是运行时的一部分。我所在小组/个人主要负责 **[真实范围]**，模型训练、基础推理或产品前端由其他团队负责。”如果只参与上下文模块，也可以明确说对其他模块只有接口理解，没有实现职责。

面试官是在确认你是否把一个局部优化说成完整 Agent 平台。用分层架构和责任矩阵回答，比笼统说“全链路都参与”更可信。

### 65. 具体 Workflow 是你定义的吗？（三面第 11 题）

先给直接结论，再给证据。如果是共同设计，可以说：“业务流程和验收条件由产品/业务方提出，框架约束由平台提供；我负责把 **[若干步骤]** 建模成节点和条件边，定义 **[状态字段、重试、终止或回退]**，方案经过 mentor 和相关同学评审。因此不是我一个人从零定义全部 Workflow，但这部分设计和实现由我主要负责。”

如果只是接入既有 Workflow，就说清自己新增了哪个节点、Tool 或校验，不要回答“是我定义的”。准备证据包括设计文档、状态结构、节点图、关键提交、测试和评审记录。面试官随后很可能问为什么某一步是动态路由、失败怎样恢复以及替代方案，所以只有真正负责的部分才展开。

### 66. 概括美团搜索链路性能优化项目。（三面第 12 题）

建议用 90 秒讲完：“项目目标是降低 **[真实搜索接口]** 的尾延迟。我们先通过 Trace 和分阶段监控定位到 **[两个真实 RPC]** 在关键路径串行等待，且业务无数据依赖；同时确认瓶颈不是单个下游自身慢。我的工作是 **[真实个人职责]**，将这部分改为有界并行，按请求标识汇总，配置总 Deadline、子超时、部分失败策略和资源隔离，并补充线程池、下游错误率和延迟监控。”

“上线前通过压测验证下游容量，随后灰度观察主链路 P95/P99、超时和下游资源水位。最终在 **[真实窗口]** 下取得 **[真实效果]**，且 **[质量/错误率护栏]** 未恶化。代价是瞬时下游并发上升、线程池和故障处理更复杂，所以设置了限流和回滚开关。”

如果“约 10ms”是唯一已知数字，也必须补齐它是平均值还是分位数、基线是多少、样本和时间窗口是什么；没有证据就不要填。

### 67. 为什么每个 RPC 使用独立线程池？为什么不用 RPC 原生异步？（三面第 13 题）

独立线程池的主要理由是故障和资源隔离：不同下游的延迟分布、超时、并发配额和重要性不同。某个下游变慢时，它的任务只堆积在自己的有界队列，不会占满共享池拖住其他分支；每个池也能设置不同的并发上限、拒绝和监控。

但独立池不是默认最优。如果 RPC 框架提供成熟的非阻塞异步接口，它通常能减少等待期间占用的线程，更自然地组合 Future/Callback，并避免为每个下游维护一批阻塞线程。没有采用时必须给真实原因，例如现有 SDK 只有同步接口、改造范围和稳定性风险较大、团队缺少统一异步链路支持，不能说“线程池一定比原生异步快”。

正确比较还要看底层是否真的非阻塞：把同步 RPC 包进 `CompletableFuture` 只是把阻塞转移到线程池。后续若框架支持且收益明确，可以迁移到原生异步；无论哪种方式，超时、取消、并发上限和部分失败都不能省略。

### 68. 分线程池有什么好处、能否共用、代价是什么？（三面第 14 题）

好处是 Bulkhead 隔离、独立限流和独立观测。慢下游的阻塞、队列堆积或拒绝不会直接耗尽另一个下游的执行资源，并且可以按各自延迟和容量定参。

可以共用，前提是任务性质、SLO、下游容量和故障域接近，而且共享池有公平性、优先级或每下游并发限制，压测证明一个分支异常不会饿死其他分支。对于调用量很小的任务，共用能减少线程和维护成本。

代价是线程总数、栈内存和上下文切换增加，参数/监控/告警更多，池间容量无法自动借用，某个池排队时另一个池可能空闲。池越多并不等于隔离越好；应围绕故障域和容量边界划分，并设全局并发/连接预算，防止多个“合理”的独立池合计后压垮进程或下游。

### 69. 两个线程池的核心指标和参数如何设计？（三面第 15 题）

先收集每个 RPC 的到达率 `λ`、服务时间分布 `W`、超时、下游允许并发和实例数。用 Little 定律 `L ≈ λW` 估算正常在途请求数，再结合峰值和目标利用率得到初始并发上限；最终通过压测和灰度校准，而不是只套“CPU 核数乘 2”。阻塞 I/O 可以多于 CPU 核数，但上限往往由下游容量、连接池和本机资源决定。

`ThreadPoolExecutor` 需要明确 `corePoolSize`、`maximumPoolSize`、`keepAliveTime`、有界 `workQueue`、命名 `threadFactory` 和拒绝策略。若使用无界队列，`maximumPoolSize` 可能基本不起扩容作用，还会把过载变成长时间排队；队列容量应由允许排队时间和峰值流量推导，并与请求 Deadline 对齐。

监控至少包括 active/pool/最大线程数、队列长度与等待时间、提交/完成/拒绝数、任务执行 P95/P99、超时/取消、连接池占用、CPU、内存和上下文切换；还要关联各 RPC 的成功率与下游延迟。参数设计目标是过载时快速、可观测地降级，而不是无限吞入任务。

### 70. 为什么使用固定线程池？固定有什么好处？（三面第 16 题）

固定并发的价值是给阻塞式 RPC 一个明确上限，防止流量突增时无限创建线程、耗尽栈内存或把下游打穿；线程复用也减少频繁创建和销毁的开销，使容量更容易压测和监控。

但固定不是“永远用同一个数字”。线程数过小会排队并浪费下游能力，过大会增加上下文切换、连接竞争和下游过载。更重要的是，`Executors.newFixedThreadPool` 默认配无界队列，可能在下游变慢时无限积压，在线服务中通常应显式创建 `ThreadPoolExecutor`，使用有界队列和明确拒绝/降级策略。

如果流量波动很大或 RPC 有真正非阻塞异步接口，应比较弹性池、事件驱动或框架原生异步方案。选择固定线程池应基于可控并发和现有同步 SDK 的约束，而不是因为写起来简单。

### 71. 如果 16/32 不严谨，你会怎样重新定参？和 mentor 讨论过吗？（三面第 17 题）

我会先承认：“16/32 如果只是经验值就不够严谨，应把它当初始配置，不当结论。”随后按真实流量重新测量：分 RPC 统计峰值 QPS、任务执行时间和等待比例，估算在途并发；核对下游单实例/集群限额、客户端连接池、请求 Deadline 和本机线程总预算；设置有界队列与拒绝策略；再用阶梯压测寻找吞吐开始不再增长、P99 或错误率开始恶化的拐点。

灰度时观察队列等待、活跃线程、拒绝、上下文切换、CPU/内存、连接池和下游 SLO，并保留动态调整和回滚。若两个池分别是 16、32，要解释它们不同的延迟和容量，而不是只说一个更重要。

“是否和 mentor 讨论过”只能按事实回答：讨论过，就说明对方质疑了什么、最后如何决定；没有正式讨论，就说当时主要沿用已有配置，复盘后认为证据不足，并给出上述补测计划。不要虚构一次评审。

### 72. Tair 到底算 RPC，还是 Client 调用？（三面第 18 题）

从代码接口看，业务通常通过 Tair/Redis Client SDK 调用；从系统边界看，只要 Client 通过网络请求远端 Tair 服务，它就是一次远程调用，具备网络 RPC 的超时、连接池、重试、序列化和服务端故障风险。两种说法描述的是不同层次，不矛盾。

更准确的项目表述是“通过 Tair Client 发起远程请求”，并指出底层协议和 SDK 由实际组件决定。不要因为代码只写了一行 `client.get()` 就把它当本地函数，也不要为了项目包装把每次 Client 调用都说成自己设计了一套 RPC 框架。

如果使用的是同进程嵌入式缓存，那才不是远程调用；判断标准是进程/网络边界，而不是方法名中有没有 RPC。

### 73. 为什么能发现约 10ms 的优化点？还考虑过哪些方案？（三面第 19 题）

发现 10ms 级问题需要端到端 Trace 和足够稳定的分阶段指标，而不是肉眼看一次日志。先比较主链路 P50/P95/P99，再看 Span 时间轴：若两个独立 RPC 串行且各占稳定耗时，它们的重叠潜力才是候选优化点。还要通过多天或足够请求量的分布确认不是采样噪声，并在同环境对照实验中验证改造收益。

并行之前应比较其他方案：优化慢 RPC 自身及其 SQL/缓存；合并批量请求以减少网络往返；减少请求/响应字段；复用前置结果；为稳定数据增加缓存；调整调用顺序，让高淘汰率的便宜条件先执行；对于非关键分支改为异步或降级。并行只是当分支独立、都必须在本请求完成且下游有容量时的一个选择。

“约 10ms”要说明是平均、P95 还是关键路径理论差值，以及端到端是否真的减少同等数值。若监控分辨率和波动大于这个量级，就不应宣称发现了可靠的 10ms 收益。

### 74. 还有哪些复杂项目？讲一下本地缓存优化。（三面第 20 题）

可以这样组织：“另一个项目是 **[真实 POI/品类模块]**。原读路径每次都访问远端存储，数据又具有 **[读多写少/可版本化]** 特征，所以评估本地缓存。但难点不是调用 `Map.get`，而是容量、冷启动、更新一致性和回源保护。”

设计上先确定缓存对象和事实源，测量 Key 数量、对象大小、访问分布和更新频率；选择全量不可变快照或有界按需缓存；启动时按版本预热并通过就绪探针控制接流；更新时构建新版本后原子替换，失败保留旧版本；过期回源使用请求合并和并发限制；监控命中率、版本差、堆内存、GC、淘汰和远端 QPS。

验证时不仅比较平均延迟，还比较 P95/P99、冷启动期间的下游压力、内存水位和数据新鲜度。具体缓存库、更新通道、收益和个人职责都必须换成真实事实。

### 75. 品类数据很多，内存容量怎样估算？（三面第 21 题）

先算数据基数，再算单条真实驻留成本。粗略公式是：`总内存 ≈ 条目数 × (Key + Value + 对象头 + 引用 + Map/节点开销 + 对齐) / 目标装载因子 × 副本数 × 安全系数`。Java 中一个对象远不只字段字节，还可能有对象头、指针、HashMap table 和 Node；String/集合也有各自对象与数组，反序列化后的体积可能远大于压缩文件。

例如不要只用“100 万条 × 20 字节 = 20MB”得出结论。应使用 JOL 做单对象估算，用接近真实分布的数据加载后查看 heap dump、JFR 或内存 profiler，测稳定堆占用和 GC；同时考虑新旧快照原子切换时可能短暂共存两份、缓存库元数据、容器内存限制和其他业务对象。

容量规划还要留安全余量并设置硬上限。若全量快照超过预算，就压缩表示、拆掉冗余字段、使用 primitive/紧凑结构、按分片加载，或改成有界缓存加远端查询，而不是寄希望于 GC 自动解决容量问题。

### 76. 缓存的是 POI→品类映射还是品类基础数据？GC 正常是否足以证明可接受？（三面第 22 题）

第一问必须明确真实对象。`POI -> categoryId` 映射可能随 POI 数量达到百万/千万级，Key 多、容量大；品类基础数据通常只有有限品类树和属性，条目少但关系结构更复杂。两者的 Key、Value、更新频率、查询路径和一致性要求不同，不能笼统叫“品类缓存”。如果两者都缓存，要分别给数据量和更新机制。

GC 正常只说明某段观察期内没有明显垃圾回收异常，不足以证明方案可接受。还要看稳定堆/RSS、Old Gen 增长、分配速率、Young/Full GC 次数与 P99 暂停、缓存命中/淘汰、版本新鲜度、冷启动时长、更新峰值中新旧快照共存，以及容器是否接近 OOM Kill 阈值。

最终用压测和灰度证明：在目标数据规模和流量下，延迟收益达到目标，内存有安全余量，GC 与业务尾延迟在 SLO 内，更新失败可回退且数据不会无限陈旧。不能用“线上没 Full GC”代替容量评估。

### 77. 这些项目中哪些是你主动发现并完成的？（三面第 23 题）

把“发现”和“完成”拆开逐项回答。可以用表述：“项目 A 的问题由监控/mentor 提出，我负责分析和实现 **[部分]**；项目 B 是我在 **[Trace/日志/代码评审]** 中主动发现，先用 **[证据]** 验证，再提出 **[方案]**，经过 **[评审者]** 确认后完成 **[编码、测试或灰度]**；项目 C 我只是参与联调。”

主动性不等于绕过团队独自拍板。高质量的主动发现包含量化证据、备选方案、风险评估、推动评审和验证闭环。准备时为每个项目列出问题来源、提出者、设计者、编码者、上线者和结果负责人，面试中就不会把团队成果说成个人成果，也不会把自己的工作说得过轻。

如果没有项目是从发现到上线都独立完成，也可以说自己主动完成了某个局部闭环，例如补监控后发现长尾、提出索引调整并完成验证。真实而具体比“全部都是我主动做的”更有说服力。

### 78. 你认为自己还需要补强哪些方面？（三面第 24 题）

可以回答一个已经在行动、又不构成岗位硬伤的方向：“我需要继续补强复杂系统的定量分析和线上容量经验。以前有时能提出可行方案，但在线程池定参、Token 指标或缓存容量上，证据链还不够完整，容易先给经验数字。现在我会先定义 SLO 和统计口径，再用 Trace、压测、执行计划或 heap 数据验证，并记录替代方案和回滚条件。”

再补一个技术方向即可，例如 Go 运行时/JVM 调优或分布式一致性，但要说明具体行动：阅读源码和官方资料、做实验、复盘实际问题、输出可验证笔记。不要回答“过于追求完美”一类伪缺点，也不要说岗位核心能力完全不会。

这个问题最好呼应本场追问：承认 16/32、21% 等数字需要更严谨的测量，同时展示已经掌握改进方法，会比为原答案强行辩解更成熟。

### 79. 最近在学习什么？这些报告主要讲原理还是用法？（三面第 25 题）

建议选一项最近真实阅读的技术报告，按“问题、核心原理、工程启发、亲自验证”回答。例如：“我最近在学习长上下文与 Agent 评测。报告不只是介绍 API 用法，核心讨论的是注意力/上下文限制、压缩与检索的质量成本权衡，以及怎样设计可复现评测。我把其中的思路转成了固定任务集、成对回放和失败分类，并用代码实验观察 Token、质量和延迟，而不是只记结论。”

如果读的是框架文档，则可以说用法占比更高，并补充自己如何继续追到底层状态模型、失败语义和性能边界。若读的是论文，要能讲清问题设定、对照基线、指标、主要结论和局限，不能只复述摘要。

最后把它与岗位连接起来：“我希望学习最终能落到服务端工程判断上，例如如何设置并发上限、怎样让任务可恢复、怎样证明优化没有牺牲质量。”具体报告名称、作者和实验只能使用确实读过且能接受追问的内容。
