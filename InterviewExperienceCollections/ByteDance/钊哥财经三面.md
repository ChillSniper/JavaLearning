### 9. 这个项目中遇到的难点是什么

我认为最核心的难点不是把接口写出来，而是在并发领取场景下同时保证库存不超卖和一人一单。

普通的“先查库存、再扣库存”是两个步骤，并发时多个请求可能同时看到库存充足；“先查订单、再创建订单”也可能让同一用户产生重复订单。我的处理思路是把活动校验、库存判断、用户是否领取以及 Redis 库存扣减放进同一个 Lua 脚本原子执行，先快速拒绝无资格请求。数据库侧再通过 `(user_id, voucher_id)` 唯一约束防止重复订单，并使用带库存条件的更新，例如 `stock > 0`，作为最终兜底。

第二个难点是 Redis 数据结构的容量边界。如果把某张优惠券的所有用户都放进一个 Set，数据量很大时会形成 Big Key，带来内存、网络传输、删除阻塞和主从同步压力。可以按照用户 ID 哈希分桶、设置合理过期时间、避免整 Key 扫描或一次性删除，并把 MySQL 唯一约束保留为最终准确判断。Bloom Filter 可以用于快速过滤，但因为存在误判，不能单独决定用户一定领过券。

第三个难点是缓存与数据库的一致性。普通门店信息可以采用 Cache Aside：读取时先查缓存，未命中再查数据库并回填；更新时先提交数据库，再删除缓存，并对删除失败做重试或补偿。它通常提供最终一致性，不应说成绝对强一致。

### 10. Redis Bitmap 是什么物理结构

从逻辑上看，Bitmap 是一个连续的位数组，每一位只有 `0` 和 `1`。Redis 没有单独新增一种 Bitmap 对象类型，而是把它建立在 String 的字节序列之上，通过 `SETBIT`、`GETBIT`、`BITCOUNT` 等命令按位操作。第 `offset` 位位于第 `offset / 8` 个字节中，再通过位运算定位到字节内的具体位置。

它最大的优点是节省空间：表示 `N` 个二值状态理论上只需要约 `N / 8` 字节，适合签到、活跃状态、在线标记等场景。例如用户 ID 能映射为连续偏移量时，可以用一位表示用户当天是否签到。

边界是：如果用户 ID 很稀疏，直接把一个很大的 ID 当偏移量会让字符串扩展到很大，空间反而浪费；Bitmap 也只适合布尔状态，不能直接保存复杂信息。设计前要考虑 ID 映射、时间分片和 Key 的大小。

### 11. Bloom Filter 是什么数据结构

Bloom Filter 由一个位数组和 `k` 个哈希函数组成。插入元素时，对元素计算 `k` 个哈希位置，并把这些位置都设为 `1`；查询时重新计算这些位置，只要其中一位是 `0`，就能确定元素一定不存在；如果全部为 `1`，只能说明元素可能存在。

因此，标准 Bloom Filter 的特点是：可能发生假阳性，也就是把不存在误判为可能存在；正常只添加、不删除时不会发生假阴性。它的空间效率很高，常用于缓存穿透防护、黑名单预筛选或大集合存在性判断。缓存场景中，如果过滤器判断一定不存在，可以直接返回；如果判断可能存在，仍然要查询缓存或数据库确认。

标准 Bloom Filter 不能安全地直接清除某一位，因为这可能影响其他元素。需要删除能力时可以使用 Counting Bloom Filter，或者通过分代、重建等方式维护。误判率取决于位数组大小、元素数量和哈希函数个数，数据规模超出设计容量后误判率会显著上升。

### 12. 怎样理解操作系统里的 CPU 调度

CPU 调度的核心是在多个可运行任务之间决定“接下来让谁使用 CPU、运行多久、什么时候被抢占”。任务会在运行、就绪和阻塞等状态之间切换；当任务等待 I/O、时间片耗尽、更高优先级任务到来或任务退出时，调度器可能重新选择任务并发生上下文切换。

调度没有对所有场景都最优的单一算法，而是在多个目标之间取舍：交互系统关注响应时间和公平性，批处理关注吞吐量，实时系统关注截止时间，同时还要控制饥饿、上下文切换开销和多核负载均衡。

短作业优先可以降低平均等待时间，但实际系统通常不知道任务未来还要运行多久，只能根据历史运行特征估计；纯优先级调度可能让低优先级任务长期得不到执行，因此常配合动态优先级或老化机制。回答调度问题时，要同时说明策略目标和它可能牺牲的指标。

### 13. 实现短任务或优先级调度，可以使用什么数据结构

如果调度依据是“预计剩余执行时间最短”，可以使用以剩余时间为 Key 的最小堆。插入新任务和任务完成后的调整通常是 `O(log N)`，查看当前最短任务是 `O(1)`；如果允许抢占，新任务到来时还要与当前任务的剩余时间比较。

如果优先级取值范围较小且固定，例如 `0～139`，可以为每个优先级维护一个 FIFO 队列，再用位图标记哪些优先级非空。这样既能快速找到最高优先级，也能保证同一优先级内部按到达顺序调度。若优先级范围很大或动态变化，可以使用 `TreeMap<Priority, Queue<Task>>`；Key 有序，Value 保存同一优先级的任务队列。

需要强调的是，数据结构只是实现工具。还要补充时间片、抢占时机、同优先级公平性、优先级老化和并发访问保护，否则只实现了“选最小值”，还不算完整调度器。

### 14. 哈希加数组找到最小优先级的复杂度是多少，TreeMap 呢

如果“哈希表 + 数组”的做法需要从数组头开始扫描，设优先级范围为 `P`，找到第一个非空优先级的复杂度是 `O(P)`；当 `P` 与任务数量同阶时，也可以近似看作 `O(N)`。哈希表只能让“根据已知 Key 找任务”接近 `O(1)`，它本身不维护 Key 的大小顺序，所以不能直接高效找到最小优先级。

使用 `TreeMap` 时，底层是红黑树。插入、删除以及按 Key 定位的复杂度都是 `O(log P)`；获取最小 Key 需要走到最左节点，通常也按 `O(log P)` 分析。同一个优先级下再挂一个队列，可以让该优先级任务入队和出队保持 `O(1)`。

如果优先级范围很小且固定，数组加位图可能比 TreeMap 更合适；如果优先级稀疏且动态，TreeMap 更通用。复杂度比较必须把 `P` 是固定常数还是随输入增长说清楚。

### 15. Linux 操作系统怎样实现调度

Linux 不是用一种算法调度所有任务，而是通过不同的调度类处理不同策略。每个 CPU 都维护自己的运行队列，调度器从本 CPU 的可运行任务中选择下一个任务，同时还要通过负载均衡把任务分配到不同 CPU。

对于普通任务，经典 CFS 会根据任务的虚拟运行时间 `vruntime` 衡量它已经获得的 CPU 份额，并使用红黑树组织可运行实体，倾向选择 `vruntime` 较小的任务，从而逼近公平分配。较新的 Linux 内核正在公平调度类中采用 EEVDF 思路：先判断任务是否“有资格”运行，再优先选择虚拟截止时间更早的任务，以改善延迟和公平性。因此面试时最好说清楚内核版本，不要把“CFS 永远只取红黑树最左节点”当成所有现代 Linux 的唯一答案。

实时任务还有 `SCHED_FIFO`、`SCHED_RR` 等策略，截止时间任务有单独的 deadline 调度类。更高调度类中的可运行任务通常会优先于普通任务。完整实现还涉及优先级、抢占、CPU 亲和性、NUMA、负载均衡和中断等问题；面试中回答到“调度类 + 每 CPU 运行队列 + 普通任务公平调度 + 实时策略”已经形成了完整主线。

### 16. 排序算法的时间复杂度下界是什么

要先限定模型：对于只允许通过元素之间的比较来确定顺序的通用排序，最坏情况下的时间复杂度下界是 `Ω(N log N)`。

证明可以使用决策树。`N` 个互不相同的元素有 `N!` 种排列，比较一次只有两种结果，因此一棵能够区分所有排列的二叉决策树至少要有 `N!` 个叶子，树高至少为 `log2(N!)`。根据斯特林公式，`log(N!) = Θ(N log N)`，所以任何比较排序最坏情况下都至少需要这个数量级的比较。

归并排序和堆排序最坏时间复杂度为 `O(N log N)`，因此达到了比较排序的渐进下界。快速排序平均是 `O(N log N)`，但普通实现最坏可以退化到 `O(N²)`。这个下界不适用于利用 Key 数值范围或位结构的非比较排序。

### 17. 有没有比 O(N log N) 更快的排序，桶排序最快是否能到 O(N)

有，但必须利用输入的额外约束，而不是解决完全通用的比较排序问题。

- 计数排序：Key 是范围为 `0～K` 的整数时，时间复杂度为 `O(N + K)`，空间复杂度为 `O(K)`。
- 桶排序：把数据分到多个桶内，再分别排序。数据分布较均匀时平均可以接近 `O(N)`，但分桶不均时可能退化。
- 基数排序：按个位、十位或字节逐轮进行稳定排序，复杂度可写成 `O(D(N + K))`，其中 `D` 是位数，`K` 是每一位的取值范围。

所以“最快能达到 `O(N)`”要带条件：当 Key 范围、位数或分布满足要求，而且这些参数相对 `N` 可以视为常量时，非比较排序能够达到线性时间。它们通常需要额外空间，也不适合任意对象和任意比较规则，因此没有推翻比较排序的 `Ω(N log N)` 下界。

### 18. 数据库索引的物理结构是什么

索引本质上是额外维护的一份有序数据结构，用空间和写入成本换取查询效率。以 MySQL InnoDB 的普通索引为例，主流物理结构是按页组织的 B+ 树。一个页中保存多条有序记录或目录项，页之间通过页号关联；数据库每次通常以页为单位从磁盘读取数据，并把热点页缓存在 Buffer Pool 中。

InnoDB 的主键索引是聚簇索引，叶子节点保存整行记录；二级索引的叶子节点通常保存索引列和主键值。通过二级索引查询其他列时，可能先找到主键，再到聚簇索引查询整行，这就是回表。若查询列都在二级索引中，则可能使用覆盖索引避免回表。

数据库也可能有哈希、全文或空间索引，所以不能把“所有数据库索引”都等同于 B+ 树。回答时最好限定为“InnoDB 常规主键和二级索引”。

### 19. B+ 树是什么结构

B+ 树是一棵多路平衡搜索树。内部节点主要保存用于导航的 Key 和子节点指针，完整数据集中存放在叶子节点；所有叶子节点位于同一层，因此从根到任意叶子的路径长度相同。叶子节点通常还按照 Key 顺序通过链表相连，便于范围扫描和顺序遍历。

它适合数据库的原因是一个磁盘页可以容纳很多 Key 和指针，树的分支因子很大，因此树高通常很低。查询时先在根页确定子区间，再逐层下降到叶子页；范围查询只需定位起点，随后沿叶子节点顺序读取。

与 B 树相比，B+ 树把完整数据统一放在叶子层，内部节点能容纳更多目录项，范围查询也更自然。节点分裂、合并和旋转等操作用于在插入删除后维持平衡和页利用率。

### 20. SELECT 在 B+ 树中查找一条数据的复杂度是多少

按算法模型分析，单点查找的复杂度是 `O(log_M N)`，其中 `M` 是每个节点大致能容纳的分支数，`N` 是记录数量。因为数据库页较大、分支因子通常很高，所以实际树高往往只有少数几层。页内还会通过槽目录等结构定位记录，不能简单理解为从头到尾线性扫描整页。

从工程角度，更重要的是访问了多少个不在内存中的页。根页和上层索引页通常会缓存在 Buffer Pool 中，因此一次查询不一定真的产生与树高相同的磁盘 I/O。通过二级索引查询非覆盖列时，还可能多一次聚簇索引查找；范围查询的复杂度则可以表示为 `O(log_M N + K)`，`K` 是返回记录数。

另外，只有查询条件能够有效使用索引时才是这条路径。如果发生全表扫描、隐式类型转换或查询条件不满足索引使用规则，复杂度和 I/O 模式都会不同。

### 21. 编程题 1：螺旋打印二维数组

思路是维护上、下、左、右四个边界。每一轮依次遍历上边、右边、下边和左边，完成一条边后立刻收缩对应边界。遍历下边和左边前必须再次判断边界是否仍然有效，否则单行或单列矩阵会重复加入元素。

```java
import java.util.ArrayList;
import java.util.List;

class Solution {
    public List<Integer> spiralOrder(int[][] matrix) {
        List<Integer> result = new ArrayList<>();
        if (matrix == null || matrix.length == 0 || matrix[0].length == 0) {
            return result;
        }

        int top = 0;
        int bottom = matrix.length - 1;
        int left = 0;
        int right = matrix[0].length - 1;

        while (top <= bottom && left <= right) {
            for (int col = left; col <= right; col++) {
                result.add(matrix[top][col]);
            }
            top++;

            for (int row = top; row <= bottom; row++) {
                result.add(matrix[row][right]);
            }
            right--;

            if (top <= bottom) {
                for (int col = right; col >= left; col--) {
                    result.add(matrix[bottom][col]);
                }
                bottom--;
            }

            if (left <= right) {
                for (int row = bottom; row >= top; row--) {
                    result.add(matrix[row][left]);
                }
                left++;
            }
        }

        return result;
    }
}
```

每个元素只访问一次，时间复杂度为 `O(MN)`；结果之外只维护四个边界，额外空间复杂度为 `O(1)`。如果把返回结果也计算在空间内，则是 `O(MN)`。常见边界包括空矩阵、单行、单列、正方形和长方形矩阵。

### 22. 编程题 2：版本号排序

先按 `.` 拆分版本号，再从左到右比较每一段的数值。较短版本缺失的段按 `0` 处理，因此 `1`、`1.0` 和 `1.0.0` 在数值语义上相等。不能直接比较字符串，因为 `"1.10"` 会被错误地排在 `"1.2"` 前面；也不建议直接使用 `Integer.parseInt`，因为版本段可能超过 `int` 范围。

下面通过去除前导零后比较有效长度和字典序，避免整数溢出：

```java
import java.util.Arrays;

class Solution {
    public String[] sortVersions(String[] versions) {
        String[] result = versions.clone();
        Arrays.sort(result, this::compareVersion);
        return result;
    }

    private int compareVersion(String first, String second) {
        String[] a = first.split("\\.");
        String[] b = second.split("\\.");
        int length = Math.max(a.length, b.length);

        for (int i = 0; i < length; i++) {
            String left = i < a.length ? normalize(a[i]) : "0";
            String right = i < b.length ? normalize(b[i]) : "0";

            if (left.length() != right.length()) {
                return Integer.compare(left.length(), right.length());
            }

            int comparison = left.compareTo(right);
            if (comparison != 0) {
                return comparison;
            }
        }
        return 0;
    }

    private String normalize(String part) {
        int index = 0;
        while (index < part.length() - 1 && part.charAt(index) == '0') {
            index++;
        }
        return part.substring(index);
    }
}
```

设一共有 `N` 个版本号，每个版本号平均长度为 `L`。排序需要 `O(N log N)` 次比较，每次比较最坏处理 `O(L)` 个字符，因此总体时间复杂度约为 `O(NL log N)`；拆分字符串和结果副本需要额外空间。

这段代码假设输入是只包含非负整数和点的普通版本号。若题目采用完整 Semantic Versioning，例如包含 `1.0.0-alpha`、构建信息或特殊优先级规则，就必须按 SemVer 规则单独解析，不能直接套用本比较器。
