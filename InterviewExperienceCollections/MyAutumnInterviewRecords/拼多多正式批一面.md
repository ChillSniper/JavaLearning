### 5. 请展开介绍一下字节风控项目，你主要负责哪些内容

我所在的团队服务于国际支付业务，业务背景涉及海外直播、电商和广告等场景。支付风控处理后，部分用户或商家会提交申诉、客诉，这些案件进入 CMS 运营审核平台。原来的处理方式主要依靠人工审核，我参与建设的是其中一条自动化审核链路：根据案件信息匹配配置的规则，调用规则关联的业务能力，再根据执行结果推动案件流转。上游 Agent 可以提供识别结果或指标，作为规则判断的输入。我主要负责场景接入、规则编排和能力调用，将这些已有能力连接成能够处理案件的业务流程。

### 6. Agent 决策链路与传统规则引擎有什么区别？项目中怎样使用 Agent

规则引擎根据明确配置的条件进行判断，例如案件类型、风险标签和识别结果是否满足某项条件，行为相对确定，也方便记录命中原因。Agent 通常会利用模型理解材料，并可能结合工具完成分析，适合处理文本、图片等复杂输入；具体能否自主规划、反复调用工具，需要结合实现判断。在这次项目中，上游 Agent 提供参考结果，下游审核链路根据规则决定如何调用业务能力、如何流转案件。可以明确介绍结果如何接入、如何参与判断；上游 Agent 内部的模型训练和决策实现，需要由实际参与的人员说明。

### 7. 这条审核链路的主要决策仍然依赖规则引擎和业务规则吗

是的，录音确认主要决策由已有规则引擎和配置规则完成。案件信息、上游识别结果等组成规则输入，规则命中后触发已经注册的业务能力，未满足自动审核条件的案件进入人工处理流程。这里需要说明规则条件、能力执行和最终审核结果之间的对应关系，例如某个识别结果只用于筛选案件，还是直接参与某项审核条件。

### 8. 项目中的 TCC 是什么？属于内部配置平台吗

这里的 TCC 指公司内部使用的配置平台，用来管理审核链路读取的规则和相关配置。业务服务取得配置后，由已有表达式解析或规则执行组件处理条件，再调用对应的业务能力。介绍时可以说明自己使用了哪些配置项、如何组织规则、配置如何被业务服务读取。平台内部实现、具体客户端机制等内容，录音没有展开。

### 9. 简历中提到对 Agent 决策链路做了优化，你具体做了哪些工作

我负责的是将上游 Agent 输出的结果或指标接入客诉审核流程，把它包装为业务链路能够使用的能力，并让规则能够引用这些结果，随后调用对应的下游处理能力。个人贡献可以围绕输入输出字段、能力注册、调用位置和案件流转方式展开。录音能够确认的是结果接入与规则编排，没有提供模型质量提升或 Agent 自主决策改进的证据，因此具体收益需要引用实际监控或评估结果。

### 10. 上游 Agent 的结果是否可以理解为规则判断过程中使用的一项能力

可以这样理解，但实现时还要明确“能力”和“规则条件”的区别。能力负责获取或计算结果，例如返回识别标签、审核建议；规则条件读取这些结果，决定当前案件是否符合某项处理要求；规则命中后的动作负责调用业务接口或变更流转状态。录音确认上游结果以能力的形式接入，具体是提前计算后传入，还是在规则执行过程中调用，转写没有给出完整执行顺序。

### 11. 运营平台迭代过程中，挑战最大的需求是什么

投入最多的是风控客诉自动化审核链路，因为需要把案件入口、配置规则、已有规则引擎、上游结果和下游业务能力连接起来。介绍挑战时，可以围绕一类案件说明：有哪些输入，哪些条件允许自动处理，命中后执行什么动作，哪些情况需要人工处理。技术设计还需要考虑重复案件、调用超时、配置变更和处理记录，保证一次业务处理能够被追踪。录音没有提供某次具体故障或性能优化数据，因此这部分更适合通过本人能够核实的接口与流程说明工作深度。

### 12. 引入自动化审核链路之前，风控客诉案件怎样审核

案件进入 CMS 后，主要由海外审核人员或外包审核人员进行人工审核。自动化需求的目标，是把规则明确、数据完整且适合自动判断的一部分案件交给程序处理，其余案件继续由人工处理。评估业务效果时，需要同时观察自动处理覆盖率、人工处理量和审核质量，不能只看程序处理了多少案件。

### 13. 审核规则由谁提供？产品、运营和开发怎样协作

录音中的流程是运营提出审核规则和业务要求，产品整理需求，再交给研发实现。研发需要把自然语言要求转换为明确的输入字段、条件表达式、规则优先级和执行动作，并明确字段缺失、规则冲突以及多个规则同时命中时的处理方式。规则发布前，应由业务人员确认代表性案例的预期结果，研发验证实际执行结果和配置生效情况；规则上线后的效果也需要结合运营复核结果持续检查。

### 14. 这套规则配置与自动化审核系统的整体架构怎样设计

录音能够还原的流程是：案件进入审核服务，服务读取 TCC 中的规则配置，已有表达式解析或规则执行组件对案件信息进行判断，命中后调用代码中注册的业务能力，完成案件后续流转；没有命中自动处理规则的案件进入人工审核。上游 Agent 的结果作为输入能力参与这条流程。转写中的表达式组件名称识别不清，保留为“已有表达式解析组件”。如果展开设计，配置中需要明确规则标识、适用案件、条件和动作；能力注册需要明确名称、参数与返回结果；执行记录需要保留案件标识、规则版本、命中情况和调用结果，以便复核具体案件为什么得到某个结论。

### 15. 规则引擎是否已经存在？你负责的具体建设范围是什么

规则引擎已经存在。我负责的是基于已有引擎建设客诉场景的业务流程，包括组织规则配置、注册和接入业务能力、获取规则需要的数据，以及按照执行结果推进案件处理。描述“从零建设”时，应把对象明确为这条具体业务链路，并说明复用了哪些平台组件。这样可以继续回答每个接口由谁提供、自己编写了哪些业务逻辑、哪些执行边界经过验证。

### 16. 怎样判断自动化审核的准确率

审核准确率需要将自动审核结论与经过复核的标准结论进行比较。可以从自动处理的案件中抽样，由有权限的审核人员独立复核，并对有争议的案件进行确认，再计算一致比例。如果重点关注某类风险，还应分别统计该类判断的 precision 和 recall：precision 关注被判为该类的案件中有多少判断正确，recall 关注实际属于该类的案件有多少被识别出来。同时按地区、案件类型和规则版本观察结果，才能知道问题出现在哪些范围。规则命中率表示满足条件的案件占比，自动处理覆盖率表示自动处理的案件占比，这些指标需要与质量指标分别记录。录音确认做了链路监控和命中统计；具体人工复核样本、准确率数值和标注标准没有提供。

### 17. 简历后面的几项工作是否主要属于技术需求

录音中确认后面的部分工作主要属于技术需求，例如处罚查询相关的性能和稳定性工作，以及银行卡能力接入、地区数据隔离相关工作。介绍每项需求时，可以说明业务使用者遇到什么问题、自己修改了哪些接口或数据处理逻辑、怎样检查结果。需求属于技术类或业务类只是背景，能够说明具体输入、处理过程和结果才有助于进一步交流。

### 18. 处罚记录原来存储在 MySQL 中吗

录音确认处罚记录原来保存在 MySQL 中，后来将一部分查询所需数据同步到 Elasticsearch。按当时的描述，MySQL 继续保存业务记录并提供增量数据，ES 保存用于检索的字段和选定时间范围内的数据。因此可以表达为“为处罚查询增加 ES 检索能力”。要进一步说明主数据职责，需要明确业务写入仍然进入哪个系统、ES 数据如何生成、历史数据在哪里查询，以及查询结果是否允许一定的同步延迟。

### 19. 引入 ES 具体要解决哪些查询问题

录音提到处罚相关的两张表字段较多，查询涉及处罚记录列表，以及部分关联查询。技术上应结合实际筛选条件和执行计划定位瓶颈，例如扫描记录过多、组合筛选条件难以得到合适索引支持、排序或分页耗时较长。ES 适合围绕查询需求构建检索文档，把经常一起展示和过滤的信息组织在一起；涉及多张关系表时，需要明确文档生成方式和更新方式。面试时最好能提供一条实际查询的条件、返回字段和优化前后的测量结果，录音中没有保留具体 SQL 和这些数值。

### 20. ES 与 MySQL 的数据一致性怎样保证

现场介绍的方案是通过唯一业务标识关联记录，定期将 MySQL 的增量数据同步到 ES，并在部分查询没有找到记录时查询 MySQL。要形成完整的最终一致性方案，同步任务需要记录可靠的处理进度，成功写入后再推进进度，失败记录进入可追踪的重试流程，并通过业务标识实现重复写入的幂等性，还需要定期核对缺失记录。按 ID 查询不到记录时查询 MySQL，可以补充该条记录；列表查询已经返回部分结果时，仍可能遗漏尚未同步的数据，因此必须明确列表允许的数据延迟和完整性要求。如果允许历史更新，还需要同步更新和删除，并使用版本控制阻止旧数据覆盖新数据。ES 写入完成后，搜索可见性还受 refresh 影响，需要将这一段延迟纳入监控。[Elasticsearch 搜索可见性说明](https://www.elastic.co/docs/manage-data/data-store/near-real-time-search)

### 38. 给定整数范围内的若干已占用区间，怎样求最长连续空闲区间

【按对话推断】根据录音，可以还原为：在整数范围 `[0,99]` 内给定若干已占用闭区间，求没有被占用的最长连续整数区间，输出其左右端点。已占用区间可能重叠，需要合并。录音没有给出完整原始输入、并列答案规则和完全占用时的输出要求。这里的参考实现约定：输入端点均在 `[0,99]` 内，长度相同选择起点较小的区间，完全占用时返回 `std::nullopt`，空输入返回 `[0,99]`。

可以按左端点升序排序，合并重叠或相邻的已占用区间，然后依次检查它们之前、之间和之后的空闲区间。相邻的两个整数区间，例如 `[10,20]` 和 `[21,25]`，中间没有空闲整数，可以合并。录音提到合并后的一个示例包含 `[10,25]` 和 `[70,72]`，对应空闲区间为 `[0,9]`、`[26,69]`、`[73,99]`，最长答案是 `[26,69]`。

```cpp
#include <algorithm>
#include <optional>
#include <stdexcept>
#include <vector>

struct Interval {
    int left;
    int right;
};

std::optional<Interval> longestFreeInterval(std::vector<Interval> occupied) {
    constexpr int lower = 0;
    constexpr int upper = 99;

    for (const auto& interval : occupied) {
        if (interval.left < lower || interval.right > upper ||
            interval.left > interval.right) {
            throw std::invalid_argument("invalid occupied interval");
        }
    }

    std::sort(occupied.begin(), occupied.end(),
              [](const Interval& a, const Interval& b) {
                  if (a.left != b.left) {
                      return a.left < b.left;
                  }
                  return a.right < b.right;
              });

    std::vector<Interval> merged;
    for (const auto& interval : occupied) {
        if (merged.empty() || interval.left > merged.back().right + 1) {
            merged.push_back(interval);
        } else {
            merged.back().right = std::max(merged.back().right, interval.right);
        }
    }

    std::optional<Interval> answer;
    int bestLength = 0;
    auto consider = [&](int left, int right) {
        if (left > right) {
            return;
        }
        int length = right - left + 1;
        if (length > bestLength) {
            bestLength = length;
            answer = Interval{left, right};
        }
    };

    int next = lower;
    for (const auto& interval : merged) {
        consider(next, interval.left - 1);
        next = interval.right + 1;
    }
    consider(next, upper);
    return answer;
}
```

代码适用 C++17。`longestFreeInterval({{10,25},{70,72}})` 返回的结果中，`left` 为 `26`，`right` 为 `69`。提交到具体评测平台时，输入输出部分需要按原始题面接入。

### 39. 请解释区间题的实现思路和时间复杂度

【按对话推断】这部分根据候选人讲解算法的内容整理。排序以后，按照左端点顺序处理每个区间：如果当前区间与最后一个合并结果重叠或相邻，就更新其右端点；否则追加一个新区间。合并完成后，维护下一个可能空闲的整数 `next`，当前已占用区间的左端点为 `left` 时，候选空闲范围是 `[next,left-1]`，处理后将 `next` 更新为当前右端点加一。最后还要检查 `[next,99]`。设原始区间数量为 `n`，排序需要 `O(n log n)`，合并和寻找答案需要 `O(n)`，总时间复杂度是 `O(n log n)`；参考实现使用排序输入副本和合并结果，额外空间为 `O(n)`。

### 40. 已占用区间与空闲区间的端点应该怎样处理

这里按整数闭区间处理，所以 `[left,right]` 包含 `right-left+1` 个整数。两个合并后的已占用区间分别为 `[a,b]` 和 `[c,d]` 时，中间空闲区间是 `[b+1,c-1]`，长度为 `c-b-1`，只有长度大于零才存在答案。例如 `[10,25]` 之前的空闲区间是 `[0,9]`，其后直到 `[70,72]` 之前的空闲区间是 `[26,69]`。首部从 `0` 开始，尾部到 `99` 结束；没有已占用区间时，两端共同形成 `[0,99]`。参考代码通过单独检查尾部处理边界，不需要额外插入占用端点。

### 45. 将 50 个红球和 50 个蓝球放入两个盒子，怎样使抽到红球的概率最大

【按对话推断】根据后续计算和面试官提示，还原条件为：50 个红球、50 个蓝球必须全部分配到两个非空盒子；两个盒子的球数可以不同；首先等概率选择一个盒子，再从选中的盒子中等概率取出一个球。最优分配是一个盒子放 1 个红球，另一个盒子放剩余 49 个红球和 50 个蓝球。这样选择第一个盒子时必然得到红球，选择第二个盒子时得到红球的概率为 `49/99`，总概率是 `1/2 + (1/2) × (49/99) = 74/99`，约为 `74.7475%`。

### 46. 两个盒子平均分配红球和蓝球时，抽到红球的概率是多少

每个盒子都放 25 个红球和 25 个蓝球时，选择任意一个盒子后，抽到红球的概率都是 `25/50=1/2`。使用全概率公式，总概率为 `(1/2) × (1/2) + (1/2) × (1/2) = 1/2`。这可以作为比较其他分配方式的基础结果。

### 47. 两个盒子的球数可以不同，这个条件怎样影响计算

选中每个盒子的概率固定为 `1/2`，所以两个盒子中红球比例对最终概率的影响相同，球数较少的盒子也占一半的选择机会。若第一个盒子有 `r` 个红球、`b` 个蓝球，总概率为 `(1/2) × r/(r+b) + (1/2) × (50-r)/(100-r-b)`，其中两个分母都需要大于零。这样就可以用很少的红球让一个盒子的红球比例达到 1，同时把更多红球保留给另一个盒子。

### 48. 如果一个盒子只放红球，应该放几个？为什么

应该放 1 个红球。设这个盒子放 `k` 个红球，`1≤k≤50`，选中它后抽到红球的概率始终为 1；另一个盒子有 `50-k` 个红球和 50 个蓝球，红球比例为 `(50-k)/(100-k)`。随着 `k` 增加，这个比例下降，因此在保持第一个盒子非空的条件下，取最小的 `k=1` 可以使第二个盒子的红球比例最大，也使总概率最大。

### 49. 最优分配下的准确概率是多少？怎样证明无法继续提高

准确概率为 `(1/2) × 1 + (1/2) × (49/99) = 148/198 = 74/99`。证明全局最优时，可以把球数较少的盒子称为第一个盒子，设它有 `n` 个球，其中 `r` 个红球，那么 `1≤n≤50`，且 `0≤r≤n`。抽到红球的概率为 `P=(1/2) × [r/n + (50-r)/(100-n)]`。固定 `n` 时，`r` 的系数为 `(1/2) × [1/n-1/(100-n)]`，因为 `n≤50`，这个系数大于或等于零，所以令 `r=n`，即较小盒子全部放红球，可以取得该 `n` 下的最大值。此时 `P=1/2+(50-n)/(2×(100-n))=1-25/(100-n)`，随着 `n` 增加而减小，因此 `n=1` 最优，对应概率 `74/99`。这个证明覆盖了所有非空盒子的分配方式。
