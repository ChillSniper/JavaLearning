### 1. HashMap 是线程安全的吗？

**面试回答：**

HashMap 本身没有提供并发读写所需的同步机制。在多个线程共享同一个 HashMap，并且有线程修改它时，可能出现数据覆盖、读取结果不可靠、内部结构被并发修改等问题。

例如，两个线程向同一个空桶插入不同的 key。它们可能同时读取到这个桶为空，分别创建节点，然后把各自的节点写入这个位置。后一次写入可能覆盖前一次写入，导致其中一个 key 丢失。这个例子可以说明，问题发生在容器内部的插入过程，两个 key 即使不同，也可能产生竞争。

在多线程共享的场景下，我通常会使用 ConcurrentHashMap。如果整个业务操作涉及多个步骤，例如判断库存后再扣减库存，还需要保证这些步骤整体的原子性。对于初始化完成后保持只读的 HashMap，只要已经安全地发布给其他线程，就可以并发读取。

**追问时可以补充：**

- HashMap 的 `put` 包含计算位置、读取桶、插入或更新节点、更新元素数量，以及可能发生的扩容；这些步骤之间缺少并发协调。
- `volatile` 修饰一个 HashMap 引用，只能帮助发布这个引用，无法给 HashMap 内部的读写操作增加互斥保护。
- 使用 `Collections.synchronizedMap` 时，单次方法调用有同步保护；遍历及需要整体原子性的组合操作，还需要按它的使用要求进行同步。

### 2. 为什么 ConcurrentHashMap 是线程安全的？举个例子说明

**面试回答：**

以 JDK 8 的实现为例，ConcurrentHashMap 通过 CAS、`synchronized` 和具有可见性保证的读写操作，协调多个线程对内部结构的访问。

向空桶插入节点时，它使用 CAS，只有在这个位置仍然为空的情况下，才会写入新节点。如果两个线程同时向同一个空桶插入，只有一个线程能够完成这次 CAS；另一个线程会重新检查桶的状态，再继续插入。因此，两个不同 key 的节点可以得到正确保存。

对于已经存在节点的桶，插入、删除和更新通常会对桶的头节点使用 `synchronized`，取得保护后还会检查桶的头节点是否发生变化。这样可以协调同一个桶内的结构修改，不同桶的更新也能够并发进行。节点的 `val`、`next` 等字段使用 `volatile`，桶位置的读取和更新也具有相应的内存可见性保证，使 `get` 通常能够直接读取节点。

业务例子可以用并发计数说明：假设当前计数为 10，两个线程分别执行 `get`，都读取到 10，再分别执行 `put` 写入 11，最终结果就可能是 11。因此，我会使用 `map.merge(key, 1, Integer::sum)`，让这个 key 的读取、计算和更新作为一次原子操作完成；在没有其他修改的情况下，两次递增后的结果就是 12。`merge` 的原子性由 ConcurrentHashMap 提供。[JDK 8 ConcurrentHashMap 文档](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ConcurrentHashMap.html)

**追问时可以补充：**

- JDK 7 的主要实现方式是 `Segment` 分段锁；解释 JDK 8 时，需要说明 CAS 和桶级别的同步。
- 扩容时可以由多个线程协助迁移桶，并通过迁移标记引导其他线程访问新数组。
- `putIfAbsent`、`compute`、`merge` 可以支持相应的原子更新；调用多个方法形成的业务流程，需要单独考虑并发正确性。
- 容器能够安全地保存一个 `ArrayList` 引用，但多个线程同时修改这个 `ArrayList` 时，仍然需要保护它自身的操作。
- 并发修改期间的遍历具有弱一致性，读取 `size` 也无法获得整个容器某个时刻的事务快照。

### 3. 讲一下常见的 GC 收集器和 GC 原理

**面试回答：**

GC 主要负责识别已经无法继续使用的对象，并回收它们占用的内存。Java 通常通过可达性分析判断对象是否仍然存活：从 GC Roots 出发沿着引用关系访问对象，能够访问到的对象会被保留。常见的 GC Roots 来源包括活动线程使用的局部变量、已加载类的静态引用和 JNI 全局引用。两个对象即使互相引用，只要已经无法从 GC Roots 到达，也可以成为回收对象。

常见的回收算法包括标记清除、标记复制和标记整理。标记清除直接释放未被标记的对象，可能产生内存碎片；标记复制把存活对象复制到另一片空间，再整体回收原来的空间，适合存活对象数量较少的区域；标记整理把存活对象移动到一起，获得较连续的空闲空间。

许多收集器会利用分代思想，因为大量对象的生命周期很短。年轻代较频繁地回收，传统实现通常采用复制算法；存活较久的对象进入老年代，老年代按照具体收集器采用清除、整理或者区域复制等方式回收。对象进入老年代还受到年龄、对象大小和可用空间等条件影响。

常见收集器中，Serial 使用一个 GC 线程，Parallel 使用多个 GC 线程并重点考虑吞吐量；CMS 通过并发标记和并发清除缩短老年代回收中的暂停；G1 把整个 Java heap 划分成多个 Region，结合垃圾数量和预计回收耗时选择回收区域；ZGC 通过让大量工作与应用线程并发执行，重点减少暂停时间。Serial、Parallel、G1 和 ZGC 的选择需要结合资源、吞吐量和暂停要求。[Oracle 收集器说明](https://docs.oracle.com/en/java/javase/24/gctuning/available-collectors.html)

我会结合具体 JDK 版本说明收集器。CMS 常见于 JDK 8 的讨论，并且已经在 JDK 14 移除。G1 的暂停目标用于指导回收决策，实际暂停时间仍然需要根据 GC 日志和业务负载验证。对于支付接口，我会关注 GC 暂停对响应时间的影响，同时检查对象分配速度、存活对象数量、内存容量和 CPU 使用情况。

**各个收集器的机制可以继续说明：**

- **Serial / Serial Old**：分别用于年轻代和老年代，经典实现分别采用复制和标记整理，回收时会暂停应用线程。
- **ParNew**：年轻代的并行收集器，在较早的 HotSpot 中常与 CMS 配合使用。
- **Parallel Scavenge / Parallel Old**：经典组合分别负责年轻代和老年代，通过多个 GC 线程进行回收，适合重点关注吞吐量的任务。
- **CMS**：老年代主要采用标记清除，经典流程是初始标记、并发标记、重新标记和并发清除。初始标记及重新标记需要暂停应用线程；并发期间会与业务竞争 CPU，也可能产生内存碎片和本轮未能回收的新垃圾。
- **G1**：Region 可以分别承担 Eden、Survivor 和 Old 的角色，年轻代回收及 Mixed GC 会把选中区域的存活对象复制到其他 Region。Mixed GC 可以同时回收年轻代和部分老年代区域。Remembered Set 用于记录相关的跨区域引用，减少每次回收需要检查的范围；对象复制等阶段仍然需要暂停应用线程。
- **ZGC / Shenandoah**：都以减少暂停为重要目标，并采用并发回收机制；具体分代方式、支持范围和配置需要结合 JDK 版本及发行版说明。
- **并行与并发**：并行表示多个 GC 线程同时工作；并发表示 GC 工作与应用线程在同一时间段内进行。一个收集器可以同时具备这两种特征。

### 4. 讲一下跳表的数据结构，以及为什么这样设计多层链表

**面试回答：**

跳表是在有序链表上增加多层索引的数据结构。最下面一层包含全部元素，上面的每一层只保留一部分节点，层数越高，节点数量通常越少。一个节点可以拥有指向多个层级后继节点的指针。

查询时，从最高层开始向右查找。如果继续向右会超过目标，就下降一层继续查找，最终在最下面一层找到目标或确定目标不存在。例如查询 70，最高层可以直接从 10 前进到 50；如果下一个节点是 90，就在 50 所在的位置下降一层，继续经过 60 查找 70。上层索引让一次前进能够跨过多个底层节点，因此查询需要访问的节点通常会显著减少。

节点的层数通常通过随机过程决定。假设每次以 `p` 的概率增加一层，那么更高层的节点数量会按比例减少，能够形成约 `O(log n)` 的预期高度。在标准随机层数设计下，查找、插入和删除的期望时间复杂度都是 `O(log n)`，空间复杂度是 `O(n)`。具体空间开销受到层数上限及 `p` 的影响。

插入时会在查询过程中记录各层的前驱节点，根据新节点随机得到的层数修改相应的后继指针；删除时修改它涉及的各层连接。跳表能够较自然地支持有序遍历和范围查询：定位范围起点后，沿最下面一层连续访问即可，查询返回 `m` 个元素的期望复杂度为 `O(log n + m)`。

**追问时可以补充：**

- 多层索引会增加指针所占的空间，但上层节点按比例减少，使总的预期空间开销保持线性。
- 随机层数使插入过程无需为了维持固定的索引间隔，大范围调整其他节点。
- `O(log n)` 是期望复杂度；如果层数分布很不理想，查找可能退化到 `O(n)`。
- Redis 的 ZSet 在采用跳表编码时，会结合字典支持按 member 查询，跳表支持有序查询；score 相同时再按 member 的字典序排序。[Redis sorted sets 文档](https://redis.io/docs/latest/develop/data-types/sorted-sets/)

### 5. 讲一下 Redis 中的 RDB 和 AOF 机制、区别，以及持久化机制

**面试回答：**

RDB 保存某个时刻的数据快照，AOF 记录改变数据的写入操作，重启时通过快照加载或操作重放恢复数据。

RDB 可以由 `SAVE` 或 `BGSAVE` 生成。`SAVE` 会阻塞服务；`BGSAVE` 通过 `fork` 创建子进程，由子进程生成快照文件，父进程继续处理请求。它利用 Copy-on-Write：父子进程开始时共享内存页面，后续发生写入时，再复制需要修改的页面。RDB 通常文件紧凑、恢复较快，适合备份；异常退出时，最后一次快照之后的更新可能丢失。

AOF 会把写入操作追加到日志。写入文件首先可能只到达操作系统的 page cache，随后通过 `fsync` 提交给存储设备。`appendfsync always` 在写入批次后同步，可靠性较高但延迟成本较高；`everysec` 通常每秒同步，异常时可能丢失约一秒的更新；`no` 由操作系统决定同步时机。文件会随更新增长，可以通过 AOF rewrite 根据当前数据生成更精简的记录。[Redis 持久化文档](https://redis.io/docs/latest/management/persistence/)

两者的主要区别是记录内容、丢失更新的时间范围和恢复成本。RDB 的恢复点取决于快照时间，AOF 的恢复点受到 `fsync` 策略影响；RDB 通常更紧凑、加载较快，纯操作日志形式的 AOF 通常更大，并且需要重放操作。具体成本还受到重写及混合持久化配置影响。

例如一个计数器递增了 100 次，重写时可以直接记录它当前的结果。启用混合持久化时，重写生成的基础内容还可以采用 RDB 格式，再配合后续的 AOF 增量操作恢复数据。Redis 7.0 及以上支持由基础文件、增量文件和 manifest 管理的多部分 AOF。

如果同一实例同时开启 RDB 和 AOF，正常重启时通常优先使用 AOF 恢复，因为它包含更完整的更新。业务选择还取决于可以接受的数据丢失时间、磁盘写入成本和恢复时间。在支付业务中，关键账务数据需要由具有明确事务和持久性保证的存储保存，Redis 的配置也需要根据它承担的缓存或业务状态职责确定。

**追问时可以补充：**

- `fork` 本身需要时间，后台生成快照期间的 Copy-on-Write 还可能增加内存使用，因此 `BGSAVE` 也可能影响请求延迟。
- `everysec` 的“约一秒”是常见故障条件下的说明，实际情况还会受到磁盘阻塞和配置等因素影响。
- AOF rewrite 根据当前内存数据重新生成基础内容，正常处理请求期间的新增写入也需要保存。
- 持久化帮助实例重启后恢复数据；主从复制提供其他副本。Redis 的异步复制仍然存在主从切换时丢失尚未复制更新的可能性。

### 6. 如果 Redis 的 key 占用 1 GB 内存，怎么删除？

**面试回答：**

我会确认这个 key 对应的类型、元素数量和删除期间是否仍然有人写入。在支持 `UNLINK` 的 Redis 4.0 及以上版本中，可以使用 `UNLINK key`，让需要大量遍历的对象释放工作交给后台线程处理。

`UNLINK` 执行时会把 key 从数据库字典中移除，后续请求就无法再通过这个 key 访问原来的数据；对于释放成本较高的对象，内存回收随后由后台线程完成。这样可以减少主线程长时间处理大量内存释放工作的情况。命令返回时，后台内存回收可能仍然在进行。[Redis UNLINK 文档](https://redis.io/docs/latest/commands/unlink/)

如果使用 `DEL` 删除包含大量元素的 Hash、Set、List 或 ZSet，主线程可能需要处理大量节点的释放，从而影响其他请求。删除成本还取决于数据类型和编码方式，单个 String 的 `DEL` 在命令复杂度上是 `O(1)`，集合类型通常还需要考虑元素数量。[Redis DEL 文档](https://redis.io/docs/latest/commands/del/)

业务侧也需要停止对旧数据的写入，或者通过版本化的 key 把后续写入切换到新的名称，否则删除后可能再次创建同名 key。如果当前环境没有 `UNLINK`，对于可逐个删除元素的集合，可以采用小批量、限速的方式持续删除元素，最后删除空 key。这个过程中要协调并发写入，并检查是否仍有剩余元素。

**追问时可以补充：**

- `UNLINK` 适合把释放成本较高的对象交给后台线程，小对象可能直接释放；它没有保证所有对象都经过后台线程。
- 可以使用 `TYPE`、对应类型的元素计数命令，以及 `MEMORY USAGE` 了解情况。对于集合，检查内存时也需要注意采样选项和检查开销。
- 可通过 `EXISTS` 检查 key 是否已经移除，通过 `INFO memory` 观察后台任务和内存使用。内存分配器可能保留已释放空间，因此进程的 RSS 未必立即减少相同大小。
- Hash 或 Set 可以使用 `HSCAN`、`SSCAN` 查找并分批删除元素；扫描期间内容变化可能导致重复或变化中的元素无法在本轮完整检查，需要结合剩余元素数量持续确认。
- 大量大 key 同时删除会增加后台队列、CPU 和内存压力，需要控制删除速度，并观察请求延迟及 `lazyfree_pending_objects`。
- 单个 value 长期增长到 1 GB 还说明需要检查数据模型，设置容量限制、过期条件，或者按业务范围分成多个 key。

### 7. 了解 Kafka 吗？怎么保证消息不丢失？

**面试回答：**

Kafka 按 Topic 和 Partition 保存消息。每个 Partition 内部是有序的追加日志，可以有多个副本，由 leader 处理读写，follower 复制日志。Consumer Group 通过 offset 记录消费进度。

我会分别检查生产者发送、Broker 存储和消费者处理这三个阶段，并明确需要应对的故障范围。

生产者需要获取发送结果。调用 `send` 后，消息可能还在客户端缓冲区，因此要处理 Future 或回调中的成功、超时和失败。可以配置 `acks=all`、合理的重试及 `delivery.timeout.ms`，并开启 `enable.idempotence=true`，减少生产者重试导致的重复写入。发送始终失败时，需要有能够恢复的业务事件记录，支持后续继续投递。幂等生产者还有相应的重试及并发请求配置要求。[Kafka Producer 配置文档](https://kafka.apache.org/40/configuration/producer-configs/)

Broker 侧可以使用三个副本，配置 `min.insync.replicas=2`，配合 `acks=all`。ISR 是当前与 leader 保持同步的副本集合，包含 leader 自身。`acks=all` 要求满足当前 ISR 的确认条件，`min.insync.replicas` 限定至少需要多少个同步副本：只剩 leader 一个同步副本时，这组配置会使写入失败。配置 `unclean.leader.election.enable=false`，关闭传统的非正常 leader 选举，防止把缺少已确认数据的副本选为 leader。[Kafka Topic 配置文档](https://kafka.apache.org/38/generated/topic_config.html)

例如 A 是 leader，B、C 是 follower，当前 ISR 中有 A、B。在 A、B 满足确认条件后生产者收到成功，A 随后发生故障，B 仍然保存着这条消息。这里的保证依赖至少有相应的同步副本继续保有数据；Kafka 常规写入依赖 page cache 和复制，`acks=all` 的确认条件不要求每个副本每条消息都执行一次 `fsync`。多个副本所在机器同时断电等故障，需要另外考虑磁盘同步策略和故障隔离。

消费者侧，我会关闭自动提交，通过 `enable.auto.commit=false` 控制进度，在业务处理及相关数据库事务完成后提交 offset。如果先提交 offset，随后业务处理失败，重启后的消费者就可能跳过这条消息。按照处理完成后提交的顺序，异常发生时可能重新消费，因此业务操作还需要按事件编号进行幂等处理。消息保留时间也要覆盖正常积压和故障恢复所需的时间。

**追问时可以补充：**

- 三个副本、最小 ISR 为两个时，容忍的故障还取决于故障发生时哪些副本在 ISR 中，以及它们是否保有数据；确认条件不足就应当向生产者报告失败。
- `enable.idempotence` 主要处理生产者协议重试造成的重复，业务主动生成两条相同事件以及消费者重复处理，还需要业务幂等设计。
- 支付场景可以使用稳定的 `eventId`，在同一个数据库事务中写入幂等记录和业务结果，并通过唯一约束协调并发重复消费。
- 同一 Partition 内并行处理时，只能提交已经连续处理完成的位置，防止后面的消息先完成后，提交的 offset 越过前面尚未完成的消息。提交值表示下一条要消费的位置。
- 如果需要把业务数据修改和待发送事件同时保存，可以使用同一数据库事务中的 Outbox 记录，并由独立任务持续投递。Kafka 的生产者配置还需要覆盖消息进入 Broker 之前的这段业务过程。

### 8. RocketMQ 如何从技术层面保证消息不丢失？

**面试回答：**

我会按生产者、Broker 和消费者说明，并以 RocketMQ 4.x 的传统主从模式为例。

生产者使用能够获取结果的同步发送或异步发送，并检查返回状态。RocketMQ 4.x 的发送结果除了 `SEND_OK`，还可能包括 `FLUSH_DISK_TIMEOUT`、`FLUSH_SLAVE_TIMEOUT` 和 `SLAVE_NOT_AVAILABLE`。这些结果说明磁盘同步或者副本确认没有达到要求，需要记录事件、检查状态并进行重试或后续处理。发送超时也可能发生在 Broker 已接收消息之后，因此每个业务事件需要稳定的唯一编号。

Broker 会把消息正文顺序追加到 CommitLog，通常通过内存映射访问文件；ConsumeQueue 保存消息在 CommitLog 中的位置等信息，支持按队列消费。写入内存映射对应的缓存页面之后，还需要把数据同步到磁盘。在 `SYNC_FLUSH` 模式下，生产者要求等待存储确认时，Broker 要等磁盘同步完成才能满足成功条件；在 `ASYNC_FLUSH` 模式下，确认时最新消息可能仍然只在缓存页面中。

主从复制也有独立的确认条件。传统 `SYNC_MASTER` 模式会等待从节点复制达到要求，以降低主节点故障造成的数据丢失；`ASYNC_MASTER` 存在主节点已经接收、从节点尚未复制的时间段。`SYNC_FLUSH` 负责磁盘同步，`SYNC_MASTER` 负责副本复制，两项都需要按照可靠性要求配置，并检查确认状态。同步复制的确认本身也没有要求从节点此时一定已经执行磁盘同步。[RocketMQ 4.x 发送状态与 Broker 配置说明](https://rocketmq.apache.org/docs/4.x/bestPractice/01bestpractice/)

例如主节点接收一条支付结果消息，如果只做异步复制，主节点可能在从节点收到消息之前故障；如果最新数据还没有完成磁盘同步，机器断电也可能造成数据丢失。因此，回答可靠性时需要说明具体等待了哪些条件，以及剩余副本能否保存数据。

消费者以 4.x 的集群并发消费接口为例，在业务处理和相关数据库事务完成后返回 `CONSUME_SUCCESS`，处理失败返回 `RECONSUME_LATER`，由重试机制继续处理。如果业务还在异步任务中执行，监听方法就已经返回成功，随后任务失败就可能失去正常的消费重试机会。超过重试上限的消息进入 DLQ 后，还需要告警、检查和重新处理。副本数量、磁盘故障以及消息保留时间都属于这套保证的条件。

**追问时可以补充：**

- “同步发送”说明生产者等待发送响应；Broker 的磁盘同步方式由 `flushDiskType` 等条件控制。
- NameServer 主要提供服务发现和路由信息，消息正文保存在 Broker 的 CommitLog 中。
- 消费进度确认和业务数据库事务之间也存在异常窗口。业务已经完成，但进度尚未保存时可能重复消费，需要业务幂等设计。
- 幂等记录和业务修改可以放在同一个数据库事务中，借助稳定的 `eventId` 和唯一约束，使同一事件的重复消费得到可重复确认的结果。
- RocketMQ 事务消息通过 half message、本地事务执行、提交或取消，以及事务状态回查，协调业务事务与消息投递。回查必须能够根据已保存的业务结果判断状态，消费端仍然需要幂等。
- DLedger、Controller 等模式需要按照各自版本和部署方式解释复制、选举与确认条件。4.x 的传统 `brokerRole` 参数不能直接代表所有部署模式的行为。

### 9. 讲一下 TCP 拥塞控制机制

**面试回答：**

TCP 拥塞控制根据网络反馈调整发送量，防止发送方持续向已经拥堵的路径注入更多数据。发送方维护拥塞窗口 `cwnd` 和慢启动阈值 `ssthresh`；接收方通过 `rwnd` 表示接收能力。能够保持在网络中的未确认数据量同时受到 `cwnd` 和 `rwnd` 的限制，还需要扣除已经发送但尚未确认的数据。

按照经典 Reno 和 RFC 5681 的说明，主要包括慢启动、拥塞避免、快速重传和快速恢复。

慢启动从较小的窗口开始，根据新数据的 ACK 增加 `cwnd`；在典型条件下，窗口大约每经过一个 RTT 增长一倍，因此整体接近指数增长。达到 `ssthresh` 附近后进入拥塞避免，每个 RTT 大约增加一个 MSS，使窗口接近线性增长，继续探测网络可以承受的负载。

发生重传超时时，发送方会认为网络可能出现较严重拥塞，将 `ssthresh` 调整到未确认数据量的一半附近，并且至少为两个 MSS，把 `cwnd` 降到一个 MSS，重传后重新进行慢启动。

如果连续收到三个重复 ACK，发送方会推断某个报文段可能丢失，触发快速重传。随后进入快速恢复：把 `ssthresh` 调整到未确认数据量的一半附近，并且至少为两个 MSS，把 `cwnd` 设置为 `ssthresh + 3 * MSS`；后续重复 ACK 会继续参与窗口调整。收到确认恢复进展的新 ACK 后，经典 Reno 把 `cwnd` 调整到 `ssthresh`，继续拥塞避免。Reno 的这一过程利用了后续报文仍在到达的反馈。[RFC 5681：TCP Congestion Control](https://www.rfc-editor.org/rfc/rfc5681.html)

例如以 MSS 为单位，当前未确认数据量是 16，快速重传时可以把 `ssthresh` 设置为 8，`cwnd` 暂时设置为 11，恢复后以 8 为基础继续增长；如果发生重传超时，则把 `cwnd` 降到 1，重新进入慢启动。这个例子体现了两种丢包反馈下不同的窗口调整过程。

**追问时可以补充：**

- `cwnd` 根据网络反馈限制发送量，`rwnd` 根据接收缓冲区的可用空间限制发送量，因此拥塞控制和流量控制共同限制发送行为。
- 重复 ACK 也可能由报文乱序产生，经典快速重传通过三个重复 ACK 形成丢包判断依据。
- 阈值计算使用尚未确认的数据量 `FlightSize`；它与当前 `cwnd` 不一定相等。
- MSS 表示单个 TCP 报文段可携带的最大数据量，RTT 表示从发送到收到确认的往返时间。
- 初始 `cwnd` 的大小与标准、实现和配置有关。重传超时后降低到一个 MSS，是经典算法中的规则。
- CUBIC、BBR 等算法具有各自的窗口或发送速率调整机制；这里的具体增长及恢复公式限定在经典 Reno 的说明范围内。
