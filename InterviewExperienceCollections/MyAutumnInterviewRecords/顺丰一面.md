### 13. Redis Sentinel 的工作原理是什么，怎样保证高可用

**考察内容：** 故障判定、执行故障转移的授权、replica 提升和客户端发现。

**你的回答与评分：2/10。** 12:13 提到了主节点故障后更换主节点，但把 Sentinel 的投票和 Redis replica 的角色混在一起；投票门槛无法确定，也没有讲出主观下线、客观下线和客户端更新。

**参考回答：** Sentinel 负责监测 Redis 主从实例、判断故障并组织自动切换。单个 Sentinel 判断主节点不可用称为 SDOWN；达到配置的 quorum 后，可以判定 ODOWN。真正执行故障转移还需要选出负责本次操作的 Sentinel，并获得多数 Sentinel 的授权。随后它从符合条件的 replica 中选择新主节点，安排其他 replica 跟随新主节点，并发布新的主节点地址。客户端需要支持 Sentinel 的主节点发现。Redis 主从复制通常是异步的，切换过程中仍可能丢失部分已经确认的写入。

**练习例子：** 5 个 Sentinel、quorum 为 2 时，2 个判断不可用可以满足客观下线条件，执行切换仍需要至少 3 个授权。quorum 与多数授权是两个不同条件。

### 14. Redis Sentinel 与 Redis Cluster 有什么区别

**考察内容：** 高可用与数据分片的关系。

**你的回答与评分：4/10。** 12:48 说出了一个主节点与多个主节点的区别，但把 Cluster 描述成查询流量分摊，缺少 key 的数据分布和容量扩展机制。

**参考回答：** Sentinel 为普通 Redis 主从组提供监控和自动故障转移，单个主从组的完整数据由一个主节点承担。Redis Cluster 将 key 空间分成 16384 个 hash slot，不同主节点负责不同 slot，因此能够分担数据容量和处理压力，每个主节点还可以有 replica 提供故障恢复。一次 key 查询会路由到负责对应 slot 的节点。Sentinel 解决主从组故障切换，Cluster 同时提供分片和各分片的故障处理。

**练习完成标准：** 能准确解释“5 个 Sentinel、quorum 为 2”的故障切换条件，并说明 Sentinel 与 Cluster 的请求路径。针对解封任务，能够讲出同一玩家先后两次封禁、旧任务延迟执行、两个实例重复执行和缓存缺少部分记录时的处理方式。

**实际练习：** 在有 Redis 的练习环境中，观察主从复制和 Sentinel 切换后的客户端连接变化；记录 ZSet 按到期时间查询的结果。故障切换实验与业务幂等验证需要分别进行。

### 第二优先级 项目设计依据与数据同步

**缺口依据：** 第 9、10、11、25、26、30、31 题中的规模、选型和一致性解释不足。这里与 Redis、ES 相互关联，重点是把原理用于你自己的项目。

**需要补齐的项目资料：** 每条业务记录的含义和唯一标识；数据的权威来源；读写及同步路径；数据库索引；调用成功条件；多实例任务机制；失败处理；总量、增量、QPS、P95/P99 耗时和同步延迟的定义及数据来源。无法确认的项目资料明确保留为待核对内容。

**练习完成标准：** 定时解封和处罚查询分别准备一段 2 分钟的说明，覆盖业务问题、你的责任、处理过程、关键判断、故障情况和验证依据。能解释为什么选择组件，以及这个选择增加了哪些维护成本。

### 第二优先级 规则生命周期与客户端执行

**缺口依据：** 第 21、24、35 题涉及规则规模、端上规则与低命中规则治理。你对规则的业务用途已有基础，这部分需要补充执行和维护机制。

**需要掌握：** 规则解析与求值、候选规则筛选、优先级、命中后的停止条件、规则冲突、版本管理；适用数、执行数和命中数的区别；低频高风险规则；客户端规则包下发、本地字段、兼容性、有效期和关键状态校验。

**练习完成标准：** 为“收派员 APP 获取版本化规则包并结合本地订单数据执行”准备完整说明；能分别处理规则过期、缺少字段、多个规则命中和服务端关键数据变化。对于一条长期未命中的规则，能够解释怎样根据适用案件、执行路径和历史案例决定是否停用。
