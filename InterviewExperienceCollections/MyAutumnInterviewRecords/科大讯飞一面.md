### 6. 使用 AI 编程时遇到过哪些问题

我遇到的主要问题是工具对历史业务和现有代码理解不完整。比如它能够根据接口说明生成实现，但可能忽略某个字段只在特定状态下有效，也可能重复实现仓库里已有的能力，或者没有处理重复请求、超时和部分步骤失败的情况。我的处理方式是把相关代码、业务规则和具体输入输出提供给工具，控制每次修改的范围，然后检查关键分支并运行测试。复杂业务的正确性需要结合完整处理流程判断，只检查代码能否编译还不充分。

### 7. AI 对业务理解不准确，具体表现是什么

技术指令通常比较明确，例如增加一个接口或调整一个查询条件，工具能够根据代码完成操作。业务知识经常包含未写进当前代码的约定，例如哪些案件可以自动审核、什么情况下必须人工确认，以及不同业务方如何解释同一个字段。工具没有获得这些信息时，就可能生成看起来合理、实际业务含义却不正确的实现。因此我会把业务规则、状态变化和具体案例写清楚，同时让工具说明它依据了哪些代码和文档，便于检查理解是否一致。

### 14. 博弈程序使用了哪些技术

校赛阶段主要采用搜索方法，核心包括 Monte Carlo Tree Search，以及结合 Minimax 思路进行局面分析。MCTS 会重复进行选择、扩展、模拟和结果回传，让计算资源更多地用于有希望的行动。Minimax 适合描述双方交替选择行动时的搜索目标，Alpha-Beta 剪枝可以减少一部分无需继续展开的分支。国赛阶段使用过较小的 CNN，通过棋盘特征辅助局面判断。整体需要在比赛时限内平衡搜索数量、评估质量和程序运行速度。

### 20. 开发 Agent 可以使用哪些技术，采用什么技术路线

### 21. 如果使用 Java 开发 Agent，会怎样实现

我会使用 Spring Boot 提供业务接口，通过 Spring AI 的 `ChatModel` 或 `ChatClient` 接入模型，把业务能力封装为具有明确参数和返回值的工具。模型提出工具调用后，由应用执行权限检查、参数校验和实际操作，再把执行结果交给模型继续处理。涉及多步骤任务时，可以使用 Spring AI Alibaba 的 Graph 组织节点、依赖关系和执行状态，需要模型持续选择下一步行动时可以使用 `ReactAgent`。任务状态和执行记录保存在数据库中，同时设置超时、最大调用次数和成本限制；输出需要通过结构校验和业务校验，重要结果进入人工审核。

以上属于技术方案回答。框架 API 的使用方法需要按项目实际选用的版本确认。参考 [Spring AI API](https://docs.spring.io/spring-ai/reference/api/) 和 [Spring AI Alibaba 官方概览](https://java2ai.com/docs/overview/)。

### 24. 请介绍 JVM 的结构，以及需要关注的内容

我会从类加载、运行时内存和执行过程来介绍。类加载子系统负责加载类，并完成验证、准备、解析和初始化等步骤；执行引擎负责执行字节码，HotSpot 会结合解释执行和 JIT 编译提高热点代码的运行效率，GC 则负责管理可回收对象占用的内存。

运行时内存中，Heap 由线程共享，用于分配对象和数组；Method Area 保存类相关信息和运行时常量池，HotSpot 使用 Metaspace 保存类元数据。每个线程还有自己的 PC Register、Java Virtual Machine Stack 和 Native Method Stack，方法调用会建立 Frame，保存局部变量、Operand Stack 等信息。JVM 规范描述这些区域的职责，实际内存布局还需要结合具体实现理解。

如果使用 JDK 17 的 HotSpot，我会关注 GC 类型、堆内存使用、对象分配速度、停顿时间和线程数量。G1 在常见服务端环境中默认使用，它把 Heap 划分为多个 Region，同时保留年轻代和老年代的逻辑划分；年轻代包括 Eden 和 Survivor。分析问题时，还需要关注 Metaspace、线程相关内存和 Direct Memory，因为进程总内存会超过 `-Xmx` 设置的大小。

### 25. 调整 JVM 时，一般关注哪些参数

我没有独立负责过生产环境的 JVM 调优。如果需要处理这类问题，我会先明确目标，例如降低 GC 停顿、控制内存使用或者提高吞吐量，并收集 GC 日志、接口延迟和进程资源数据，再根据现象调整参数。

常见参数包括：

- `-Xms` 和 `-Xmx`：控制初始与最大堆内存，需要结合容器限制及其他内存开销设置。
- `-Xss`：控制每个线程的 Stack 大小，需要同时考虑线程数量和方法调用深度。
- `-XX:MaxMetaspaceSize`：限制类元数据能够使用的空间，动态生成类较多时需要关注。
- `-XX:+UseG1GC`：明确选择 G1；`-XX:MaxGCPauseMillis` 设置期望的 GC 停顿目标，实际停顿仍受对象存活量和机器资源影响。
- `-Xlog:gc*`：记录 GC 事件；`-XX:+HeapDumpOnOutOfMemoryError` 和 `-XX:HeapDumpPath` 用于保存内存不足时的诊断信息。

调整之后，需要在相同负载下检查停顿时间、吞吐量和内存使用是否改善。对于 G1，我会优先保留其自适应能力，再根据日志判断是否需要调整并发标记等参数。参考 [JDK 17 G1 官方文档](https://docs.oracle.com/en/java/javase/17/gctuning/garbage-first-g1-garbage-collector1.html)。

### 26. 线程安全问题是怎样发生的

线程安全问题经常出现在多个线程共同访问可修改数据、至少一个线程执行写入，并且缺少必要同步的情况下。以库存只剩一件为例，业务要求先确认库存大于零，再减少库存并创建订单。线程 A 读取库存为一，判断可以购买；它还没有完成处理时，线程 B 也读取到一并通过判断；随后两个线程都创建订单。即使最后库存数值为零，也已经产生了两笔订单，业务要求被破坏。

发生这种情况，是因为“检查库存、更新库存、创建订单”包含多个步骤，线程调度可以让两个请求在这些步骤之间交替执行。单核处理器也会发生这种交替，多核处理器还可能让线程同时运行。类似地，`count++` 包含读取、加一和写回；两个线程都从零计算出一，再分别写回，最终可能只增加一次。这属于原子性问题。

可见性问题关注的是一个线程写入的结果，另一个线程是否能够按照规定观察到。Java Memory Model 通过 happens-before 关系规定同步行为，例如释放某个监视器之后，另一个线程成功获取同一个监视器，可以看到之前受到保护的写入。编译器和处理器还可能重新排列操作；缺少同步时，其他线程可能观察到不符合业务预期的执行效果。这属于有序性需要处理的问题。

单个 JVM 内，可以使用同一把 `synchronized` 监视器或同一个 `Lock`，保护完整的检查和修改过程；简单计数可以使用 `AtomicInteger` 等原子类。`volatile` 能够提供相应的可见性和顺序保证，但 `count++` 仍然包含多个步骤。多个服务实例共同修改数据库时，需要把并发控制放在它们共同访问的数据资源上，例如使用条件更新 `UPDATE inventory SET stock = stock - 1 WHERE id = ? AND stock > 0`，根据受影响行数判断是否成功，并结合事务和业务唯一约束处理订单创建及重复请求。不同 JVM 中各自持有的本地锁，不能形成跨实例的共同互斥。

### 27. Redis Cluster 与 Sentinel 模式有什么区别

Sentinel 主要为主从复制提供监控、故障判断、自动切换和主节点地址发现。一组主从实例通常保存同一份逻辑数据，由主节点处理写入，副本复制主节点的数据；主节点发生故障后，Sentinel 协调选出新的主节点。Sentinel 本身不保存业务数据，也不直接代理业务请求。

Redis Cluster 同时提供数据分片和故障转移。它把 key 映射到 16384 个 Hash Slot，并把这些 Slot 分配给不同主节点；每个主节点负责一部分数据，也可以配置副本。客户端需要根据 Slot 路由请求，并处理迁移期间的重定向。需要涉及多个 key 的命令、事务或 Lua 脚本时，相关 key 通常必须处于同一个 Slot。两种模式都需要考虑异步复制带来的数据丢失窗口。

参考 [Redis Sentinel 文档](https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/) 和 [Redis Cluster 规范](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)。

### 28. Redis Cluster 与 Sentinel 分别适合什么场景

如果数据容量和主要写入压力可以由一台 Redis 主节点承受，需求主要是故障后的自动切换，可以使用 Sentinel 管理主从实例。如果总数据量或写入压力已经需要多台主节点共同承担，就可以考虑 Cluster，通过分片扩大容量和处理能力。

选择 Cluster 时还要检查业务的 key 设计。需要原子执行的多个 key 可以使用相同的 Hash Tag 放入同一个 Slot，但过多数据集中到一个 Slot，又会限制分片效果。单个热点 key 的负载也不会因为增加分片而自动平均分配。对于一致性要求，两种模式都需要结合复制方式、读请求访问的节点和故障转移行为进行分析，不能仅凭部署模式保证数据绝对不丢失。

### 29. 请完整介绍 HashMap 的 put 方法执行过程

以 JDK 17 的 `HashMap` 为例，`put(key, value)` 会计算 key 的 hash，常见实现是 `h ^ (h >>> 16)`，其中 `null` key 的 hash 为零，然后进入 `putVal`。如果内部数组还没有初始化，就通过 `resize` 创建数组。数组长度为二的幂，因此可以通过 `(n - 1) & hash` 找到对应位置。

如果这个位置为空，就直接创建节点。如果已有节点，就检查 hash 和 key 是否匹配，key 的比较会结合引用相同和 `equals`。找到相同 key 时，更新对应 value 并返回旧值；如果该位置使用红黑树，就进入树节点的插入或更新流程；如果是链表，就继续遍历，找到相同 key 后更新，遍历结束仍未找到则在尾部加入新节点。链表达到触发条件时还会调用 `treeifyBin`，由它根据数组容量决定扩容或转换为红黑树。

新增映射后，`size` 和结构修改计数会增加。如果 `size` 超过 `threshold`，就调用 `resize`，通常把数组容量扩大为两倍并重新分配节点位置。更新已有 key 的 value 不会增加 `size`。整个过程由调用线程执行，普通 `HashMap` 的 `put` 没有内置的互斥保护；并发修改时需要另外提供同步，或使用适合并发访问的集合。

### 30. HashMap 扩容和链表转红黑树的条件分别是什么

扩容主要关注整个 Map 的映射数量。默认负载因子是 `0.75`，常见情况下 `threshold` 等于数组容量乘以负载因子。例如数组容量为 16 时，阈值为 12，加入第 13 个不同 key 后会触发容量扩展。`size` 统计全部 key-value 映射，同一个数组位置中的多个节点也分别计入。

树化关注的是某一个位置上的链表。JDK 17 定义 `TREEIFY_THRESHOLD = 8` 和 `MIN_TREEIFY_CAPACITY = 64`。按照普通 `putVal` 的链表追加路径，原本具有八个节点的链表再加入第九个不同 key 时，会尝试调用 `treeifyBin`；数组长度小于 64 时优先扩容，达到 64 时才执行树化。这里需要结合遍历计数理解触发位置。

通常扩容到原容量的两倍后，一个节点的新位置只可能是原位置 `j` 或 `j + oldCap`，可以根据 `hash & oldCap` 判断。这样可以利用已有 hash 分配节点，减少重新计算的工作。参考 [JDK 17 HashMap API](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/HashMap.html)；这里的树化触发过程采用 JDK 17 的实现口径。

### 31. 链表和红黑树可以继续增加节点，HashMap 为什么还需要扩容

HashMap 需要控制查询和写入的成本。数组容量长期不变、元素持续增加时，平均每个位置容纳的节点数量会增加，查询就需要进行更多比较。扩容能够让一部分原本处于同一位置的节点分配到不同位置，减少冲突，在 hash 分布合理的情况下维持接近常数的平均访问时间。

红黑树主要用于控制某个位置发生大量冲突时的查找成本；增加数组容量则能够改善整个 Map 的平均分布。两者处理的问题范围不同。扩容也有分配数组和迁移节点的成本，因此需要通过负载因子在内存使用和访问效率之间取得平衡。如果许多 key 的 hash 完全相同，增加数组长度也无法把它们分散到不同位置，还需要树节点等机制处理。

### 32. 如何用“空间换时间”解释 HashMap 扩容

假设原来有 16 个数组位置，随着元素增加，每个位置平均需要容纳更多节点。把数组扩大到 32 个位置，就使用了更多内存，但其中一部分节点能够分配到新增位置，后续查找和插入通常需要比较的节点就会减少。这里增加的数组空间，换来了后续访问时间的减少。扩容本身需要时间，合理的初始容量可以减少多次扩容的开销；实际效果还取决于 key 的 hash 分布。

### 36. 配置热更新背后的具体技术是什么

热更新需要解决变更发现、内容传输和应用生效三个步骤。发布配置时，服务端保存新的配置内容和版本；客户端通过长轮询或订阅连接发现版本变化，再获取配置；应用收到更新后完成类型和业务校验，构造完整的新配置对象，通过 `volatile` 引用或 `AtomicReference` 一次性发布给工作线程。对于多字段配置，把所有相关字段作为一个不可变对象更新，可以防止请求读取到新旧字段混合的状态。

长轮询的过程是客户端带着自己已经知道的版本发起请求，服务端在没有变化时等待，在出现新版本或请求超时后返回，客户端处理响应后继续发起下一次请求。更新过程还需要处理连接中断、重复通知和乱序通知，并通过版本比较识别有效更新。热更新是否真正完成，取决于业务代码何时使用新对象，因此需要记录“收到配置”“校验完成”和“开始使用”的状态。

### 37. 配置中心、规则引擎和热部署分别负责什么

配置中心负责保存、发布和分发配置，规则引擎负责根据输入数据执行规则。比如配置中心分发“某类案件满足若干条件时进入自动审核”的规则定义，规则引擎读取案件字段并计算条件，业务服务再根据结果执行后续动作。规则引擎可以支持表达式、决策表等形式，具体能力取决于选用的实现。

如果应用已经支持一种规则结构，只修改该结构中的条件和参数，就可以通过更新规则数据改变行为。新增应用从未提供过的执行能力时，仍然需要进行相应的代码开发和发布。热部署通常涉及运行中的程序组件或代码更新，配置热更新则关注运行时配置变化。对于实习中使用的 TCC 平台，我能够说明的是配置接入与使用过程，内部是否集成了某种规则引擎，需要依据平台文档或实现确认。

### 38. 规则同步这件事情复杂吗

复杂之处在于不同实例接收和处理更新的时间不同。某个实例可能已经启用新规则，另一个实例还在处理旧版本，另一个实例可能暂时无法连接配置服务。如果一组规则还存在相互依赖，就需要保证整组内容一起校验和切换。此外，还需要处理重复通知、乱序通知、发布权限、版本恢复以及更新过程中的请求。

跨地区出现网络分区时，还需要明确业务要求。如果必须使用最新规则，就要限制无法确认版本的实例继续处理相关请求；如果业务允许在规定时间内继续使用已验证版本，就需要记录版本有效期并监控更新状态。CAP 讨论的是发生网络分区时，一致性与可用性无法同时完全满足。具体系统仍然要把要求写成可执行的条件，例如允许旧版本存在多久、哪些动作必须暂停，以及恢复连接后如何确认新版本已经启用。

### 40. 配置怎样在跨机房、多个服务实例之间同步

需要分别考虑配置服务之间的数据复制，以及配置服务向业务实例的分发。一种设计是由明确的发布入口为每次变更生成版本，把配置内容可靠地复制到目标地区，再由各地区的配置服务通知本地业务实例。业务实例收到通知后获取完整配置，验证版本和内容，启用成功后上报当前使用的版本。服务端可以据此检查传播进度，并发现尚未完成更新的实例。

多个实例需要的是同一份已发布配置时，应当从配置服务获取该版本，实例之间不必相互转发。遇到断开连接的实例，恢复连接后需要主动检查版本，防止只依赖某一次通知。对于要求统一生效的变更，还可以增加准备和启用两个阶段：各实例先加载指定版本，再在满足发布条件后允许使用；未准备完成的实例需要限制相关流量，单独设置一个生效时间无法解决所有异常情况。

### 41. 配置中心的实现逻辑是什么

以 Apollo 官方设计为例，用户通过 Portal 修改和发布配置，Admin Service 保存发布结果，Config Service 向应用提供配置读取与变更通知。Apollo 客户端通过 HTTP 长轮询等待通知，发现关注的 Namespace 有变化后，再请求该 Namespace 的最新配置。客户端同时维护内存中的配置，并通知应用订阅者；它还会定时检查配置，以及在本地文件中保存已取得的内容。

应用要让新配置真正改变业务行为，还需要在更新回调中完成自身的处理。例如重新建立规则对象、更新限流参数或切换功能开关，并对业务约束进行校验。配置服务可达、客户端取得新内容和业务开始使用新版本，分别是需要观察的状态。规则内容如果作为配置分发，也可以采用相同的版本通知与获取机制，随后交给规则执行组件处理。

我当时没有研究过实习配置平台的内部实现，这里的原理使用公开系统说明。参考 [Apollo 官方设计文档](https://raw.githubusercontent.com/apolloconfig/apollo/master/docs/zh/design/apollo-design.md)。

### 44. 如何看待 Go、Python、Java 等语言的差异

我会从运行方式、并发支持、类型表达和项目生态来看。Go 通常编译为可执行程序，同时带有 GC 和调度等运行时能力；goroutine 和 channel 使并发任务的组织比较直接。Java 代码通常编译为字节码，由 JVM 执行，HotSpot 可以对热点代码进行 JIT 编译；Java 的企业应用、数据库访问和服务治理生态比较完善。Python 表达灵活，在数据处理和模型应用方面有丰富的库，具体性能则取决于解释器、实现方式，以及是否调用原生计算库。

类型和代码组织方面，Go 常通过组合与接口表达能力；Java 类采用单继承，可以实现多个接口，也支持组合。并发方面，Go 的 goroutine 和 Java 的线程机制都需要正确处理共享数据；Java 21 及之后的版本还可以使用 Virtual Threads 组织大量等待型任务。选择语言时，我会结合团队经验、现有系统、第三方库、部署条件和实际负载进行判断，性能结论需要通过对应场景的测试确认。
