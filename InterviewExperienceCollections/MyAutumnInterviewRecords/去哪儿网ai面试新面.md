### 2. G1 相较于 CMS 有哪些改进？它如何选择回收区域并预测停顿时间？

CMS 主要针对老年代执行并发标记和清除，常规回收阶段采用 Mark-Sweep，存活对象通常保留在原位置，因此长期运行可能产生不连续的可用空间。G1 将 Java Heap 划分为大小相等的 Region，Eden、Survivor 和 Old 都由不同 Region 组成，区域的用途可以随回收过程变化。

G1 在 Young GC 和 Mixed GC 中，把 Collection Set 内的存活对象复制到其他 Region，随后释放原区域。复制过程能够整理存活对象的布局，减轻内存碎片问题。Mixed GC 会回收年轻代和选定的一部分老年代 Region，从而把老年代回收工作分配到多次停顿中。

G1 选择老年代候选区域时，会考虑可回收空间、存活对象数量和处理引用的成本。某个 Region 的垃圾较多，并且处理成本较低，它通常具有更高的回收收益。选择区域时还需要兼顾回收进度和停顿目标。

停顿预测来自历史统计。G1 会记录此前扫描引用、复制对象等阶段的耗时，据此估算本次回收的成本，再调整年轻代大小及 Collection Set 的组成。例如，`-XX:MaxGCPauseMillis=200` 表示希望把停顿控制在约 200 毫秒的目标范围内。这个参数是预测和调节的目标，单次 GC 仍可能超过它。

G1 的复制回收也需要足够的目标空间。空间不足可能产生 Evacuation Failure，进一步可能触发 Full GC；Humongous Object 的分配还会受到连续 Region 的限制。

停顿目标、Region 布局和 Evacuation 的说明可参考 [Oracle G1 文档](https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-g1-garbage-collector1.html)。

### 3. G1 只回收部分 Region 时，如何处理跨区域引用？

局部回收需要找到从 Collection Set 外部进入 Collection Set 的引用。例如，Region B 中的对象引用了 Region A 中的对象，本次只回收 Region A，那么 GC 必须考虑这条引用，并在对象移动后更新引用地址。

Remembered Set 用于记录可能包含这种引用的位置。以 Region A 为例，它关注哪些外部位置可能引用 A 中的对象。GC 可以根据这些记录检查相关内存区域，结合 GC Roots 扫描，找到需要保留和移动的对象。

Card Table 将 Heap 划分为较小的 Card。传统 HotSpot G1 的 Card 通常对应 512 字节的内存。记录 Card 索引可以减少逐条维护对象引用所需的空间；回收时，再检查相应 Card 中的对象和引用。Card 标记表示需要检查的范围，具体引用仍然需要扫描确认。

Write Barrier 在应用修改对象引用时执行附加操作。例如执行 `a.field = b`，Post-Write Barrier 可以将引用所在的 Card 标记为 Dirty。应用线程完成必要的记录，Concurrent Refinement Threads 再分析这些 Card，更新相关 Remembered Set。GC 停顿期间还会处理必要的待处理信息，保证局部回收能够正确检查外部引用。

另外，G1 的并发标记采用 SATB，Pre-Write Barrier 会记录必要的旧引用，保护标记开始时的数据视图。SATB 处理并发标记期间的对象存活信息，Remembered Set 处理区域之间的引用，两者承担不同任务。

这里的实现说明以传统 HotSpot G1 为背景。Remembered Set 的具体组织和维护策略会随 JDK 版本变化。其引用记录和 Card 索引机制见 [Oracle G1 文档](https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-g1-garbage-collector1.html)。

### 4. Java 线程有哪六种状态？各状态之间如何转换？

`Thread.State` 定义了六种状态：

- `NEW`：线程对象已经创建，还没有调用 `start()`。
- `RUNNABLE`：线程已经具备执行条件，可能正在运行，也可能等待操作系统分配 CPU。
- `BLOCKED`：线程正在等待获取 Java Monitor，例如等待进入 `synchronized` 代码块。
- `WAITING`：线程无限期等待其他线程完成某项操作，例如调用没有超时时间的 `Object.wait()`、`Thread.join()` 或 `LockSupport.park()`。
- `TIMED_WAITING`：线程进行有时间限制的等待，例如调用 `Thread.sleep()`、带正数超时时间的 `wait()`、`join()` 或 `parkNanos()`。
- `TERMINATED`：线程已经执行结束。

线程对象创建后处于 `NEW`，调用 `start()` 后进入 `RUNNABLE`。竞争 Monitor 失败会进入 `BLOCKED`，成功获得 Monitor 后重新具备运行条件。执行等待方法后进入对应的等待状态，条件满足、被唤醒或者超时后，再继续参与调度和必要的锁竞争。

`run()` 正常结束，或者线程因未处理的异常而结束执行，都会进入 `TERMINATED`。同一个线程对象只能启动一次，结束后再次调用 `start()` 会产生 `IllegalThreadStateException`。

`wait()` 会释放当前对象的 Monitor，恢复执行前需要重新获得它。`sleep()` 会让当前线程暂时停止执行，但会保留已经持有的 Monitor。Java 的线程状态与操作系统的线程状态也需要分别理解。

六种状态的定义见 [Java Thread.State 文档](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Thread.State.html)。

### 5. 调用 Object.wait 的线程被 notify 唤醒后，会立即进入 RUNNABLE 吗？notify 会立即释放锁吗？

调用 `wait()` 的线程被通知后，需要重新获取这个对象的 Monitor，才能继续执行 `wait()` 后面的代码。如果 Monitor 仍由其他线程持有，被通知的线程会等待重新进入同步区域，此时可以处于 `BLOCKED`。

调用 `notify()` 的线程本身需要持有该对象的 Monitor。执行通知操作后，它仍然保留 Monitor，直到退出对应的 `synchronized` 区域并完成释放。因此，被通知线程的恢复时间取决于 Monitor 什么时候可用，以及线程什么时候得到调度。

例如，线程 A 在同步区域内执行 `wait()`，释放 Monitor 并进入等待。线程 B 获得 Monitor，修改共享条件，调用 `notify()`，随后继续执行同步区域内的代码。在 B 释放 Monitor 后，A 才有机会重新获取 Monitor 并检查条件。

等待条件应当放在 `while` 循环中检查。线程恢复时，条件可能已经被其他线程修改，也可能出现 Spurious Wakeup。`notify()` 通知一个等待线程，`notifyAll()` 通知所有等待线程；每个恢复的线程都需要重新竞争 Monitor，并重新检查自身条件。

`BLOCKED` 包含从 `Object.wait()` 恢复后等待重新获取 Monitor 的情形，定义见 [Java Thread.State 文档](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Thread.State.html)。

### 6. 为什么等待 synchronized 的线程通常处于 BLOCKED，等待 ReentrantLock 的线程通常处于 WAITING？

`BLOCKED` 有明确的 JVM 含义：线程正在等待获取 Java Monitor。`synchronized` 使用 Monitor，线程竞争失败后，等待进入同步区域时可以表现为 `BLOCKED`。

`ReentrantLock` 的常见实现建立在 AQS 之上。获取锁失败后，线程进入同步等待队列；当需要停止运行并等待时，会通过 `LockSupport.park()` 等机制等待许可。没有超时时间的 `park()` 对应 `WAITING`，带有正数等待期限的操作可以对应 `TIMED_WAITING`。

从执行过程看，`ReentrantLock` 获取锁可能经历尝试修改同步状态、入队、短暂重试、等待许可和再次竞争。线程尝试获取锁或者执行重试时仍可能处于 `RUNNABLE`，真正执行等待操作之后才进入相应的等待状态。

因此，查看线程诊断信息时，需要结合调用位置理解状态。`BLOCKED` 提示 Monitor 竞争；`WAITING` 配合 `LockSupport.park()` 和 AQS 的调用记录，则可能提示显式锁、同步器或者其他队列等待。单独看到 `WAITING` 无法确定具体等待对象。

Monitor 等待与 `park()` 等待对应的状态定义见 [Java Thread.State 文档](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Thread.State.html)。

### 7. Redis 的 RDB 和 AOF 分别如何实现持久化？各自适用于哪些场景？

RDB 保存某个时间点的数据快照。以 `BGSAVE` 为例，Redis 主进程调用 `fork()` 创建子进程，由子进程读取快照视图并生成临时 RDB 文件，成功完成后替换原文件。父进程在创建子进程后继续处理请求；`fork()` 本身仍可能产生停顿。`SAVE` 则由执行命令的进程同步生成快照，会阻塞正常请求处理。

AOF 记录恢复数据库状态所需的写操作。写操作执行后，相应内容进入 AOF Buffer，再通过 `write()` 写入操作系统的 Page Cache，随后根据 `appendfsync` 策略进行文件同步。重启时，可以通过加载基础数据和重放后续操作恢复状态。读取命令通常无需记录，因为它们没有改变数据库的数据状态。

RDB 文件通常比较紧凑，适合定期备份、异地备份，以及允许丢失最近一段时间数据的场景。对于较大的数据集，加载二进制快照通常能够较快完成恢复。单独使用 RDB 时，最近一次成功快照之后的修改可能在故障中丢失。

AOF 的同步频率可以根据持久性要求调整。`always` 在同步完成后才确认相关写入，增加了 I/O 成本；`everysec` 通常每秒在后台同步一次；`no` 由操作系统安排同步。AOF 需要重写来控制文件体积，重写根据当前状态生成恢复所需的数据，因此重写后的文件无需保留完整操作历史。

Redis 7.0 起，AOF 可以由 Base File、Incremental Files 和 Manifest 共同组成，Base File 还可以采用 RDB 格式。RDB 与 AOF 可以同时启用，备份文件和日常恢复机制需要分别配置。

持久化流程和多文件 AOF 机制见 [Redis Persistence 文档](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)。

### 8. Redis 生成 RDB 时调用 fork，物理内存会立即增加一倍吗？Copy-on-Write 如何保证快照期间的数据视图？

在 Linux 的常见实现中，`fork()` 后父子进程拥有独立的地址空间描述，但大量数据页继续共享。创建子进程会增加页表、进程管理结构等开销，通常无需立即复制整份 Redis 数据。

Copy-on-Write 的含义是：父子进程共享物理页时，如果某个进程需要修改共享页面，操作系统会创建必要的页面副本，让写入发生在该进程自己的页面上。Redis 父进程继续处理更新，RDB 子进程可以读取 `fork()` 时保留的数据视图。

例如，父子进程原先共享一个包含旧值的页面，父进程准备修改其中的数据，就会触发页面复制。父进程使用包含新值的页面，子进程继续读取旧页面，因此快照能够保留创建子进程时的数据状态。

额外内存主要取决于快照期间被修改的共享页面数量，以及页面粒度、分配器活动和写入分布。修改一个很小的对象也可能导致整个页面复制。大量写入触及大部分共享页面时，总内存可能明显增加，因此生成 RDB 仍需要预留内存。

观察父子进程内存时，还要注意共享页面可能分别计入各自的 RSS，直接相加会重复计算共享部分。可以结合 PSS、容器内存和 Redis 的 COW 相关统计判断实际资源使用情况。

快照使用 Copy-on-Write 的说明见 [Redis Persistence 文档](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)。

### 9. Redis AOF 配置为 appendfsync everysec，服务器突然断电时可能丢失多少数据？为什么？

在后台同步正常完成的情况下，通常可能丢失最近约一秒尚未完成持久化的写操作。这是 `everysec` 按秒安排文件同步所形成的数据窗口。

原因是写入存在不同阶段：命令执行成功后，AOF 内容可能仍在 Redis 的 Buffer 中，也可能已经通过 `write()` 进入操作系统的 Page Cache。只有完成相应的 `fsync()` 或 `fdatasync()`，才能按照存储系统提供的保证确认这些数据已经同步到持久存储。断电会丢失尚未持久化的部分。

“约一秒”需要结合运行条件理解。如果磁盘繁忙，后台文件同步迟迟没有完成，Redis 的追加写入也可能被延迟，实际可丢失的数据窗口就可能扩大。仅进程终止与整台机器断电的影响也不同：操作系统继续运行时，已有的 Page Cache 仍然可能随后写入存储设备。

如果业务需要进一步减少丢失窗口，可以评估 `appendfsync always`，同时接受更高的同步成本。对重要业务状态，还需要结合权威数据来源、复制和恢复机制进行设计。

按秒同步的常见数据窗口见 [Redis Persistence 文档](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)，后台同步和追加写入的延迟条件见 [Redis Latency 文档](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/)。

### 10. 进程和线程有什么区别？资源共享、通信方式、隔离性和创建成本分别如何？

进程通常是操作系统进行资源组织和隔离的基本单位，线程通常是执行代码和参与调度的基本单位。一个进程至少包含一个线程，也可以包含多个线程。

不同进程通常拥有独立的地址空间。某个进程直接修改自己的内存，通常无法影响另一个进程的普通私有内存。同一个进程中的线程则共享 Heap、全局变量、代码和文件描述符等资源，每个线程分别保留自己的程序计数器、寄存器上下文和 Thread Stack。

进程通信可以使用管道、Socket、消息队列和共享内存。RPC 是基于网络通信等基础设施建立的调用方式。线程可以通过共享对象直接交换信息，但多个线程并发读写共享数据时，需要使用锁、原子操作或其他同步机制保证正确性。

创建线程通常比创建拥有独立地址空间的进程开销更低，同一进程内的线程切换也通常省去了地址空间切换的工作。不过具体成本与操作系统、页面数量、调度方式和应用的工作集有关。

进程隔离提供了故障边界。一个进程终止后，其他进程通常仍可以继续运行。同一进程中的线程共享资源，一个线程发生非法内存访问等严重问题，可能影响整个进程。在 Java 中，普通未捕获异常通常会结束对应线程，是否导致整个应用退出，还取决于其他线程和应用的管理方式。

### 11. Linux 中进程切换和同一进程内的线程切换，成本差异主要来自哪里？

两类切换都需要保存当前任务的执行上下文，并恢复下一个任务的上下文，包括必要的寄存器、执行位置、Stack Pointer 和调度信息。Linux 使用 `task_struct` 管理可调度任务，因此保存和恢复执行状态是两类切换共同需要的工作。

同一进程内的线程通常共享同一个 `mm_struct` 和地址空间。它们之间切换时，通常无需切换到另一套用户地址空间。不同进程拥有各自的地址空间，切换时还需要调整内存管理上下文。在 x86 上，这涉及 CR3 和页表相关状态。

TLB 缓存地址转换结果。地址空间发生变化时，部分已有转换可能无法继续使用，从而增加 TLB Miss 和 Page Table Walk。PCID 可以为不同地址空间的转换记录提供标识，减少必要的 TLB 清理；具体行为仍受到处理器特性、内核实现和安全配置影响。相关机制见 [Linux PTI 文档](https://www.kernel.org/doc/html/next/x86/pti.html)。

CPU Cache 还会受到工作集变化的影响。切换后的任务可能访问不同代码和数据，导致原有缓存的命中率下降。普通任务切换通常会保留已有缓存内容，后续访问逐步改变其中的数据。同一进程内的线程如果访问完全不同的工作集，同样可能出现明显的 Cache Miss。

所以，跨进程切换通常增加了地址空间处理及相关缓存成本，但两类切换之间没有固定的耗时倍数。具体情况需要结合工作集、CPU 架构、NUMA 和调度行为测量。

### 12. 线上 Java 服务 CPU 占用过高或者发生 OOM，如何定位和排查？

我会确认异常实例、Java 进程 PID、请求量、CPU 使用率、内存曲线和近期发布情况，同时保留日志和诊断信息。服务可用性受到影响时，可以从异常实例移除流量，结合扩容或限流恢复处理能力，再继续定位原因。

对于 CPU 使用率过高，常见排查顺序是：

1. 在 Linux 上使用 `top -H -p <pid>`，定位持续消耗 CPU 的线程，并记录原生线程 ID。
2. 将线程 ID 转换为十六进制，在 `jstack <pid>` 或 `jcmd <pid> Thread.print -l` 的输出中查找对应的 `nid`。这条关联方法主要用于 HotSpot 平台线程；容器内外的 PID 和线程 ID 需要使用一致的命名空间。
3. 间隔获取几次线程调用记录，确认同一线程是否持续执行循环计算、序列化、正则匹配、自旋等代码。单次记录可能恰好捕获到正常的瞬时工作。
4. 如果主要消耗来自 GC 线程，结合 GC 日志和 `jstat -gcutil <pid> 1000`，检查对象分配速率、回收频率、晋升情况和回收效果。
5. 需要连续观察时，通过 JFR 或 async-profiler 获取 CPU 采样，寻找持续占用较高的调用路径。

对于 OOM，需要按照异常类型选择方向。`Java heap space` 重点检查 Heap 中保留的对象和引用关系；`Metaspace` 重点检查 ClassLoader、动态类生成及类卸载；`Direct buffer memory` 重点检查 Direct Buffer 使用情况；`unable to create native thread` 重点检查线程数量、系统资源限制及 Native Memory。

Heap 问题可以使用 Heap Dump 配合 Eclipse MAT，查看 Histogram、Dominator Tree、Retained Size 和 Path to GC Roots。需要同时区分合理的大量数据、对象生命周期过长，以及持续保留对象的内存泄漏。

如果进程直接被操作系统或容器终止，需要查看内核日志、容器退出原因、`OOMKilled` 和 cgroup 内存限制。此时 JVM 可能没有机会产生 `OutOfMemoryError`。内存预算需要包含 Heap、Metaspace、Direct Memory、Thread Stack、Code Cache 和其他 Native Memory，单独检查 `-Xmx` 无法覆盖整个进程。

### 13. 如何在生产环境获取 Heap Dump？需要提前配置什么，执行时需要考虑哪些影响？

生产环境可以在启动时配置 `-XX:+HeapDumpOnOutOfMemoryError`，并通过 `-XX:HeapDumpPath=/srv/diagnostics` 指定保存目录。目录需要存在、可写，并预留足够空间。这样在符合条件的 JVM OOM 发生时，可以自动保存用于后续分析的 Heap Dump。

这类自动保存也有边界：进程被操作系统直接终止，或者因 Native Memory 和权限、磁盘空间等问题无法完成输出时，文件可能无法生成。需要同时保留进程日志、容器事件和内存监控数据。

进程仍在运行时，可以使用 `jcmd <pid> GC.heap_dump /srv/diagnostics/heap-<pid>.hprof` 主动获取，也可以使用 `jmap -dump:format=b,file=/srv/diagnostics/heap-<pid>.hprof <pid>`。执行前，应使用与目标 JVM 相适配的工具，并检查目标命令的帮助信息和运行权限。

Heap Dump 需要遍历对象并输出大量数据，可能造成 JVM 停顿和较高 I/O 压力。在 JDK 21 的 `jcmd` 中，`GC.heap_dump` 默认还会请求 Full GC；`-all` 可以包含不可达对象并改变这一默认行为，但扫描和输出本身仍然存在成本。

我会选择需要诊断的异常实例，评估是否能够先移除流量，检查可用磁盘空间及文件保存位置，再执行采集。文件中可能包含业务数据，后续需要使用适当的访问权限保存和分析。完成诊断信息采集后，再结合业务情况恢复实例。

命令参数和操作影响见 [JDK 21 jcmd 文档](https://docs.oracle.com/en/java/javase/21/docs/specs/man/jcmd.html)。

### 14. 服务需要持续运行，无法接受明显停顿时，如何排查持续增长的内存和对象分配问题？

我会从已有监控和日志判断增长发生在哪个区域。需要分别观察 Heap、Metaspace、Direct Memory、线程数量和进程 RSS。如果 Heap 基本稳定，但 RSS 持续增长，就需要重点分析 Native Memory、Direct Buffer、线程资源或其他进程内分配。

对于 Heap，重点观察回收后的内存基线和业务负载之间的关系。如果 Old 的回收后占用持续增长，说明长期保留的数据越来越多，需要分析缓存、队列、会话和集合的生命周期。如果内存能够正常回收，但 Young GC 越来越频繁，就需要分析对象分配速率和短生命周期对象的创建路径。两种情况也可能同时出现。

GC 日志可以提供分配、晋升、Mixed GC、Full GC 和 Humongous Object 等信息。例如，大量大数组、图片数据或序列化 Buffer，可能表现为 Humongous 分配活动。应当根据日志和业务请求确认原因，再选择相应的诊断工具。

JFR 可以使用适合持续运行的配置记录一段时间，观察对象分配、GC、线程和相关调用路径。async-profiler 的 Allocation Profiling 可以帮助定位高分配速率的代码。分配采样告诉我们哪些调用不断创建对象，长期保留对象的原因仍需要结合对象生命周期和引用关系分析。

如果启用了 NMT，可以使用 `jcmd <pid> VM.native_memory baseline` 建立基线，随后通过 `VM.native_memory summary.diff` 比较 JVM 跟踪到的 Native Memory 变化。NMT 通常需要在 JVM 启动时开启，统计范围也需要结合对应 JDK 的实现理解。

Class Histogram 和 Heap Dump 都需要评估执行成本。JDK 21 将 `GC.class_histogram` 标为高影响操作，因此无法接受明显停顿时，应优先使用已有指标、GC 日志和适当配置的持续采样，必要时在移除流量的实例上获取对象统计或 Heap Dump。

JFR 配置及诊断命令的影响级别见 [JDK 21 jcmd 文档](https://docs.oracle.com/en/java/javase/21/docs/specs/man/jcmd.html)。

### 15. 介绍实习中风控客诉、申诉智能化审核项目的业务背景、个人职责、执行流程和核心难点

我参与的是 ByteDance 国际支付风控平台下的客诉、申诉自动化审核项目。国际支付服务于直播、电商、广告等业务，风控处理后，部分用户或商家会提交申诉和证明材料，这些案件进入运营审核平台。项目希望让适合自动处理的案件完成机器审核，提高处理效率。

这条链路建立在已有微服务和能力之上，录音中提到涉及约五至六个微服务。我的主要工作是围绕规则配置、上游案件标签和 Agent 参考结果的接入，以及下游工具的编排执行，完成端到端的审核处理。

执行过程可以这样说明：上游提供案件信息、标签和必要的模型识别结果；审核链路读取业务规则，检查字段及命中条件；满足规则要求后，按照配置的顺序调用已经注册的业务工具；最终产生通过、拒绝或转交人工审核等处理结果。

核心难点包括不同业务线的规则差异、规则优先级、Agent 结果的有效性，以及多区域配置发布时的版本管理。运营和产品参与定义业务规则，开发需要把这些规则表达为能够校验和执行的配置，并保证规则条件与后续动作之间的关系明确。

关于模型能力，需要明确个人工作范围：录音支持我参与下游审核链路开发和上游 Agent 结果接入。上游识别 Agent 的训练、内部模型结构和全部识别能力由其他能力提供，转录没有给出我独立负责这些工作的证据。

在进一步讨论系统设计时，可以补充案件标识、规则版本、模型结果版本、动作幂等和执行状态记录。例如，同一案件重复投递时，已经成功执行的业务动作需要能够识别重复请求；同一次审核使用的规则版本需要可追溯。这些属于技术设计补充，转录没有完整记录其具体实现。多区域配置平台的内部同步协议和一致性级别也需要以其实际设计为依据。

### 16. 针对 Agent 审核结果准确率的问题，当时最先想到的简单处理方案是什么？它具体在哪些场景下失效？

按录音中的陈述，最直接的处理思路是沿用已有的规则审核链路，把 Agent 结果视为没有参与有效决策，由既有规则产生通过、拒绝或者转交人工审核等结果。这样可以让原有业务流程继续处理案件。

这个思路遇到的限制主要出现在需要识别证明材料的案件中。录音举的是 Risk Support Case 一类场景，涉及银行卡材料真实性的识别。如果 Agent 没有在规定时间内返回有效结果，规则链路缺少必要的识别依据，相关案件会大量进入人工审核，自动化覆盖下降，人力消耗增加。

录音没有提供某次失效的具体日期、案件数量和单个样本。“失效”能够确认的含义是自动化处理能力不足、更多案件转交人工。关于材料识别的准确率，需要单独进行质量评估。

在技术回答中，可以把结果状态区分为有效结果、超时、执行失败和结果无法确认。超时属于没有获得有效判断，后续流程应当按照明确的人工复核政策处理。模型返回结果后，还需要检查案件标识、输入材料和必要字段，再决定它能否作为规则的输入。这是针对该场景的设计补充。

评估识别质量时，可以把欺诈材料定义为 Positive：Precision 是被识别为欺诈的材料中，真实欺诈材料所占的比例；Recall 是全部真实欺诈材料中，被成功识别的比例。还需要观察正常材料被错误拒绝的比例，以及欺诈材料被遗漏的比例。指标应当来自带有可靠标注的数据集，并按业务线、材料类型和模型版本分别观察。

最后，还需要同时观察模型超时率、转人工比例、处理耗时和单案件成本。模型识别质量、服务可用性和自动化覆盖分别影响业务效果，评估时应当保留各自的统计范围。

### 17. 为什么审核链路采用规则引擎与模型结合的方案？全规则审核和全模型审核分别有哪些限制？

规则引擎适合处理能够明确表达的条件，例如黑名单、金额阈值、字段完整性、案件状态和业务权限。这类判断执行稳定、便于解释，也便于根据配置进行检查和追溯。

图片、证明材料和自然语言说明需要额外的识别与理解能力。例如，银行卡图片可以经过 OCR 或其他图像识别能力提取信息，用户申诉文本可能需要结合历史状态和上下文判断。提取出来的结构化信息仍然可以进入规则引擎，完成确定性的业务检查。

全规则方案在面对大量表达方式和复杂语义时，维护成本可能持续增加。针对每种文本描述分别增加规则，很难覆盖所有变化，还可能导致条件之间的关系越来越复杂。模型能够补充这部分识别和语义处理能力。

全模型方案则需要承担输出波动、错误判断、调用延迟、服务稳定性和成本等问题。涉及资金安全的阈值、权限和业务状态检查，需要保留可以明确验证的执行条件。银行卡和身份信息的处理还需要符合业务的数据访问范围与传输要求。

因此，审核链路可以按照处理职责组合这些能力：规则引擎负责明确的业务条件；模型负责需要识别或语义理解的部分；最终执行前由代码检查结构化结果和业务条件。材料不足、结果冲突或者无法确认的案件进入人工复核，并保留相应原因。

模型是否值得接入，需要结合增加的自动审核覆盖、减少的人工工作量、识别质量和调用成本评估。能够用规则明确处理的案件，直接按照规则执行；需要模型理解的案件，再调用对应能力。

### 18. 最近半年系统学习了哪些新技术？为什么学习 Agent、ReAct、Tool Calling、RAG、结构化输出和流式响应？如何应用这些能力？

最近半年，我重点学习了大模型 Agent 的开发方式，包括 ReAct、Tool Calling、RAG、结构化输出、流式响应和执行状态记录。我关注这些技术，是因为后端业务中有一部分任务需要理解自然语言、读取外部数据，并根据执行结果继续完成处理。

Tool Calling 让模型选择需要调用的工具，并输出相应参数，实际执行由程序完成。ReAct 可以组织多轮工具调用：根据当前任务选择动作，获得工具执行结果，再据此决定后续操作。工程上需要限制可用工具、校验参数、设置执行次数和时间范围，并记录工具结果。

RAG 用于从知识库获取与当前问题相关的资料。例如，审核规范发生变化时，可以对规范进行更新，并在处理案件时检索相关条目，将材料和规范依据提供给模型。规则的标识、适用条件和版本需要保留，强制执行的业务限制仍然由代码和规则配置检查。

结构化输出可以规定审核结论、风险类型、命中的规则和判断依据等字段，便于后续程序使用。程序需要检查字段类型、必填内容和允许的取值；校验未通过时，结束当前自动审核步骤，记录失败原因，按照业务规定进入后续处理。

流式响应可以通过 SSE 等方式展示处理进度，改善长时间任务的交互体验。模型本身的推理耗时还需要通过减少不必要的输入、工具调用和重复执行来优化。记录步骤状态和成功结果，有助于明确哪些工作已经完成；如果要支持进程重启后的恢复，还需要进一步实现持久化状态和动作幂等。

结合实习经历，我能够说明的应用是规则配置、上游 Agent 结果与下游业务工具的协作。转录也提到了个人 Agent 项目与学习实践。MCP、RAG、SSE 和可恢复执行各自在哪个项目中完成了何种实现，转录没有逐项提供验证材料，因此这些技术可以作为学习内容和实现思路展开，个人项目完成范围需要依据对应代码说明。

### 19. 在继续扩展传统规则引擎、采购成熟 SaaS、自建大模型 Agent 审核能力之间，如何进行技术选型？

我会结合问题类型、数据访问要求、业务定制程度、接入成本和长期维护成本进行选择。录音所描述的审核场景与内部用户状态、业务单据及自定义规则联系紧密，因此需要重点考虑内部数据和决策流程能否有效结合。

继续扩展规则引擎，适合大部分条件已经可以清楚表达为结构化判断的情况。它通常具有明确的执行行为和较好的可解释性。需要评估规则数量增长后，维护工作、条件冲突和新增场景的覆盖情况。

采购成熟 SaaS，适合其能力已经满足需求，并且数据使用范围、服务稳定性和定制接口能够满足业务要求的情况。它可以减少部分能力建设工作，但仍需要评估实际案件上的识别质量、内部数据接入、供应商依赖和长期费用。

自建 Agent 审核能力，适合需要调用多个内部系统、组合专有规则、读取内部业务状态，并对执行过程进行管理的情况。这里的建设范围可以包括数据接入、工具编排、规则配置、结果校验和审核执行，模型能力由经过业务认可的服务提供。

在这个项目背景下，规则引擎可以继续负责明确的业务限制，自建审核链路负责连接内部数据、上游模型能力和业务工具。选择自建能力的价值在于这些业务组合能够受控、可追溯，同时需要承担评测、运维和版本管理工作。

如果进一步说明选型过程，应当用相同类型的案件比较覆盖率、识别质量、延迟、费用和维护工作量。录音提到了对 SaaS 和自建方案的考虑，但没有给出供应商名称、报价或者完整选型测试报告；具体比较结果需要相应材料支持。

### 20. 智能化审核项目带来了哪些可以量化的收益？如何评估自动化覆盖、识别质量、审核耗时和规则迭代效率？

按录音中的陈述，项目收益可以从四个方面说明，同时保留每个数字的统计范围。

第一是自动化覆盖。录音中提到，整体案件中超过 20% 进入这条审核链路，进入链路的案件中约 80% 能够完成机器审核，其余转交人工。如果两项指标使用相同的统计期间和案件范围，以 20% 和 80% 估算，整体案件中完成机器审核的比例约为 16%。具体比例需要使用实际案件数量计算。

因此，整体案件进入链路的比例和链路内部完成机器审核的比例，需要分别表达。还应当记录进入链路的案件数、机器审核完成数、转人工案件数，以及最终处理完成数，明确“完成机器审核”的统计定义。

第二是材料识别质量。录音提到了银行卡真实性相关识别能力的准确率约为 92%。这个数字属于录音中的项目陈述，转录没有给出样本数量、正负样本比例、统计期间和是否经过线上复核。它适合描述特定识别任务，整个审核链路的通过、拒绝和人工复核质量还需要单独统计。进一步评估时应当同时提供 Precision、Recall、正常材料误拒比例和欺诈材料遗漏比例。

第三是审核耗时。录音提到，人工审核的 AHT 约为七至八分钟，符合自动处理条件的案件可以在几秒内完成机器处理。人工操作耗时和机器处理耗时需要使用明确的起止点。评估整体效率时，还要计入排队时间、转人工复核时间和异常处理时间，并观察同类案件的平均值及 P95、P99 等分布指标。

第四是规则迭代效率。录音提到，本次需求的开发周期不到一个月；已有配置平台中新增规则后，多区域传播通常可以在几秒内完成。配置传播时间对应规则发布后的同步过程，业务规则讨论、开发、测试、审批和验证则各自需要时间，衡量迭代效率时应当分别记录。

如果需要计算成本收益，可以在同一统计范围内记录减少的人工处理量和工时，再计算新增的模型调用、系统运行和维护费用。转录没有提供完整的成本数据，因此目前能够保留的是上述覆盖、质量、耗时和配置传播指标，以及对应的统计边界。
