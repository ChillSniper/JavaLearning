### 4. TCP 和 UDP 有什么区别？

**时间：** 08:18 提问，08:22—09:05 回答。

**考察内容：** 传输层协议、连接、可靠传输、数据边界和适用条件。

**现场回答与评分：3/10。** 你知道两者位于传输层，也提到了 TCP 建立和关闭连接、UDP 按数据报传输，以及视频等场景。TCP 的传输单位和可靠性机制没有解释准确，“稳定”“安全”等词语没有对应到具体能力。

**分析：** 需要准确使用“字节流、数据报、顺序、重传、流量控制、拥塞控制”等概念。建立连接的过程和可靠传输的机制应分别解释。

**参考回答：**

TCP 面向连接，向应用提供可靠、有序的字节流。它通过序列号、ACK、重传、重复数据处理和接收端重组等机制支持可靠传输，并通过流量控制限制发送方超出接收能力，通过拥塞控制适应网络状态。应用的一次写入可能被分成多次接收，多次写入也可能合并接收，因此应用协议需要定义消息边界。

UDP 按数据报发送，保留消息边界，协议本身提供的能力中没有可靠交付、顺序交付和重传保证。它的协议处理开销较少，适合能够容忍一定数据遗失，或者自行实现所需传输控制的应用，例如实时音视频中的部分传输方案。UDP socket 也可以调用 `connect` 设置默认通信对象，这与 TCP 握手建立连接属于不同机制。

TCP 本身没有加密能力。需要保密和防篡改时，应结合 TLS 等安全机制。最终选择还取决于时延、可靠性、消息大小和应用协议要求。

**改进重点：** 能解释“TCP 一次 write 为什么不对应接收端一次 read”，并准确说出可靠传输由哪些机制支持。

### 5. 长连接为什么通常比短连接请求更快？

**参考回答：**

长连接可以让多个请求复用已经建立的连接，减少反复进行 TCP 握手的网络等待。使用 HTTPS 时，还可以减少重复进行 TLS 握手、密钥协商和证书处理的成本。

### 7. HTTP client 接收响应时，如何判断数据是否接收完整？

**时间：** 09:51 提问，09:57—10:35 回答。

**考察内容：** HTTP 消息边界、传输完整性与客户端读取错误。

**现场回答与评分：3/10。** 你尝试从确认机制、长度字段和结束标记回答，能够接近相关概念，但没有说明 HTTP 的字段名称、具体判定方式和协议版本。转录中的几个英文词语识别不清，不能据此断言你准确说出了 ACK 或 `Content-Length`。

**分析：** HTTP client 需要知道当前响应何时结束。TCP 提供字节流，HTTP 协议负责确定其中一个响应的边界；长度完整与内容防篡改又有各自的检查方式。

**参考回答：**

以 HTTP/1.1 为例，客户端按照协议定义确定响应体边界。使用有效 `Content-Length` 时，需要接收指定数量的字节；采用 `Transfer-Encoding: chunked` 时，需要完整解析每个 chunk，直到零长度 chunk 和后续 trailer section 正常结束。某些响应通过关闭连接标记结束，这种方式对异常截断的识别能力有限。`HEAD`、`204`、`304` 等还有专门的无响应体规则。

如果声明长度尚未读完就遇到连接关闭，或者 chunked 编码不完整，客户端应将其作为不完整响应处理。在 Go 中，拿到 response 之后还需要检查读取 `Body` 时返回的错误，并正确关闭 `Body`；仅仅成功取得 response headers 不代表响应体已经完整读取。

HTTP/2 使用 frame 和 stream 的结束标志描述响应传输，也需要检查 stream 错误。若业务还要求识别内容是否被修改，可以结合 HTTPS、可信来源提供的摘要或签名。业务字段是否合法，需要在解析后继续校验。

**改进重点：** 熟练说出 `Content-Length`、chunked、连接关闭、无响应体规则，并解释正常结束与提前 EOF 的区别。

**参考依据：** [RFC 9112 消息体长度与不完整消息处理](https://www.rfc-editor.org/rfc/rfc9112.html#section-6)。

### 8. 同一个 HTTP 连接，在尚未收到上一次响应时，能否发起新的请求？

**时间：** 10:35 提问，10:43—10:51 回答。

**考察内容：** HTTP 持久连接、pipelining 与 multiplexing 的区别。

**现场回答与评分：2/10。** 你表示应该可以并发，但没有区分协议版本，也明确说明自己并不清楚。

**分析：** 题目限定同一个连接。能否提前发送、响应能否交错传输、客户端是否启用相关功能，都需要分别说明。

**参考回答：**

需要区分 HTTP 版本。HTTP/1.1 支持 pipelining，客户端可以在前一个响应到达之前发送后续请求，但服务端响应仍需保持请求顺序，因此存在 HTTP 层面的队首阻塞。实际客户端通常不启用 pipelining，常见的并发方式是连接池中的多个连接。

HTTP/2 可以在一个连接上建立多个 stream，多组请求和响应的 frame 能够交错传输，并通过 stream ID 区分。它仍然受到底层 TCP 有序交付的影响，TCP 数据遗失可能使多个 stream 等待。

HTTP/3 在 QUIC 上使用独立 stream，进一步减少传输层不同 stream 之间因数据遗失造成的相互等待。面试中如果默认讨论 HTTP/1.1，应同时交代协议能力和客户端实际行为。

**改进重点：** 必须能够分别解释“长连接”“pipelining”“HTTP/2 multiplexing”，并说明各自解决什么问题。

**参考依据：** [MDN HTTP 连接管理与 pipelining](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Connection_management_in_HTTP_1.x)。

### 20. 请介绍消费组和分区 Rebalance 的概念。

**时间：** 20:03 提问，20:08—20:55 回答。

**考察内容：** 消费者协作、分区归属、触发条件和消费进度。

**参考回答：**

以 Kafka 的普通 consumer group 为例，一组使用相同 `group.id` 的消费者共同处理订阅 Topic 的数据。在稳定分配下，同一个 partition 在同一组内只分配给一个成员；一个成员可以负责多个 partition，不同消费组拥有各自的消费进度。

Rebalance 是把 partition 重新分配给消费组成员的过程。成员加入、退出、失联，或者订阅及相关 partition 发生变化，都可能触发分配调整。分区交接时需要处理正在进行的任务和已提交 offset，否则可能出现重复处理或进度错误。

Rebalance 期间的影响与协议和分配策略有关。Kafka 4.x 支持新的 consumer rebalance protocol，实际是否启用需要查看配置，不能把所有版本都描述成全组同时暂停。
