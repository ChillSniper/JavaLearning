### 业务纠错题

题目背景
商家账户体系涉及两个系统：
货款账户系统：维护商家货款账户（seller_account），对外提供账户接口；
保证金账户系统：维护商家保证金账户（deposit_account），内部直接操作本地 SQL。
业务规则：当货款账户余额为负（商家欠款）时，自动用保证金补足——保证金账户系统调用货款账户系统的接口给货款账户增加金额，同时在本地 SQL 调减保证金账户余额。
实现方式：保证金账户系统监听货款账户的 binlog，货款账户表变更推送到消息队列，保证金系统消费消息后执行补足逻辑。binlog 消费入口伪代码如下：

```java
// 伪代码入口：binlog 消息消费（真实实现已简化）
public void onSellerAccountChange(MessageExt msg) {
    // 解析出货款账户变更前/后的 available_amount
    BigDecimal before = rowData.getBefore("available_amount");
    BigDecimal after  = rowData.getAfter("available_amount");
    String sellerId   = rowData.getAfter("seller_id");

    if (after.compareTo(BigDecimal.ZERO) < 0) {
        // 货款账户余额为负：用保证金补足
        // 1) 调货款账户系统接口给货款增加金额（外部 RPC）
        // 2) 本地 SQL 调减保证金账户余额
        depositCoverService.tryCoverNegativeBalance(sellerId);
    }
}
```

消费组开启失败重试，消费失败会重投消息；消息重投时上述代码会完整重跑一遍。

```java
public void tryCoverNegativeBalance(String sellerId) {
    try {
        doTryCover(sellerId);
    } catch (Throwable e) {
        log.error("[AutoCover] 自动补足异常, sellerId={}", sellerId, e);
    }
}

private void doTryCover(String sellerId) {
    // 1. 查货款账户负数欠款金额
    BigDecimal debt = sellerAccountQueryService.queryDebt(sellerId);
    if (debt <= 0) return;

    // 2. 查本地保证金余额，算出可补金额
    BigDecimal depositBalance = depositAccountMapper.queryBalance(sellerId);
    BigDecimal coverAmount = min(depositBalance, debt);
    if (coverAmount < MIN_THRESHOLD) return;

    // 3. 执行补足：外部 RPC 给货款加钱 + 本地保证金调减
    depositCoverService.cover(sellerId, coverAmount);
}
```

【代码 B】补足核心（外部 RPC + 本地 SQL）

```java
public void cover(String sellerId, BigDecimal amount) {
    // 1. 生成幂等单号——每次调用都新生成
    String coverNo = idGenerator.generateXhsSequenceNo(IdKeyEnum.DEPOSIT_COVER);
    // 2. 执行补足：失败自动重试 2 次（共 3 次）
    return coverWithRetry(sellerId, amount, coverNo, 3);
}

private CoverResult coverWithRetry(String sellerId, BigDecimal amount, String coverNo, int retry) {
    for (int i = 1; i <= retry; i++) {
        try {
            return doCover(sellerId, amount, coverNo);
        } catch (Throwable e) {
            if (i == retry) throw e;   // 最后一次重试仍失败则抛出
        }
    }
    throw new RuntimeException();
}

private CoverResult doCover(String sellerId, BigDecimal amount, String coverNo) {
    transactionTemplate.execute(status -> {
        sellerAccountRpcService.increaseAmount(sellerId, amount, coverNo); // 外部 RPC：给货款账户增加金额
        depositAccountMapper.decreaseBalance(sellerId, amount, coverNo);   // 本地 SQL：保证金账户调减
        return null;
    });
    // 发补足成功消息 + 开收据
    coverNotifyService.notifyAndReceipt(sellerId, coverNo);
}
```

业务流程：binlog 触发 → 调货款账户接口加钱（RPC）→ 本地保证金调减（SQL）。

### 7. Agent 输出、业务条件和最终审核结果之间是什么关系？

Agent 输出可以理解为案件的一个判断依据，例如某份凭证是否通过识别。规则把这个结果与业务线、案件类型、名单信息等条件组合，只有满足对应条件，才产生该规则指定的审核决定。因此，凭证识别通过不等于整个申诉一定通过，还需要满足其他业务要求。审核决定产生后，系统继续执行对应动作，并记录动作是否完成，这样才能知道案件最终处于什么状态。

### 12. 配置中除了规则表达式，还包含预期结果和后续动作吗？

配置包含规则适用条件、匹配表达式、命中后对应的审核结果，以及后续需要执行的 actions。actions 与代码中注册的处理能力对应，配置指定调用哪些能力，代码负责执行并检查结果。为了让规则容易维护，还应明确规则标识、优先级、启用状态和版本。原文能够确认的是表达式、审核结果和 actions 的配置化，以及 actions 与代码中注册能力的对应关系；其他字段属于完善方案时需要考虑的内容。

### 13. 配置中的预期结果与实际产出的结果有什么区别？规则未命中时怎么处理？

配置中的结果表示某条规则命中后应该作出的业务决定，例如 approve 或 reject。实际运行时还需要看输入是否完整、规则是否命中，以及后续动作是否成功。如果没有命中可自动处理的规则，案件会进入人工审核；如果规则产生了通过决定，但后续动作调用失败，案件仍然需要记录为处理未完成。评估审核质量还需要人工复核结论，配置中的目标结果本身无法证明决定正确。

### 24. 阅读补足链路代码，说明各个问题的触发条件、后果和改造方案，并给出处理优先级。

这道题需要检查一笔补足业务在异常、重复执行和并发时能否保持资金一致。我会按照资金风险和恢复能力安排处理优先级。

- **最高优先级：外部入账成功、本地扣减失败。** `increaseAmount` 已经增加货款余额，随后本地 SQL 执行失败或事务提交失败，本地事务只能撤销自己管理的数据库修改，外部入账会保留。需要持久化补足单，记录每一步状态，让未完成的业务能够继续处理。
- **最高优先级：同一业务再次进入 `cover` 时更换单号。** 方法内部三次尝试复用 `coverNo`，消息重复投递、进程重启后的恢复或者其他调用重新进入 `cover`，会生成新单号。只要重新查询后仍满足补足条件，下游可能把它当成新的入账。需要让补足单与稳定的业务标识对应，并在所有重试中复用同一单号。
- **最高优先级：本地扣减的幂等性和并发保护没有在题面中得到保证。** `decreaseBalance` 虽然接收 `coverNo`，其 SQL 和唯一约束没有展示。需要检查是否存在按单号去重的资金流水、余额条件及受影响行数校验；如果缺少这些措施，重复执行可能重复扣减，并发操作可能超额使用保证金。
- **最高优先级：最外层捕获异常后正常返回。** `tryCoverNegativeBalance` 仅记录日志，调用它的消费入口无法从异常判断业务失败。如果消费适配层把正常返回视为成功，预期的失败重投就无法触发。应让失败结果传到消费适配层，或者在返回成功之前可靠保存待恢复任务。
- **后续优先级：通知和收据失败会重新执行资金操作。** `notifyAndReceipt` 在本地事务提交之后执行，却仍位于 `coverWithRetry` 的重试范围。它抛出异常时，下一次尝试会再次进入 `doCover`。应将资金处理状态与通知投递状态分别保存，通过本地事件表恢复通知和开收据。
- **后续优先级：补足触发与完成后的核对不足。** 保证金不足或金额低于阈值时直接返回，之后如果只有保证金增加，现有货款账户监听可能没有新的触发机会。需要补充保证金变更触发或待处理任务扫描，并核对两边资金流水及长期未完成的补足单。

改造采用持久化补足单、保证金预留、按单号幂等入账、本地幂等确认和 Outbox 通知的完整流程，具体执行方式见第 28 题。原有代码属于业务伪代码，分析重点是操作顺序和事务范围；未展示的 SQL、RPC 返回定义及框架配置，需要保留条件后再判断实际结果。

### 25. 为什么可能出现货款账户重复增加金额、保证金只扣减一次？请按执行顺序说明。

可以用一个具体过程说明：货款账户余额为 -200 元，保证金有 100 元。第一次处理计算补足金额为 100 元，生成单号 A，外部 RPC 成功后，货款余额变为 -100 元；这时进程在本地扣减成功提交前异常退出，本地保证金仍为 100 元，消息也没有确认。消息重新投递后，代码重新查询到欠款 100 元和保证金 100 元，再次进入 `cover`，生成单号 B。下游接受 B，货款余额增加到 0 元，本地这次扣减 100 元。结果是货款累计增加 200 元，保证金累计只扣减 100 元。

这个过程需要再次进入 `cover`，并且重新查询后仍满足补足条件。如果只在同一次 `coverWithRetry` 内部重试，传递的仍是 A，按题目给定的下游幂等规则，外部入账只会执行一次。还有另一种情况：第一次入账已经把欠款补足，消息重投时 `debt <= 0` 会直接返回，这时不会继续增加货款，但第一次未完成的保证金扣减仍然缺少恢复机会。因此必须保存原补足单的执行进度。

### 26. 下游已经通过 `coverNo` 保证幂等，链路还可能有什么问题？

下游幂等只保证同一 `coverNo` 对应的外部入账重复提交时只生效一次。链路还需要保证同一笔业务始终使用这个单号，并检查本地扣减是否也按该单号去重。例如，外部入账和本地扣减都成功以后，`notifyAndReceipt` 抛出异常，重试仍然使用相同的 `coverNo`，外部入账会去重；如果本地扣减没有幂等控制，就可能再次扣减保证金。题面没有展示 `decreaseBalance` 的内部实现，所以需要核实其唯一约束和资金流水处理。

完整的幂等设计还要核对商家、账户、币种和金额等参数，同一个单号携带不同业务参数时应当拒绝，并让幂等记录的保留时间覆盖业务恢复和对账周期。同一单号重试及参数一致性的要求，也可参考 [Stripe 幂等请求说明](https://docs.stripe.com/api/idempotent_requests)。本题下游行为以面试官给定的条件为准。

### 27. `coverNo` 在重试循环之前生成，是否意味着所有重试和消息重投都会使用同一个单号？

这个位置只能保证一次 `cover` 调用中的重试复用同一个单号。`coverWithRetry` 的循环每次都接收同一个 `coverNo`；但消息重投会重新经过 `tryCoverNegativeBalance`、`doTryCover` 和 `cover`，只要前面的判断没有返回，就会再次调用单号生成器。进程重启以后，单靠方法局部变量也无法找回原单号。

我会在执行资金操作前持久化补足单，并通过稳定的业务标识找到它，例如能够唯一标识一次补足操作的业务事件标识。重复请求先查询已有单据，读取相同的单号、金额和状态继续处理。商家编号本身无法区分同一商家后续的新业务；消息标识也只能覆盖对应消息的重复投递。对于不同事件同时触发同一商家补足，还需要通过账户维度的进行中任务约束来协调。

### 28. 外部 RPC 与本地 SQL 为什么存在分布式事务问题？怎样保证两个账户的资金一致性？

在题目给定的普通 RPC 和本地数据库事务下，`transactionTemplate` 管理本地 SQL 的提交与撤销，外部账户服务有自己的事务。即使 RPC 调用写在事务回调里面，也需要外部服务明确参与同一个分布式事务协议，才能获得统一的提交控制。外部入账已经成功后，本地事务失败会留下两个系统处理进度不同的状态。Spring 的事务回调和事务管理器关系见 [编程式事务说明](https://docs.spring.io/spring-framework/reference/data-access/transaction/programmatic.html)。

针对这道题，我会采用可恢复的补足单流程，允许短暂的处理中状态，并保证每笔资金最终有对应流水：

1. **创建或获取补足单。** 消费事件时通过稳定业务标识获取单据，记录 `coverNo`、商家、两个账户、币种、金额和状态。对同一商家同一币种设置数据库层面的进行中任务唯一约束，遇到已有任务就恢复它，完成后再判断剩余欠款。
2. **在本地事务中预留保证金。** 校验可用余额足够，把本次需要的金额从可用余额转为冻结金额，同时保存补足单状态和待执行任务。余额更新、冻结流水及任务记录一起提交。没有预留成功就终止这次资金执行，让调用方明确感知失败。
3. **在本地事务外调用货款账户服务。** 使用持久化的 `coverNo` 和固定请求参数执行入账。超时后保存待确认状态，通过原单号查询结果或按原单号重试；持续扫描未完成任务，进程重启后也能恢复。资金已被冻结，其他任务无法重复使用这部分保证金。
4. **确认货款账户的实际入账金额。** 如果业务要求严格按当前欠款补足，货款服务需要在自身事务内检查欠款，并原子完成限额入账和幂等结果保存，返回实际入账金额。实际金额可以小于请求预留金额。同一单号再次调用时返回已经保存的结果。题目当前只展示了普通增加金额接口，这项要求需要补充到接口实现中。
5. **在本地事务中完成资金确认。** 按实际入账金额消耗冻结保证金，把未使用部分释放回可用余额，同时写入唯一资金流水、更新单据为完成，并写入通知事件。通过单据状态条件和流水唯一约束保证重复确认只生效一次。如果远端明确拒绝且能保证该单号后续无法再入账，就取消本地预留；结果未知时保留冻结并继续核实。
6. **发送通知并持续核对。** Outbox 任务负责投递完成事件，通知和收据按业务单号去重。定期按照 `coverNo` 核对远端入账、本地扣减和单据状态，对长期未完成或金额不一致的记录告警并安排处理。已完成的单据需要满足两个账户的金额变化一一对应，处理中的差异必须能够由冻结资金和执行状态解释。

远端超时表示调用结果尚未确定，不能直接释放冻结资金，也不能立即生成新单号重做。简单查询到“暂未找到”同样需要考虑原请求仍在执行的情况。两阶段提交需要相关资源支持协调协议；业务 TCC 则需要完整的 Try 预留、Confirm 确认和 Cancel 取消接口，单独增加余额检查无法提供这些能力。

### 29. 除了幂等和两个账户的更新，还有哪些执行失败场景需要考虑？

最直接的场景是资金操作已经完成，通知或开收据失败。题目会重新执行整个 `doCover`，因此需要将资金确认和待通知事件一起保存在本地事务中，再独立重试通知；如果发送通知后进程退出，接收方还要能够识别重复事件。通知成功与收据成功也应当分别记录，避免其中一个动作失败后反复执行已经完成的动作。

另外，当前入口只判断变更后的余额小于零，只要仍然欠款，其他字段更新也可能触发一次检查，需要确认事件过滤和业务去重。欠款、保证金不足或者低于阈值的案件，应有后续重新检查机制，例如保证金增加时触发或者扫描待处理记录。RPC 超时要进入待确认状态，余额不足等业务条件也需要明确处理结果。对不可恢复错误应及时终止并报告，避免把所有异常都放进相同的重试循环。

### 30. `doCover` 的异常能否向上传递？最后一次重试的 `throw e` 与外层 `catch` 会怎样影响消息重投？

可以沿调用层级直接判断：`doCover` 内的 RPC 或 SQL 如果抛出异常，异常会进入 `coverWithRetry` 的 `catch`；前面的尝试继续循环，最后一次执行 `throw e`，把异常交给外部调用者。`notifyAndReceipt` 抛出的异常也会进入这个循环。随后异常到达 `tryCoverNegativeBalance`，这里的 `catch (Throwable e)` 只记录日志，方法正常返回，因此异常没有继续传到 `onSellerAccountChange`。按常见的消费适配方式，如果正常返回被确认成功，这次业务失败就无法触发失败重投。具体确认方式仍需查看消费框架的适配代码。[RocketMQ 消费重试文档](https://rocketmq.apache.org/docs/featureBehavior/10consumerretrypolicy/)说明了失败状态、异常及超时等重试条件。

`RuntimeException` 表示 Java 的运行时异常类别，具体可能是参数问题、空引用、业务执行失败等，不能只凭类名推断为超时。Spring `TransactionTemplate` 的常规执行分支会在回调异常时处理事务并继续向外传播异常，参见其 [源码](https://raw.githubusercontent.com/spring-projects/spring-framework/main/spring-tx/src/main/java/org/springframework/transaction/support/TransactionTemplate.java)。此外，如果 Mapper 用受影响行数为 0 表示更新未完成，调用方需要主动检查这个返回值；没有异常也可能没有完成业务操作。

### 31. 同一个商家会不会出现多个补足任务并发执行？会产生什么问题？

面试官明确确认了同一商家存在并发。比如货款欠款 100 元，保证金有 200 元，两个任务同时查询到这些数据，各自计算补足 100 元，并生成不同单号。即使保证金足够让两次扣减都成功，货款也可能被补成正数，这说明保证金充足检查无法单独防止同一笔欠款被两个任务同时补足。如果保证金只有 100 元，还会同时出现两次操作竞争同一余额的问题。处理上需要账户维度的任务协调、本地原子预留，以及货款系统对当前欠款的原子检查。下游按单号幂等能够处理同一任务的重复请求，两个不同单号之间仍需要业务并发控制。

### 32. 查询时保证金有 100 元，执行时已经被其他任务扣减为 0，现有逻辑能够阻止错误补足吗？

前面的查询与 `min` 计算无法阻止。任务 A 查询到保证金 100 元并计算补足 100 元；任务 B 把保证金扣减到 0；任务 A 继续使用之前计算的金额调用外部 RPC，货款就可能先增加 100 元。后续 SQL 能否拒绝扣减，要查看 `decreaseBalance` 的实际实现：如果有余额条件且检查更新结果，可以阻止保证金继续减少，但已经发生的外部入账仍需要恢复处理。

因此应在外部入账前完成本地资金预留，把余额足够的条件写入原子更新，并验证受影响行数；也可以在短事务内使用 `SELECT ... FOR UPDATE` 读取并更新同一条账户记录。普通查询无法保证后续更新之前数据一直不变，相关机制见 [MySQL 锁定读取说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)。原题没有展示数据库约束，能够确定的是前置查询检查不足，最终是否允许账户变负还需要查看 SQL。

### 33. `min(depositBalance, debt)` 和 `MIN_THRESHOLD` 分别有什么作用？能否解决并发问题？

`min(depositBalance, debt)` 计算本次最多能够补足的金额，保证它在查询时没有超过保证金余额和欠款金额。`MIN_THRESHOLD` 用于限制过小的补足操作，例如余额不足或金额小于业务允许的最小值时直接返回；具体阈值和设置原因需要业务确认。它们都基于已经读取的数据进行普通判断，无法保留资金，也无法阻止其他任务随后修改账户。并发条件必须在真正预留或更新资金时再次校验，并且让校验与修改一起完成。金额低于阈值时，还需要规定剩余欠款后续怎样处理。

### 37. 两个非空链表按逆序存储两个非负整数，怎样返回它们相加后的链表？请说明思路并实现。

链表从头到尾依次表示个位、十位、百位，可以直接按照加法的计算顺序遍历。每次取两个当前位置的数字，加上上一位进位 `carry`，用 `sum % 10` 创建结果节点，再用 `sum / 10` 更新进位。某个链表提前结束时，将它在后续位置的数字视为 0。循环条件是任意链表还有节点，或者还存在进位，这样能够处理长度不同和最后多出一位的情况。时间复杂度为 `O(max(m, n))`，结果链表占用 `O(max(m, n))` 空间，除结果以外的辅助空间为 `O(1)`，输入链表保持不变。

```cpp
struct ListNode {
    int val;
    ListNode* next;

    ListNode(int value = 0, ListNode* nextNode = nullptr)
        : val(value), next(nextNode) {}
};

class Solution {
public:
    ListNode* addTwoNumbers(ListNode* l1, ListNode* l2) {
        ListNode dummy;
        ListNode* tail = &dummy;
        int carry = 0;

        while (l1 != nullptr || l2 != nullptr || carry != 0) {
            int sum = carry;
            if (l1 != nullptr) {
                sum += l1->val;
                l1 = l1->next;
            }
            if (l2 != nullptr) {
                sum += l2->val;
                l2 = l2->next;
            }

            tail->next = new ListNode(sum % 10);
            tail = tail->next;
            carry = sum / 10;
        }

        return dummy.next;
    }
};
```

例如，`[2, 4, 3]` 表示 342，`[5, 6, 4]` 表示 465，结果是表示 807 的 `[7, 0, 8]`。在线题目如果已经提供 `ListNode` 定义，提交时只保留 `Solution`。

### 38. 这道题需要反转链表吗？头节点表示哪一位？长度不同和最后的进位怎样处理？

这道题的头节点就是个位，因此直接从头节点相加即可。比如 `[9, 9]` 与 `[1]` 相加，个位得到 10，写入 0 并产生进位 1；十位是 9 加进位 1，继续写入 0 并保留进位 1；两个链表都结束后，还需要增加值为 1 的节点，得到 `[0, 0, 1]`。所以只有当两个链表都结束且进位为 0 时，计算才完成。用 `l1 != nullptr || l2 != nullptr || carry != 0` 可以统一处理这些情况。
