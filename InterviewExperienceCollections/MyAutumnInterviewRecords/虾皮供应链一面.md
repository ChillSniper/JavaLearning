## System design 完整参考方案

### 题目字段与补充条件

业务字段包括：`tn`、`status`、`receiver_name`、`receiver_phone`、`receiver_address`、`sender_name`、`sender_phone`、`sender_address`、`created_at`、`channel`。

- 每天新增 100 万单，订单保存一年；以下按最近 365 天估算。
- 高频调用只提供 TN，应能够找到订单并更新状态。
- 低频查询提供渠道与下单时间范围，可能需要大量导出。
- 渠道可能在订单创建后确定；TN 和下单时间在本设计中保持不变。
- TN 的长度、字符含义、大小写和空白是否有业务意义，需要确认。示例按 UTF-8 原始字节保存，允许 1—256 字节；不自动修改大小写或删除空白。
- 查询索引允许短时间同步延迟；结算导出前需要确认索引已经同步到业务要求的截止位置。严格即时一致的要求会影响事务与部署设计，需要在设计时确认。

最近 365 天、TN 与下单时间保持不变、TN 长度与编码、索引同步延迟等具体约定属于参考方案的设计条件，需要由业务确认。

### 容量计算与表数量

1. 年订单量：`1,000,000 × 365 = 365,000,000`，约 3.65 亿条。
2. 采用本题每表 2000 万行的目标，理论最少 `ceil(365,000,000 / 20,000,000) = 19` 张主表。
3. 建立 30 张主表，平均每张约 1217 万行；按 1.5 倍年量估算，每张约 1825 万行。该计算假定 TN Hash 分布较均匀，仍需检查真实数据分布。
4. 31 天的索引记录约 3100 万条。每月建立 4 张索引表，平均每张约 775 万条；按 1.5 倍月量估算，每张约 1163 万条。
5. 最近 365 天通常跨越 12 或 13 个自然月，应允许最多 13 组月表，即最多 52 张活动索引表。30 张主表加 52 张索引表，共最多 82 张核心活动表；提前创建的未来月表和 Outbox 表另计。

存储空间也需要单独计算。仅作估算，假设主表平均每单含索引约 1000 字节，查询表每单含索引约 150 字节，则一份数据约为 `3.65 亿 × 1150 = 419.75 GB`，使用十进制单位。若保留一主两副本，再预留一倍可用空间，总规划约为 `419.75 × 3 × 2 = 2518.5 GB`，约 2.52 TB；日志、Outbox、备份和导出数据需要额外估算。这些行大小及副本数量均为示例条件，正式规划应根据样本测量。

平均新增速率约为 `1,000,000 / 86400 = 11.57` 单每秒。假设每单有 `k` 次状态更新，则平均更新速率约为 `11.57 × k`；峰值、查询流量、批量导出和复制负载还需要独立测量。

分表数量确定以后，物理实例根据容量与负载分配。一个可说明路由的示例是：30 张主表分到 3 个逻辑库，每库 10 张；索引月表组通过配置映射到对应实例。3 个逻辑库是否需要独立机器，应依据资源与压测结果确定。

### 订单主表

以下为一张主表的 DDL 示例，其他主表采用相同结构，表名为 `logistics_order_00` 至 `logistics_order_29`。

```sql
CREATE TABLE logistics_order_00 (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    tn VARBINARY(256) NOT NULL,
    status INT NOT NULL,
    receiver_name VARCHAR(128) NOT NULL,
    receiver_phone VARCHAR(32) NOT NULL,
    receiver_address VARCHAR(512) NOT NULL,
    sender_name VARCHAR(128) NOT NULL,
    sender_phone VARCHAR(32) NOT NULL,
    sender_address VARCHAR(512) NOT NULL,
    created_at DATETIME(6) NOT NULL,
    channel INT NULL,
    version BIGINT UNSIGNED NOT NULL DEFAULT 0,
    updated_at DATETIME(6) NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_tn (tn),
    KEY idx_created_id (created_at, id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

- `id` 只作为分表内部的主键，TN 是业务唯一标识。采用较短主键可以控制二级索引中的主键占用。
- `tn` 使用 `VARBINARY`，应用统一使用 UTF-8 字节路由、读写和比较，避免字符比较规则与路由判断不同。
- 电话使用字符串，保留国家区号、前导零等业务信息。名称、地址和电话的长度均为示例，需要由业务限制确认。
- 渠道尚未确定时允许 `NULL`，后续赋值不会改变主表位置。
- `created_at` 固定表示下单时间，统一保存 UTC；月份计算也使用同一时区。需要按当地月份结算时，应把业务区间换算为 UTC 边界后查询。
- `version` 用于应用侧的并发更新检查。`idx_created_id` 用于分批寻找过期订单，控制每次清理范围。

同一 TN 在固定路由下总会进入同一主表，该表的 `uk_tn` 阻止重复记录。Hash 相同的不同 TN 可以进入同一张表，表内仍按完整 TN 判断身份。这个唯一性说明以所有写入都遵守同一路由为条件。

### 渠道时间查询索引表

表名采用 `order_search_YYYYMM_00` 至 `order_search_YYYYMM_03`。月份来自订单下单时间，末尾编号来自 TN Hash。

```sql
CREATE TABLE order_search_202610_00 (
    tn VARBINARY(256) NOT NULL,
    channel INT NOT NULL,
    created_at DATETIME(6) NOT NULL,
    projection_version BIGINT UNSIGNED NOT NULL,
    PRIMARY KEY (tn),
    KEY idx_channel_time_tn (channel, created_at, tn)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

查询表只保存找到订单所需的信息，名称、电话和地址保存在主表。`projection_version` 表示最近一次已应用的查询字段版本，用于处理重复和先后顺序不同的同步事件。

月份选择与联合索引各有作用：应用根据时间范围确定需要访问的月表组；表内使用渠道等值条件和下单时间范围定位 TN。`tn` 提供相同时间记录之间的稳定排序。

同一个热门渠道的订单按照 TN 继续分布到 4 张索引表，单月查询访问这 4 张表。渠道尚未确定的订单保存在主表，赋予渠道后再加入相应查询表。

### 路由伪代码

下面的 Python 片段是路由规则示例，可独立执行。所有服务必须采用相同的编码、Hash、截取方式和表名规则。

```python
from datetime import datetime, timedelta
from hashlib import sha256


def stable_hash(tn: str) -> int:
    if not isinstance(tn, str):
        raise TypeError("tn must be a string")
    data = tn.encode("utf-8")
    if not 1 <= len(data) <= 256:
        raise ValueError("tn must contain 1 to 256 UTF-8 bytes")
    return int.from_bytes(sha256(data).digest()[:8], "big")


def order_route(tn: str) -> tuple[int, str]:
    slot = stable_hash(tn) % 30
    return slot // 10, f"logistics_order_{slot:02d}"


def search_route(tn: str, created_at: datetime) -> str:
    if created_at.utcoffset() != timedelta(0):
        raise ValueError("created_at must use UTC")
    slot = stable_hash(tn) % 4
    return f"order_search_{created_at:%Y%m}_{slot:02d}"


def search_tables(start: datetime, end: datetime) -> list[str]:
    if start.utcoffset() != timedelta(0) or end.utcoffset() != timedelta(0):
        raise ValueError("query boundaries must use UTC")
    if start >= end:
        raise ValueError("query interval must be nonempty")
    month = start.replace(day=1, hour=0, minute=0, second=0, microsecond=0)
    tables = []
    while month < end:
        tables.extend(f"order_search_{month:%Y%m}_{slot:02d}" for slot in range(4))
        if month.month == 12:
            month = month.replace(year=month.year + 1, month=1)
        else:
            month = month.replace(month=month.month + 1)
    return tables
```

表名只能由服务端规则生成；月份范围还需检查保存期限、允许跨度和已创建表清单。SQL 参数用于业务值，表名从可信配置选取。

### 高频 TN 查询与状态更新

1. 根据 TN 得到逻辑库与主表名。
2. 使用完整 TN 查询唯一记录。
3. 状态更新需要先验证业务允许的状态变化，再结合版本更新并检查影响行数。

```sql
SELECT id, tn, status, channel, created_at, version
FROM logistics_order_00
WHERE tn = ?;

UPDATE logistics_order_00
SET status = ?, version = version + 1, updated_at = ?
WHERE tn = ? AND version = ? AND status = ?;
```

上面使用具体表名展示语句形状，运行时按路由选择表。状态变化必须依据业务状态机检查，状态编号大小无法表达所有先后关系。

版本检查可以处理并发竞争。承运商通知还可能重复或延迟，需要结合事件标识、承运商事件序号或业务时间规则判断；更新零行时应明确区分订单缺失、版本冲突、重复通知和非法状态变化。版本检查本身不能确定外部事件先后关系。

InnoDB 根据索引和事务进行记录锁定，表行数增加不会自动等同于所有写入都锁定整张表。索引、SQL 与事务范围需要具体检查。[MySQL InnoDB Locking](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking.html)

### 渠道加时间的列表查询

查询区间使用 `[start, end)`。例如查询 UTC 2026 年 9 月，访问 9 月的 4 张索引表，时间条件为 `2026-09-01 00:00:00` 至 `2026-10-01 00:00:00`，后一个边界不包含在内。

```sql
SELECT created_at, tn, projection_version
FROM order_search_202609_00
WHERE channel = ?
  AND created_at >= ?
  AND created_at < ?
ORDER BY created_at, tn
LIMIT ?;
```

1. 计算时间范围涉及的月份，每个月访问 4 张索引表。
2. 每张表使用 `(created_at, tn)` 游标分批读取；后续页增加下面的游标条件。
3. 对多张表的有序结果进行归并，保留每个分表读取进度。
4. 将本批 TN 按 30 个主表位置分组，每张主表使用一条或有限批次的 `WHERE tn IN (...)` 查询完整订单。
5. 按索引结果次序组织输出，并检查主表中的当前渠道、下单时间是否符合要求。

```sql
SELECT created_at, tn, projection_version
FROM order_search_202609_00
WHERE channel = ?
  AND created_at >= ?
  AND created_at < ?
  AND (created_at > ? OR (created_at = ? AND tn > ?))
ORDER BY created_at, tn
LIMIT ?;
```

同一时间可能有很多订单，游标同时包含时间和 TN。渠道变更造成的索引同步延迟需要明确处理：主表复核可以排除已经不匹配的结果，缺少的新索引记录仍需要等待同步或通过完整性检查确认。

大批量导出使用后台任务、受控批次和进度记录，避免一次加载全部订单。结算需要固定截止时刻的内容时，应生成结算快照并记录版本，分批读取当前订单无法自动提供跨多个数据库的一致历史快照。

### 主表与查询表的数据同步

订单主表保存业务事实，查询表保存便于查找的字段。本方案使用 MySQL Outbox：业务变更与待发送事件在同一个主库事务中写入，后台任务可靠地处理事件。这里增加的机制属于参考设计，转录没有考察完整同步实现。

每个主库可以配置相应的 Outbox 表，下面给出核心字段示例：

```sql
CREATE TABLE order_outbox (
    event_id VARBINARY(128) NOT NULL,
    tn VARBINARY(256) NOT NULL,
    channel INT NOT NULL,
    order_created_at DATETIME(6) NOT NULL,
    projection_version BIGINT UNSIGNED NOT NULL,
    delivery_state INT NOT NULL DEFAULT 0,
    next_attempt_at DATETIME(6) NOT NULL,
    created_at DATETIME(6) NOT NULL,
    PRIMARY KEY (event_id),
    KEY idx_delivery (delivery_state, next_attempt_at, event_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

- 创建时已经确定渠道，或者后续赋予、变更渠道时，在更新订单的同一个事务中写入事件。渠道变更继续使用原下单月份与原 TN 分组，因此索引记录位置保持稳定。
- 事件包含渠道、下单时间、TN 和业务版本。消费者按搜索路由定位索引表，在一个事务内确认版本，插入新记录或应用更高版本；并发首次插入需要通过主键唯一约束与事务重试完成。
- 同一版本重复处理不再次改变结果，较早版本到达时不覆盖新版本。普通状态更新不改变查询字段，因此无须同步修改查询表。
- 消费成功后再确认发送进度。处理失败时保留事件和错误，按受控次数重试并告警；主表已经提交的事件由后台继续处理。
- 订单过期后，过期事件直接终止处理，后台不能因为旧事件重新创建已清理月份的表。本方案约定已赋值渠道可以变更为另一个渠道；如果允许撤销渠道，需要增加版本化删除事件及相应记录。
- 监控事件等待时间、待处理数量、失败数量，并定期根据主表与查询表核对缺少记录、冗余记录及字段差异。

导出前，应确认相关主库在业务截止时刻以前提交的索引事件均已处理；有缺少记录时修复并重新检查。导出内容的历史一致性还应由结算快照或明确的业务冻结规则保障。

### 保存期与扩容

索引表按月份管理。只有整个月都超出保存范围，且没有仍需使用它的业务任务时，才可以清理整个表组；边界月份按准确时间条件分批清理。主表按 TN 分组，需要使用 `(created_at, id)` 分批寻找并删除过期记录，同时控制每次事务大小。

30 张主表的取模规则需要保持稳定。需要增加容量时，可将已有逻辑分表迁移到其他实例，并更新表到实例的映射；如果必须增加逻辑分表数量，需要设计包含数据迁移、旧新路由版本和切换检查的完整流程。仅修改取模数量会改变已有 TN 的目标位置。

### 面试时的完整表达

一天 100 万单，保存一年约 3.65 亿条。按每张表 2000 万行的目标，至少需要 19 张，我选择 30 张订单主表，平均每张约 1217 万行。主表通过稳定的 TN Hash 取模路由，并建立 TN 唯一索引，高频查询和更新只访问一张主表。

按渠道和时间查询时，我增加只保存渠道、下单时间与 TN 的查询表。它按照下单月份组织，每个月继续按 TN 分成 4 张表，每张平均约 775 万条，并建立渠道、时间、TN 的联合索引。查询时选取相关月表，取得 TN，按主表位置分组并批量读取完整订单。

主表与查询表通过同一业务事务产生的 Outbox 事件同步，处理重复与先后顺序不同的事件，监控同步延迟。对账导出需要检查索引完整性，并根据业务要求固定结算结果。容量还需要计算行大小、索引、增长、副本与备份，状态更新则需要并发检查和业务状态机校验。
