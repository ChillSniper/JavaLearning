### 2. Java 里面常用的集合类型有哪些，它们是否线程安全？

**参考回答：**

我会按 List、Set、Queue 和 Map 四类介绍。其中 Map 属于集合框架，但不继承 Collection 接口。

| 类别 | 常见实现与特点 | 线程安全情况 |
| --- | --- | --- |
| List | ArrayList 基于动态数组；LinkedList 基于双向链表 | 默认不安全；CopyOnWriteArrayList 适合读多写少 |
| Set | HashSet 用于去重；TreeSet 维护排序 | 默认不安全；可选 ConcurrentHashMap.newKeySet()、ConcurrentSkipListSet |
| Queue / Deque | ArrayDeque 用作队列或栈；PriorityQueue 是优先队列 | 默认不安全；可选 ConcurrentLinkedQueue、ArrayBlockingQueue、LinkedBlockingQueue |
| Map | HashMap、LinkedHashMap、TreeMap | 默认不安全；可选 ConcurrentHashMap、ConcurrentSkipListMap |

Vector、Hashtable 是较早的同步容器，Collections 也提供同步包装。但**单个方法线程安全，不代表一串方法组成的业务操作具有原子性**。例如“先判断 key 不存在，再写入”应优先使用 `putIfAbsent` 等原子操作；同步包装容器的遍历也需要按其约定加锁。

**现场复盘：** 仅列出 LinkedList、HashMap 和 ConcurrentHashMap，缺少分类框架。先说类型，再举实现，再回答线程安全，比临时回忆名称更完整。

### 3. HashMap 的底层数据结构是什么？

**参考回答：**

OpenJDK 8 的 HashMap 主要由数组、链表和红黑树组成。数组的每个位置是一个桶；key 经过哈希扰动后，通过 `(n - 1) & hash` 定位桶，同一个桶里的冲突元素使用链表或树组织，再结合 `equals` 判断是否为相同 key。

扩容与树化是两回事。扩容通常由总元素数量超过“容量乘负载因子”触发，默认负载因子为 0.75。树化则针对某一个桶冲突过多的情况，还要求数组容量至少达到 64，否则优先扩容。

常说“树化阈值为 8”，但不能说整个 map 有 8 个元素就变成树。若追到 OpenJDK 8 的普通 `put` 路径，桶中已有至少 8 个节点再插入新节点时会尝试树化；不能把阈值名称机械理解成所有操作都在第 8 个节点立刻树化。相关分支可对照 [OpenJDK 8 HashMap 源码](https://raw.githubusercontent.com/openjdk/jdk8u/master/jdk/src/share/classes/java/util/HashMap.java)。

哈希分布良好时，查询和插入的平均复杂度接近 O(1)；扩容一次需要 O(n)。链表桶查找是 O(k)，红黑树结构可改善严重碰撞时的查找，常见分析为 O(log k)，但对哈希相同且无法有效比较的特殊 key，不能承诺任意查找都严格是对数复杂度。这里 k 是单桶节点数。

**现场复盘：** 数据结构说对了，但漏掉容量 64 的条件，也把整体元素数、桶内元素数和查询复杂度混在了一起。HashMap 本身不提供并发安全保障。

### 4. synchronized 有什么作用，怎样使用？

**参考回答：**

synchronized 用来保护多个线程共同访问的临界区。线程进入临界区前需要获得指定对象的监视器锁，同一时刻只有一个线程可以持有这把锁，从而让遵守同一加锁规则的操作互斥执行。

它不只有互斥作用。同一个监视器的解锁先行发生于后续对这个监视器的加锁，因此前一个线程在释放锁前的写入，对后续获得同一把锁的线程具有可见性。它还是可重入锁，线程正常返回或异常退出同步区域时都会释放锁。

例如多个线程执行 `count++`，它包含读取、加一、写回多个步骤，可以用同一个锁保护这段操作。仅仅把 count 声明为 volatile，不能保证自增操作的原子性。

**现场复盘：** 原回答“防止一个变量同时被多个线程持有”不准确。多个线程仍然可以持有对象引用，关键是对共享状态的操作是否遵守同一把锁。锁也不会阻止未加锁的代码直接访问该状态。

### 5. synchronized 可以用在哪些位置，不同用法锁住的对象是什么？

**参考回答：**

synchronized 可以修饰实例方法、静态方法，也可以用于同步代码块，**不能直接修饰字段或局部变量**。

| 写法 | 锁住的对象 |
| --- | --- |
| `public synchronized void update()` | 当前实例 `this` |
| `public static synchronized void updateAll()` | 声明该方法的类对应的 Class 对象 |
| `synchronized (lock) { ... }` | 括号中的非 null 对象 `lock` |

两个不同实例的同步实例方法，通常使用不同的锁；同一类的静态同步方法共享该类的 Class 对象锁。实例同步方法与静态同步方法也不会自动互斥，因为锁对象不同。同步代码块适合缩小临界区，通常使用专门且引用稳定的私有锁对象。

**现场复盘：** 面试官是顺着现场“修饰变量”的错误继续追问，不能把这个错误前提写成知识点。方法锁对象的规则见 [Java 语言规范 synchronized 方法](https://docs.oracle.com/javase/specs/jls/se21/html/jls-8.html#jls-8.4.3.6)。

### 6. 什么是反射，它有哪些优缺点和应用场景？

**参考回答：**

反射是在运行时获取类的信息，并按需要创建对象、访问字段或调用方法的机制。普通调用通常在编译期就知道目标类型和方法，而反射允许程序根据运行时的类名、配置或注解决定操作对象。

它适合框架级的通用能力，例如依赖注入、对象与数据的映射、序列化、测试框架发现测试方法等。优点是灵活、减少对具体业务类的硬编码；缺点是部分错误从编译期推迟到运行期，调用关系不直观，也可能增加访问检查和动态调用成本。

反射并不等于随意访问私有成员。默认仍有访问控制，尝试放宽访问还受 Java 模块等机制限制。业务代码已经知道类型时，直接调用通常更清晰，也更容易让编译器检查。

**现场复盘：** “不用 getter 就能更快捷地访问私有变量”不是反射的主要优势，更不能暗示性能更快。核心价值是运行时的通用性和动态性。

### 7. 动态代理有哪些应用，常见实现方式是什么？

**参考回答：**

动态代理是在运行时生成代理对象，让调用先经过代理，再按需要执行目标逻辑。这样就可以统一加入日志、鉴权、事务、监控等逻辑，而不必在每个业务方法里重复编写。RPC 客户端也可用代理把本地接口调用转换为远程请求。

常见方式有 JDK 动态代理和基于子类的代理。JDK 动态代理围绕接口工作，通过 InvocationHandler 处理方法调用；以 CGLIB 为代表的子类代理继承目标类并拦截可重写方法，因此无法用这种方式代理 final 类，也不能覆盖 final 或 private 方法。

以基于代理的 AOP 为例，外部通过代理进入方法时可以执行增强；目标对象内部直接通过 `this` 调用自己的另一个方法，通常不会重新经过代理，因此可能绕过事务等增强。这是代理调用路径的边界，不是所有 AOP 实现的共同限制。

**现场复盘：** 现场想到了 AOP，但没有讲清“代理怎样插入调用链”以及接口代理、子类代理的区别。依赖注入与动态代理可以配合使用，但不是同一个概念。

### 8. Java 的类加载机制是怎样的？

**参考回答：**

通常按加载、链接、初始化介绍，其中链接包括验证、准备和解析。

- **加载：** 获取类的二进制表示，建立 JVM 内部的类信息和对应的 Class 对象。
- **验证：** 检查字节码、结构和类型使用等是否符合虚拟机要求。
- **准备：** 为类变量，也就是静态字段，准备存储并赋初始值。通常先得到零值；带 ConstantValue 属性的常量字段有相应的常量赋值规则。
- **解析：** 将符号引用解析为运行时可使用的引用或目标。
- **初始化：** 执行类初始化方法 `<clinit>`，完成需要在这一阶段执行的静态字段赋值和静态代码块。

例如 `static int value = 10`，准备阶段先得到 0，初始化阶段再执行赋值为 10。类初始化与 `new` 创建某个对象、执行实例构造器是两回事。

这些阶段不应理解成所有类都一次性严格完成的流水线，解析可以按使用情况延迟。一般情况下，创建实例、调用静态方法、访问非编译期常量静态字段等主动使用会触发初始化。规则见 [JVM 规范：加载、链接与初始化](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html)。

**现场复盘：** 现场从验证开始回答，漏掉加载，并把静态字段初始化与对象分配内存混在一起。

### 9. Java 有哪些类加载器，它们是什么关系？

**题意说明：** 原文是“一共有两种类类加载器”，无法确认面试官是在问分类还是数量。下面同时覆盖“两类划分”和常见具体层次，不把“两种”认定为唯一标准答案。

**参考回答：**

从 JVM 的分类看，可以区分引导类加载器与用户定义的类加载器；具体到常见 JDK 层次，Java 8 通常讲 Bootstrap、Extension、Application，Java 9 以后扩展类加载器的位置由 Platform 类加载器接替，另外还可以自定义加载器。

常见的 `loadClass` 路径会先检查是否已经加载，再委托父加载器尝试，父加载器无法找到时才由当前加载器尝试，这就是通常说的双亲委派。它有助于基础类型的一致性，也减少重复加载。

这里的“父”主要是委托关系，不是说这些加载器必须形成 Java 类继承链。双亲委派是常见实现约定，不是所有自定义加载器都无法改变的规则。一个类的运行时身份还与定义它的类加载器有关，相同全限定名被不同加载器定义，也可能是不同类型。

**现场复盘：** 这题当时没有答出。复习时不要只背加载器名字，还要能解释委派流程及类型隔离。

### 10. 常见的垃圾回收算法有哪些？

**参考回答：**

先区分“对象是否可以回收”和“怎样回收内存”。Java GC 通常从 GC Roots 出发做可达性分析，判断对象的存活情况；具体回收策略常见有标记清除、标记复制和标记整理。

| 算法 | 基本过程 | 主要代价 |
| --- | --- | --- |
| 标记清除 | 标记存活对象，回收其余对象占用的空间 | 容易产生不连续的空闲空间 |
| 标记复制 | 将存活对象复制到另一块区域，整体回收原区域 | 需要预留目标空间，存活对象多时搬迁成本增加 |
| 标记整理 | 标记后移动存活对象，使可用空间更连续 | 对象移动和引用更新有成本 |

分代回收是一种组织策略：利用多数对象生命周期短、少数对象存活较久的特点，对不同代采用合适的回收方式。它可以组合上述算法，不是与它们完全同层级的第四个基本搬迁算法。

**现场复盘：** 算法名字大体说到了，但需要补上各自过程、碎片和空间开销，才能回答“为什么这样选”。

### 11. 常用垃圾回收器有哪些，它们有什么区别？

**参考回答：**

我主要从吞吐量、停顿时间、堆规模和 CPU 开销比较，而不是只列名称。

| 收集器 | 主要特点 | 理解重点 |
| --- | --- | --- |
| Serial | 主要回收工作使用单线程，回收时暂停应用线程 | 实现简单，适合资源有限或较小堆的场景 |
| Parallel | 使用多个 GC 线程并行回收，强调吞吐量 | 仍有 STW，不能把并行误认为与业务并发执行 |
| CMS | 历史上的低停顿老年代收集器，主要基于并发标记清除 | 有碎片及并发回收跟不上分配等问题；现代 JDK 已不再提供它 |
| G1 | 基于 Region，分代，综合考虑停顿目标与回收收益 | 兼顾吞吐和停顿，但目标不是绝对的停顿上限 |
| ZGC | 将大量工作并发执行，重点降低停顿 | 需要结合 CPU、内存余量、分配速度和实际负载评估 |

G1 与 ZGC 都不能说“完全没有 STW”。选择时应结合 GC 日志、停顿分布、分配速率和业务 P99；低停顿收集器也不意味着所有业务吞吐都更高。参照 [JDK 21 收集器说明](https://docs.oracle.com/en/java/javase/21/gctuning/available-collectors.html)。

**版本纠正：** ZGC 早在 JDK 11 就以实验特性引入，不能说到 JDK 17 或 21 才出现；JDK 21 的重要变化是引入分代 ZGC。参照 [OpenJDK ZGC 引入记录](https://bugs.openjdk.org/browse/JDK-8205334)与 [JDK 21 发布说明](https://www.oracle.com/java/technologies/javase/21-relnote-issues.html)。

**现场复盘：** 现场对收集器只有名称印象，缺少比较维度，并且版本时间线不准确。

### 12. ThreadLocal 有什么应用，使用时要注意什么？

**参考回答：**

ThreadLocal 用来把一个值与当前线程关联，让不同线程通过同一个 ThreadLocal 对象访问各自的值。常见用途包括线程内的请求上下文、追踪标识或事务上下文。它解决的是线程间状态隔离，不是给共享对象加锁；如果各线程存入的是同一个可变对象引用，对象本身仍然可能存在并发问题。

在常见 OpenJDK 实现中，值保存在当前线程的 ThreadLocalMap 里。Entry 对 ThreadLocal key 使用弱引用，对 value 使用强引用。如果 key 被回收而线程长期存活，value 可能仍沿着 `Thread -> ThreadLocalMap -> Entry -> value` 的强引用链被保留。

因此在线程池里，应在一次任务结束时通过 finally 调用 `remove()`，避免对象滞留和下一个任务读到上一个请求的数据。即使 key 一直被静态字段强引用，缺少清理也可能导致上下文长期保留。

普通 ThreadLocal 不会自动传播到异步任务或线程池中的另一个线程；跨线程时要显式传递、设置并在结束时清理。它的每线程关联语义见 [ThreadLocal API](https://docs.oracle.com/en/java/javase/26/docs/api/java.base/java/lang/ThreadLocal.html)。

**现场复盘：** 现场抓住了弱 key、强 value 和内存泄漏风险，这是正确方向；“定期 remove”应改成“任务结束时确定性清理”。

### 13. 深度优先搜索 DFS 和广度优先搜索 BFS 有什么区别？

**参考回答：**

DFS 沿一条路径尽量向深处走，走不通再回退；BFS 先访问离起点近的一层，再扩展下一层。DFS 可以用递归或显式栈实现，BFS 通常用队列实现。

例如 A 的邻居是 B、C，B 的邻居是 D、E，按该邻接顺序访问，DFS 可以是 `A -> B -> D -> E -> C`，BFS 则是 `A -> B -> C -> D -> E`。BFS 按边数递增探索，所以可以求无权图或等权图中的最少边数路径；DFS 第一次找到的路径通常不保证最短。

使用邻接表且每个顶点只访问一次时，二者时间复杂度都是 O(V + E)，最坏辅助空间可以达到 O(V)。DFS 在深链上可能导致递归栈溢出；BFS 在某一层特别宽时需要较大的队列。若使用邻接矩阵，扫描邻居的开销通常变成 O(V²)。

**现场复盘：** 队列、递归与复杂度相同的方向基本正确，但缺少适用条件和 BFS 最短路性质。图有环时要维护访问状态，BFS 通常在入队时标记，防止重复入队。

### 14. 请介绍网络协议的分层模型，五层模型或 OSI 七层模型均可

**参考回答：**

常见教学五层模型从上到下是应用层、传输层、网络层、数据链路层和物理层。

| 层次 | 主要职责 | 例子 |
| --- | --- | --- |
| 应用层 | 约定具体应用的请求、响应和数据语义 | HTTP、DNS |
| 传输层 | 提供进程间通信，使用端口区分应用端点 | TCP、UDP |
| 网络层 | 跨网络寻址与路由 | IP |
| 数据链路层 | 在相邻节点之间组织和传输帧 | 以太网、Wi-Fi 链路 |
| 物理层 | 通过物理介质传输比特 | 电、光、无线信号 |

OSI 七层在应用侧进一步区分应用层、表示层和会话层；表示层强调编码、格式转换等，会话层强调会话组织。实际 TCP/IP 协议体系也常用四层描述，不应把这些模型当成完全相同的实现规范。

**现场复盘：** 本题主体答对了。继续追问时，可以结合“HTTP 请求经过 TCP、IP 和链路封装后发送”说明每层职责。

### 15. TCP 和 UDP 有什么区别？

**参考回答：**

TCP 提供面向连接、可靠、有序的字节流服务；UDP 提供无连接的数据报服务，保留报文边界，但自身不保证送达、顺序或去重。

TCP 的可靠性主要靠序列号、确认、重传等机制，有序字节流还需要排序和重复数据处理；它同时具有接收端流量控制和网络拥塞控制。三次握手用于建立连接和同步初始状态，四次挥手是常见的连接关闭过程，不能把数据传输可靠性直接归因于握手与挥手。

UDP 的协议头和端点状态相对简单，应用可以根据需求自行决定哪些消息重传、哪些旧消息直接丢弃。它适合部分实时交互，也可以作为 QUIC 等协议的承载层，但不能笼统地说“UDP 一定更快”。

**现场复盘：** “TCP 稳定，UDP 不稳定”过于模糊，且现场把可靠性、文件大小和加密能力混在了一起。TCP 的可靠传输也不等于业务处理成功：游戏结算是否成功，仍需应用层确认、事务和幂等控制。

### 16. 为什么说大文件要用 UDP，TCP 难道不能传输大文件吗？

**参考回答：**

TCP 完全可以传输大文件，而且很多文件下载就是通过基于 TCP 的 HTTP 完成。文件大小与是否必须使用 UDP 没有这样的对应关系。

TCP 可以持续传输数据，应用负责分块读取、发送和写入，不需要把整个文件一次性放进内存。三次握手主要发生在连接建立阶段，不能由握手开销推导出 TCP 不适合大文件。连接也不会因为文件大就必然到时关闭；实际中断需要看网络故障、应用超时、代理配置等因素。

视频同样要区分场景：点播通常重视内容完整性，可以缓存后播放；实时音视频更看重数据的时效性，可能容忍少量丢失。传输协议应根据可靠性、延迟和应用协议选择，而不是按“视频或者大文件就用 UDP”判断。

**现场复盘：** 面试官第二次追问是在指出因果关系不成立。更好的现场回应是直接承认“我刚才说得不准确，TCP 当然可以传大文件”，再补充真正的选型依据。

### 17. UDP 不能传输加密数据吗，加密与传输层协议是什么关系？

**参考回答：**

UDP 可以传输加密数据。TCP、UDP 都可以承载字节内容，保密性不是由选 TCP 还是 UDP 直接决定的。

应用可以使用成熟的安全协议完成身份认证、密钥协商、加密和完整性保护。例如 DTLS 面向数据报传输，QUIC 也在 UDP 之上集成了安全机制。不能简单把面向有序字节流的 TLS 原样套到裸 UDP 上。

校验和也不等于加密。校验和主要用于发现传输差错，不能提供密码学意义上的防篡改、身份认证和保密性。设计时还要考虑重放攻击与密钥管理，不能只说“把数据加密一下”就认为安全协议完整。

**现场复盘：** 现场把 UDP 的校验能力与加密能力联系起来，随后又直接用 HTTPS 举例，没有把可靠性和安全性分开。

### 18. HTTPS 底层使用 TCP 还是 UDP？

**参考回答：**

要区分 HTTP 版本。常见的 HTTP/1.1、HTTP/2 的 HTTPS 连接使用 TLS 建立在 TCP 之上；HTTP/3 使用 QUIC，QUIC 承载在 UDP 之上，并使用 TLS 1.3 的握手机制。

可以分别记作：`HTTP/1.1 或 HTTP/2 -> TLS -> TCP -> IP`，以及 `HTTP/3 -> QUIC（集成 TLS 1.3 握手）-> UDP -> IP`。QUIC 自己提供可靠流和拥塞控制等能力，并不是裸 UDP 突然获得了可靠性。参照 [RFC 9114：HTTP/3](https://www.rfc-editor.org/rfc/rfc9114.html)。

**现场复盘：** 只回答“HTTPS 是应用层的”没有回应底层协议问题。面试时先讲最常见的 TLS over TCP，再补 HTTP/3 的例外即可。

### 19. 如果要在 UDP 之上实现可靠传输，应该怎样处理？

**参考回答：**

需要在 UDP 之上增加确认、重传、排序和控制机制，不能只增加建立连接时的握手。

- 为数据分配序列号，接收端据此去重，并在需要有序交付时缓存和重排。
- 通过 ACK 或选择性确认报告已收到的数据，发送端缓存尚未确认的数据。
- 根据 RTT 估计和超时判断丢失并重传，设置重试上限和失败通知。
- 增加窗口与流量控制，避免接收端来不及处理；增加拥塞控制，避免重传进一步压垮网络。
- 处理会话标识、旧包、报文大小和必要的分片重组，并结合成熟安全机制防止伪造或重放。

例如发送 1、2、3 号包，接收端收到 1 和 3，就可以报告缺少 2；发送端重传 2，接收端补齐后按序交付。若旧位置更新已经没有业务价值，也可以设计为无需重传，而奖励、购买等重要消息必须走可靠的业务确认。

**工程边界：** 实际项目优先评估成熟传输实现。即使可靠传输层去除了重复数据，也不能自动解决“服务端已发奖但响应丢失，客户端重新发起业务请求”的问题，仍要有业务幂等标识。

**现场复盘：** 想到了序列号和确认，是正确方向；重点应从握手转向持续传输阶段的机制。

### 20. 死锁是怎样产生的，怎样预防和恢复？

**参考回答：**

经典资源模型中，死锁需要同时具备互斥、持有并等待、不可剥夺、循环等待四个必要条件。比如线程 A 持有锁 X 等待锁 Y，线程 B 持有锁 Y 等待锁 X，双方都不会释放已持有的锁，就会永久等待。

预防可以破坏其中一个条件。工程上常见的是规定全局一致的加锁顺序，例如始终先锁较小 ID 再锁较大 ID；还可以减少嵌套持锁，或在适当场景使用带超时的尝试加锁，获取失败后主动释放已持有资源并回退。

发现死锁后，可以先用线程转储或 ThreadMXBean 定位参与线程和锁依赖。恢复通常需要取消或回滚某个参与者、释放资源；操作系统资源死锁可能涉及终止进程，数据库可选择回滚一个事务。Java 的 synchronized 不提供超时获取，也不能靠普通线程中断强制解除其锁等待，所以超时和取消能力要在设计阶段准备。

**现场复盘：** 当时只零散提到互相等待、占有资源。需要准确说齐四个条件，并区分“避免发生”和“已经发生后恢复”；不能随意从别的线程强行释放它持有的监视器锁。

### 21. MySQL 的 SQL 优化有哪些方法？

**参考回答：**

我会先找出最值得优化的 SQL，再用执行计划定位瓶颈，最后针对瓶颈改写并验证收益。EXPLAIN 是分析工具，不是优化动作本身。

具体先看慢查询、调用频率、耗时分布、扫描行数和返回行数；用 EXPLAIN 看访问方式、使用索引、连接顺序和排序情况。必要时在可控环境用 EXPLAIN ANALYZE 对照实际行数与耗时，因为它会真正执行查询。

优化时围绕实际条件设计联合索引，减少不必要的列和返回行数，避免不必要的全表扫描、重复查询、深分页和大量回表。还要检查隐式类型转换、列上的函数运算、连接字段索引，以及统计信息是否导致行数估算偏差。最终对比执行计划、延迟和数据库资源开销，而不是只看“出现了某个索引名”。参照 [MySQL SELECT 优化](https://dev.mysql.com/doc/refman/8.4/en/select-optimization.html)。

**必须纠正的现场说法：**

- 范围条件 `>`、`<` 并不必然导致索引失效，它们可以形成范围扫描。
- `LIKE 'abc%'` 与 `LIKE '%abc'` 的可利用索引方式不同，不能一概说模糊查询都不走索引。
- 多表 JOIN 不一定慢，取决于过滤效果、连接方式和数据量；拆成多次查询反而可能增加开销。
- ORDER BY 是业务需要就应保留，应优化其执行方式。
- `Using index` 通常说明覆盖索引访问，不等于整条 SQL 已经最优。

### 22. 为什么说不要使用排序，ORDER BY 应该怎样优化？

**参考回答：**

不能笼统地说不要排序。业务需要按时间、分数或排名返回结果，就应该明确写 ORDER BY。优化重点是能否利用索引顺序，以及能否减少进入排序的数据量。

例如查询某个玩家最近 20 条记录：

```sql
SELECT id, created_at
FROM player_event
WHERE player_id = ?
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

可以评估与过滤和排序相匹配的联合索引，例如 `(player_id, created_at, id)`。首列等值过滤后，后续键顺序有机会服务于排序；对于这里同向的降序，也可能反向扫描相应升序索引。是否实际采用，仍要结合真实表结构、数据分布和执行计划确认。这个 SQL 是解释原理的示例，并非录音中的生产 SQL。

无法通过索引完成排序时，MySQL 可能执行 filesort，但 filesort 不等于一定落磁盘，它也可能在内存中完成。只创建有序索引却去掉 ORDER BY，不能从 SQL 语义上保证返回顺序。参照 [MySQL ORDER BY 优化](https://dev.mysql.com/doc/refman/8.0/en/order-by-optimization.html)。

**现场复盘：** 后半段“通过索引保存顺序”抓到了方向，但结论应是优化排序，而不是禁止排序。

### 23. 索引有哪些优点和缺点？

**参考回答：**

索引的主要优点是加快查找，减少需要读取的记录或页面；适当的索引还可以帮助排序、分组和关联，覆盖索引能够减少回表，唯一索引可以落实唯一性约束。

代价主要是额外的存储和写入维护。插入、删除或修改索引字段时，需要维护相关索引，可能产生页分裂、日志写入等开销；索引也会占用缓存空间。索引越多，写入和维护的负担通常越大。

所以应该围绕高频查询和约束设计必要的索引，清理重复、冗余索引，而不是每个字段都建一个。选择性较差的索引也不是绝对无用，需要结合过滤比例、覆盖能力和查询结构判断。参照 [MySQL 索引优化](https://dev.mysql.com/doc/refman/8.4/en/optimization-indexes.html)。

**现场复盘：** “占用内存”只覆盖一部分代价；更关键的是磁盘空间、写放大和维护成本。

### 24. MySQL 索引采用什么数据结构，聚簇索引与二级索引有什么区别？

**参考回答：**

以 InnoDB 普通索引为例，主要使用 B+ 树。非叶子页保存导航所需的键和子页信息，叶子页保存具体记录。

聚簇索引把整行记录组织在叶子页中，一张 InnoDB 表只有一个聚簇索引。通常使用主键；没有主键时，会优先选择合适的全列非空唯一索引，否则由 InnoDB 生成隐藏的行标识来组织聚簇索引。

二级索引叶子记录保存二级索引键和对应的聚簇索引键。通过二级索引找到记录后，如果所需列不全在索引中，还要拿聚簇键去聚簇索引取完整记录，这叫回表；若所需列都能由该索引提供，就有机会形成覆盖索引访问。

因此，二级索引里通常是主键值，不是可以直接跳到整行的内存指针；过长的主键还会放大二级索引的体积。参照 [InnoDB 聚簇索引与二级索引](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html)。

**现场复盘：** 原回答已区分叶子节点保存整行或索引字段加主键，整体方向正确。应补充回表及“讨论的是 InnoDB”的前提。

### 25. 为什么 InnoDB 选择 B+ 树作为普通索引的存储结构？

**参考回答：**

主要因为 B+ 树适合按页组织数据，同时支持等值查询、范围查询和有序扫描。

数据库以页为重要读写单位。B+ 树内部节点主要存放索引键和子页信息，一个页可以容纳较多分支，因此相同记录规模下树通常比二叉搜索树矮，有利于减少从根到叶需要访问的页面数量。叶子记录有序，叶子页之间又可以顺序遍历，找到范围起点后便于连续扫描。

与哈希结构相比，它更适合范围和排序；与普通二叉树相比，分支更多、树更矮；与内部节点也放完整数据记录的 B 树相比，B+ 树内部页通常能保存更多导航项。

**边界：** 不能承诺任何表都只需要两三层，也不能把层数直接当成物理磁盘 I/O 次数。实际高度取决于键宽、页大小、填充程度和数据量，Buffer Pool 命中后访问页面未必需要读磁盘。

**现场复盘：** “多路、树矮、叶子有序支持范围查询”答到了重点，但应说一个内部节点可以有很多子节点，而不是“一个节点有很多叶子节点”。

### 26. 怎样解决缓存击穿？它与缓存穿透、缓存雪崩有什么区别？

**参考回答：**

缓存击穿指一个访问量很大的热点 key 失效或缺失，导致大量并发请求同时回源数据库。核心是控制同一个热点的并发重建数量，并限制数据库承受的回源流量。

常见做法是缓存重建互斥：请求发现缓存未命中后尝试获得该 key 的重建资格，获得后再次检查缓存，再查数据库并写缓存；其他请求短暂等待后重试，或者按业务要求返回可接受的旧值或降级结果。单进程可以合并相同 key 的请求，多实例还要考虑跨实例竞争。使用分布式锁时，需要超时、唯一持有标识和安全释放，数据库侧仍应保留限流保护。

另一种方式是逻辑过期：缓存同时保存值与业务过期时间，过期后允许暂时返回旧值，再由一个任务异步刷新。这要求业务允许短时间陈旧，并且旧值仍然存在；它不适合直接用于必须读取最新余额或处罚状态的判断。

| 问题 | 发生了什么 | 常见应对 |
| --- | --- | --- |
| 缓存穿透 | 反复查询缓存和数据库都没有的数据 | 参数校验、短期空值缓存、布隆过滤器、限流 |
| 缓存击穿 | 单个热点 key 缺失，引发大量并发回源 | 重建互斥、请求合并、预热或提前刷新、合适场景下逻辑过期 |
| 缓存雪崩 | 大量 key 同时失效，或缓存整体不可用 | TTL 加随机量、错峰刷新、高可用、熔断限流和降级 |

布隆过滤器可能误判“存在”；在数据维护正确且元素已加入过滤器的前提下，不会把该元素判断为不存在。业务新增数据还未同步到过滤器时，仍可能被错误拦截，不能忽略维护时序。

**现场复盘：** 面试官明确问击穿，应该先回答击穿再对比其他两类。**Redis 的惰性过期删除不是防击穿方案**：访问过期 key 时它会被视为不存在，不会自动把旧值返回，也不会自动只放一个请求去数据库。Redis 还会主动清理过期键；这与应用层逻辑过期是不同机制。参照 [Redis EXPIRE 的过期机制](https://redis.io/docs/latest/commands/expire/)。

### 27. Redis 缓存和 MySQL 之间怎样保证数据一致性？

**参考回答：**

如果业务允许短时间不一致，常见方案是 Cache Aside：MySQL 作为事实来源，读取先查缓存，未命中再查库并回填；修改时先提交数据库事务，再删除对应缓存，让后续读取重新加载。

比起“先删缓存再更新数据库”，这个顺序减少了一个常见窗口：缓存先删后，另一个读请求可能在数据库更新前读出旧值并回填，随后数据库才更新，缓存就留下旧数据。原回答对这个时序的解释是正确的。

但“先更新数据库再删缓存”仍不等于强一致，需要补两类问题：

- **删除失败：** 数据库已提交，但删除缓存失败。可通过可靠的重试任务、与数据库事务绑定的待处理事件，或者基于变更日志的同步机制补偿，并配置合理 TTL 和监控。仅把失败打印到日志里不够。
- **并发旧值回填：** 缓存原本未命中，读线程先从数据库读到旧值；写线程随后提交新值并删缓存；读线程最后又将旧值写回缓存。可以结合版本校验、读写协调或适当的失效补偿降低风险，但需要说明具体实现如何挡住旧版本，不能只说“加一个版本号”。

延迟双删能缓解某些竞态，但固定等待时间不能证明强一致。对发奖、扣款等关键操作，应在权威存储中完成事务、条件更新和幂等判断；不能依据可能陈旧的缓存值直接决定资产变更。

**现场复盘：** 主流程和先删缓存的反例答得较好，欠缺删除失败处理及最终一致性的边界。

### 33. 游戏服务器与传统互联网后端最本质的区别是什么？

**参考回答：**

对需要多人实时交互的游戏而言，最突出的特点是：服务器持续维护一群玩家共同参与的游戏状态，并在较紧的时间约束下处理相互影响的操作。因此它更强调会话、局内状态、事件顺序和时间推进。

## 四、本场重点复习结论

从本场追问来看，优先需要修正的是基础知识的准确性和解释中的因果关系，而不只是增加术语数量。
