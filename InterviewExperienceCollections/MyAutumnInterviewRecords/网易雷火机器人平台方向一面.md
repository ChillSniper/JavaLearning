### 3. Java `HashMap` 的底层数据结构是什么

**建议时长：45～60 秒。**

以 Java 8 及之后的常见实现为例，`HashMap` 的主体是一个 `Node<K,V>[]` 数组，也叫桶数组。每个桶可能为空、只有一个节点、是一条链表，或者在冲突严重时是一棵红黑树，所以完整答案是“数组 + 链表 + 红黑树”。

插入时先根据 key 的 `hashCode()` 计算扰动后的 hash，再通过 `(n - 1) & hash` 定位桶。发生冲突后沿链表或红黑树查找相同 key；找到就替换 value，找不到才新增节点。

链表长度达到树化阈值 8 时并不一定立即树化：只有数组容量至少为 64 才会转成红黑树，否则优先扩容。节点减少到一定程度时还可能退化回链表。`HashMap` 默认不保证线程安全。

### 4. `HashMap` 根据 key 查找 value 的完整过程是什么

**建议时长：60 秒。**

第一步，若 key 为 `null`，其 hash 按 0 处理；否则调用 `key.hashCode()`，再让高位参与低位运算得到扰动后的 hash。第二步，根据数组长度 `n` 计算桶下标 `(n - 1) & hash`。

第三步，检查桶的首节点。实现通常先比较节点保存的 hash，再判断 key 是否为同一引用，或者在引用不同的情况下调用 `equals()`。首节点不匹配时，如果桶已经树化，就按红黑树规则查找；否则沿单链表逐个比较。找到返回 value，全部不匹配返回 `null`。

因此不是“只根据 hash 就找到 value”。hash 只负责缩小到某个桶，同一桶内仍要依靠 `equals()` 区分真正的 key。

### 5. `HashMap` 数组中的节点具体保存哪些信息

**建议时长：30～45 秒。**

普通链表节点 `Node<K,V>` 主要保存四项：扰动后的 `hash`、原始 `key`、对应的 `value`，以及指向同一桶中下一个节点的 `next`。

桶数组中保存的是节点引用，节点本身同时包含 key 和 value，并不只是“链表头指针”。树化后的 `TreeNode` 还会增加父节点、左右子节点、前驱节点和颜色等红黑树维护信息。

### 6. Java 中 `==` 和 `equals()` 有什么区别

**建议时长：45 秒。**

`==` 是运算符。比较基本类型时，它比较数值；比较引用类型时，它比较两个引用是否指向同一个对象。

`equals()` 是对象方法，用来表达业务或内容上的相等。`Object.equals()` 默认仍然等价于引用比较，但 `String`、包装类和很多集合类重写了它，所以这些类型可以按内容比较。

`equals()` 本身不会先计算 `hashCode()`。哈希容器为了提高查找效率，才会先比较 hash，再在候选节点之间调用 `equals()`；不要把容器的查找过程误说成 `equals()` 的实现。

### 7. `new String("A") == "A"` 的结果是什么，为什么

**建议时长：30～45 秒。**

结果是 `false`。字符串字面量 `"A"` 引用字符串常量池中的对象，而 `new String("A")` 会显式创建一个新的 `String` 对象。两边内容相同，但引用不同，所以 `==` 为 `false`。

如果写成 `new String("A").equals("A")`，结果是 `true`，因为 `String.equals()` 比较字符内容。若对新对象调用 `intern()`，得到的是常量池中规范化对象的引用，此时再与字面量用 `==` 比较可以为 `true`。

### 8. `new String("A")` 和字符串字面量 `"A"` 在对象创建和存储上有什么区别

**建议时长：45 秒。**

字符串字面量会从字符串常量池取得规范化的 `String` 对象；如果池中已有相同字面量，就复用该引用。`new String("A")` 则要求在堆上再创建一个新的 `String` 对象，其内容来自字面量对应的字符串。

现代 HotSpot 中字符串常量池本身也位于堆内，不能再简单回答成“字面量在方法区、新对象在堆”。真正关键的区别是是否复用池中的规范化对象，以及两个引用是否指向同一实例，而不是死记某个 JVM 版本的物理区域名称。

### 9. `equals()` 与 `HashMap` 有什么关系？自定义类型重写 `equals()` 时要注意什么

**建议时长：60 秒。**

`HashMap` 用 `hashCode()` 决定 key 大致落在哪个桶，再用 `equals()` 判断桶中的候选 key 是否与查询 key 逻辑相等。因此，自定义对象作为 key 时，相等语义必须稳定且与哈希语义一致。

重写 `equals()` 要满足自反、对称、传递、一致以及对 `null` 返回 `false`；同时必须重写 `hashCode()`。参与比较和计算 hash 的字段在 key 放入 Map 后最好保持不可变，否则对象的桶位置和相等语义会变化，可能出现“明明在 Map 中却查不到”的问题。

类型判断可以使用 `getClass()` 或 `instanceof`，但要结合继承设计保持对称性。实际工程中更推荐使用不可变值对象作为 key。

### 10. 为什么重写 `equals()` 时通常必须同时重写 `hashCode()`

**建议时长：45 秒。**

Java 约定要求：如果两个对象通过 `equals()` 判断相等，它们的 `hashCode()` 必须相同；反过来，hash 相同不代表对象一定相等。

如果只重写 `equals()`，两个逻辑相等的对象仍可能沿用基于身份生成的不同 hash。放入 `HashMap` 或 `HashSet` 后，它们会进入不同桶，容器可能存下重复元素，或者用另一个等价对象查找失败。

所以 `equals()` 和 `hashCode()` 必须基于同一组稳定字段实现。普通业务对象可以借助 IDE、record 或 `Objects.equals/hash` 生成，但仍要确认字段选择符合业务身份定义。

### 11. CAS、`volatile` 和 `synchronized` 分别解决什么问题，有什么区别

**建议时长：60～90 秒。**

三者不是同一层面的替代品。

- `volatile` 主要保证可见性和一定的有序性：一个线程写入后，其他线程能看到最新值，并限制相关指令重排。它不保证 `count++` 这种读改写操作的原子性。
- CAS 是 Compare-And-Set，比较内存中的当前值是否等于期望值，相等才原子更新。它常用于 `AtomicInteger` 和无锁算法，冲突时通常自旋重试，适合临界区短、竞争不高的单变量更新。
- `synchronized` 是 JVM 提供的互斥与同步机制。同一时刻只有持有 monitor 的线程进入临界区，其他线程需要等待；进入和退出监视器还带来可见性和有序性保证，适合保护包含多个步骤、多个共享变量或必须维护整体不变量的代码。

CAS 还存在 ABA、自旋消耗 CPU、难以原子维护多个变量等边界。`volatile` 不能被称为乐观锁，`synchronized` 也不能简单等同于“重量级锁”。

### 12. `ReentrantLock` 是什么？它与 `synchronized` 有什么区别

**建议时长：60 秒。**

`ReentrantLock` 是 `java.util.concurrent.locks` 包中的可重入独占锁，常基于 AQS 管理同步状态和等待队列。可重入表示同一线程已经持锁时可以再次获取，内部记录重入次数，释放相同次数后才真正解锁。

它和 `synchronized` 都可以实现进程内互斥与 happens-before 可见性。`ReentrantLock` 额外提供可中断获取、超时尝试、多个 `Condition`、公平策略和显式查询锁状态等能力；代价是必须手动在 `finally` 中 `unlock()`。`synchronized` 语法更简单，异常退出会自动释放，JVM 也能做针对性优化，普通互斥场景应优先选择更简单、正确的写法。

二者都只能协调同一 JVM 内的线程，不能直接作为跨实例分布式锁。

### 13. `ReentrantLock` 的公平锁和非公平锁有什么区别

**建议时长：45 秒。**

公平锁倾向于让等待时间更久、排在队列前面的线程先获得锁，减少长期饥饿，但线程切换和排队成本更高，吞吐通常较低。

非公平锁允许刚到达的线程先尝试抢锁。它可能直接复用当前 CPU 上的运行线程，减少唤醒和切换，所以默认吞吐通常更好；代价是等待顺序不严格，极端情况下某些线程等待更久。

这里的非公平不是“按优先级获取”。选择时应看业务是否要求等待顺序和最长等待时间，而不是只看平均吞吐。

### 14. 实际应用中怎样选择乐观锁和悲观锁

**建议时长：60 秒。**

核心不是“并发越高越用悲观锁”或“追求性能就用乐观锁”，而是看冲突概率、临界区长度、重试成本和业务不变量。

读多写少、冲突概率低、操作很短且失败可以重试时，乐观方案通常更合适，例如 CAS 或数据库版本号。它避免线程阻塞，但高竞争下会反复失败、自旋或回滚，反而浪费资源。

冲突频繁、临界区包含多个步骤、失败重试代价很高，或者必须串行保护复杂不变量时，更适合悲观锁，例如 `synchronized`、`ReentrantLock` 或数据库行锁。最终应通过冲突率、重试次数、锁等待时间、吞吐和 P95/P99 延迟验证，而不是只凭标签选择。

### 15. 乐观锁通常怎样实现

**建议时长：45～60 秒。**

内存中的典型实现是 CAS：读取旧值，计算新值，只有当前值仍等于旧值时才更新，否则重新读取并重试。

数据库中的典型实现是版本号条件更新：

```sql
UPDATE account
SET balance = ?, version = version + 1
WHERE id = ? AND version = ?;
```

受影响行数为 1 表示成功，为 0 表示期间已有其他事务修改，需要重读、重试或返回冲突。也可以用 `updated_at` 做条件，但版本号语义通常更清晰。乐观锁只负责检测并发修改，重试次数、退避、幂等和冲突后的用户提示仍需业务设计。

### B. MySQL 与 Redis

### 16. MySQL 有哪些索引类型，它们有什么区别

**建议时长：60～90 秒。**

需要先说明分类维度，避免把不同概念混在一起。

从 InnoDB 的存储关系看，有聚簇索引和二级索引。聚簇索引通常就是主键 B+ 树，叶子节点保存整行记录；如果没有合适主键，InnoDB 会选择唯一非空索引或生成隐藏行 ID。二级索引叶子节点保存索引列和主键值，查询其他列时可能需要拿主键回表。

从约束和列数看，可以分为普通索引、唯一索引、主键索引、单列索引和联合索引；覆盖索引不是一种独立物理结构，而是某次查询需要的列都能从索引取得。MySQL 还支持全文索引、空间索引；MEMORY 等引擎可支持 Hash 索引，但 InnoDB 常规索引主要是 B+ 树。

### 17. 使用联合索引时需要注意什么

**建议时长：60 秒。**

联合索引 `(a,b,c)` 按 `a`、再按 `b`、再按 `c` 排序，所以通常可以支持 `(a)`、`(a,b)`、`(a,b,c)` 这样的最左前缀，也能在某些场景支持跳跃扫描等优化，但不能把后者当成稳定前提。

设计列顺序时要根据真实查询决定：常用等值过滤列、范围列、排序分组列和选择性都要综合考虑，并通过 `EXPLAIN ANALYZE` 验证。某列出现范围条件后，后续列通常不能继续缩小 B+ 树的扫描边界，但仍可能通过索引下推过滤，不能笼统说“后面的索引全部失效”。

还要避免对索引列做破坏可搜索性的函数或计算、隐式类型转换和前导通配符；同时考虑覆盖索引、索引长度、写放大和冗余索引，而不是索引越多越好。

### 18. 常见的索引失效或优化器不选择索引的情况有哪些

**建议时长：60～90 秒。**

常见情况包括：

- 不满足联合索引的有效前缀，直接只查后面的列。
- 对索引列做函数、运算或无法利用函数索引的表达式，例如 `DATE(create_time)=...`。
- 字段类型或字符集不一致引发隐式转换。
- `LIKE '%keyword'` 以通配符开头，普通 B+ 树无法定位起点。
- `OR` 的某个分支没有可用索引，优化器判断全表扫描成本更低。
- `!=`、`NOT IN`、低选择性条件返回数据比例过高，回表成本可能高于全表扫描。
- 表很小、统计信息不准、返回行过多时，优化器基于成本主动选择全表扫描。

“没有走索引”和“索引结构完全不能用”不是一回事。排查时应看执行计划中的 `type`、`key`、`rows`、`filtered`、`Extra`，必要时用 `EXPLAIN ANALYZE` 对比估算和真实执行。

### 19. `>`、`<`、`!=` 等范围或否定条件一定会导致索引失效吗？为什么

**建议时长：45～60 秒。**

不一定。`age > 20`、`created_at BETWEEN ...` 这类范围条件通常可以在 B+ 树中先定位边界，再沿叶子节点链表做范围扫描，属于正常的 range scan。

在联合索引 `(a,b,c)` 中，如果 `a` 等值、`b` 是范围，`c` 往往不能继续参与确定扫描区间，但可能通过索引条件下推过滤。`!=`、`NOT IN` 也不是语法上必然失效，只是命中比例常常很高，优化器可能认为走二级索引再大量回表不划算。

因此正确回答是：是否使用索引由可搜索条件、索引顺序、数据分布、覆盖情况和成本共同决定，最终看执行计划，不能背诵“出现大于小于就失效”。

### 20. Redis 有哪些常用数据类型，分别适合什么场景

**建议时长：60～90 秒。**

五种基础类型及典型场景是：

- `String`：缓存对象、计数器、分布式锁值、限流计数和 Bitmap 的底层载体。
- `Hash`：保存对象的多个字段，例如用户资料或配置项，适合局部字段读写。
- `List`：按插入顺序组织元素，可做简单队列、栈或时间线，但不适合按任意到期时间排序。
- `Set`：无序去重集合，适合标签、共同关注、抽奖候选和去重。
- `ZSet`：每个 member 关联一个 score 并按 score 排序，适合排行榜、优先队列和按时间范围扫描任务。

扩展类型还包括 Stream、Bitmap、HyperLogLog、GEO 等。Stream 适合带消费组的消息流；Bitmap 适合签到或布尔状态；HyperLogLog 做近似基数统计；GEO 用于经纬度附近搜索。GEO 和 Bitmap 在实现上依托已有基础类型，但对使用者提供了独立命令语义。

### 21. Redis `Set` 和 `ZSet` 的核心区别是什么

**建议时长：30～45 秒。**

两者都保证 member 唯一。`Set` 没有 score，不维护业务顺序，擅长成员判断、去重以及交并差集；`ZSet` 为每个 member 绑定一个浮点 score，并按 score 排序，支持排名和分数范围查询。

所以普通黑名单只需要判断“是否存在”时可以用 `Set`；如果还要按解封时间找出已经到期的人，就更适合用 `ZSet`，把解封时间戳放入 score。`Hash` 才是字段到值的映射，不应与 `ZSet` 混淆。

### 22. `ZSet` 按什么排序？分数相同时怎样处理

**建议时长：30 秒。**

`ZSet` 首先按 score 从小到大排序。分数相同时，Redis 按 member 的字典序排列，从而得到确定顺序。

排行榜可以把积分作为 score，延时任务可以把执行时间戳作为 score。需要同时保存更多业务字段时，通常让 member 保存任务 ID，再到数据库或 Hash 中查询详情，不宜把经常变化的大对象直接塞进 member。

### C. 途游黑名单到期解封项目

### 23. 结合项目说明你是怎样使用 Redis `ZSet` 的

**建议时长：60～90 秒。**

这个需求是对临时进入支付风控黑名单的用户自动解封。业务系统保存封禁事实和解封时间，调度侧使用 Redis ZSet：`member` 使用能够唯一标识用户、项目和本次封禁的值，`score` 保存解封 Unix 时间戳。

定时任务执行 `ZRANGEBYSCORE key -inf now LIMIT 0 batchSize`，分批找出已经到期的记录，然后执行解封并从 ZSet 移除。多实例可能同时扫到同一用户，所以要有任务领取或分布式互斥，并让最终解封操作具备幂等性，例如数据库做带当前状态和封禁版本条件的更新。

回答边界要说清：ZSet 更适合作为可重建的调度索引，数据库或权威风控服务保存最终业务状态。录音中的扫描周期与仓库复盘材料冲突，所以这里不声称具体周期；面试前必须核对真实配置。

### 24. 如果待解封用户很多，而且要求解封时间尽可能准确，怎样改进现有 `ZSet` 方案

**建议时长：90 秒。**

先在现有方案上改，不需要一上来就“多开 Redis”。扫描任务每次只查询 `score <= now` 的到期元素，按固定批次循环拉取，直到本轮没有到期数据或达到时间预算；把轮询间隔从业务可接受的最大延迟倒推出来。处理侧使用有界协程池并发执行，但必须限制对数据库或下游服务的并发。

多实例之间需要原子领取任务。可以用 Lua 在 Redis 内完成“检查到期 + 移入 processing 集合”之类的领取过程，失败任务按重试时间重新入队；最终业务更新仍通过封禁版本、状态条件、唯一 operation ID 保证幂等，避免旧解封任务解除一次新的封禁。

数据量继续增长时，可以按项目或用户稳定分片多个 ZSet，让不同 Worker 负责不同分片；同时监控到期积压量、最老任务延迟、每批成功/失败数、重试次数和下游耗时。只有确认单分片吞吐不足后再扩分片或换 MQ，不能只靠增大线程池掩盖下游瓶颈。

### 25. 扫描间隔和每批处理数量应该怎样确定？为什么不能随意写成“30 分钟、100 条”

**建议时长：60 秒。**

扫描间隔由解封延迟 SLA 决定。例如业务要求到期后 1 分钟内解封，就不能设置 30 分钟轮询；还要为任务执行、重试和时钟误差预留预算。批大小由单条平均耗时、下游容量、实例数和单轮时间预算决定，可以用以下关系先估算：

```text
单实例吞吐约等于 并发数 / 单条平均耗时
单轮处理能力约等于 单实例吞吐 × 实例数 × 可用处理时间
```

上线前通过压测选择初值，上线后根据队列积压、最老任务延迟、Redis 耗时、DB 连接池和下游限流动态调整。`100` 可以是为了限制单批内存和下游冲击的经验起点，但必须有数据支持。

本场录音中的“30 分钟、100 条”没有给出这种推导，而且与已有复盘材料中的扫描周期冲突，因此下一次不能继续把它作为已确认事实。

### 26. 不使用 `ZSet` 时还能怎样实现延时解封？为什么普通 Redis `List` 通常不合适

**建议时长：60～90 秒。**

替代方案包括支持延迟或定时消息的 MQ、带 `(next_execute_at, id)` 索引的 MySQL 任务表、应用内时间轮，以及 Redis 过期事件等。选型要看任务规模、最长延迟、精度、可修改性、可观测性和可靠性。

普通 `List` 只按插入顺序排列，不会按解封时间自动排序。不同用户的封禁时长不同，后插入的任务可能更早到期；要维持有序就需要线性查找位置或反复排序，效率和并发正确性都较差。只有所有任务延迟完全相同且创建时间严格有序等特殊前提下，List 才可能勉强充当简单队列。

Redis key 过期通知也不能作为关键任务的唯一触发源，因为通知是事件提示而非可靠消息，订阅端离线时可能错过。无论哪种方案，数据库状态、幂等、重试和补偿仍要存在。

### 27. 使用消息队列实现延时解封依赖什么能力，还要处理哪些问题

**建议时长：60 秒。**

需要 MQ 支持延迟消息或定时消息：生产者创建封禁任务时把期望解封时间写入消息，Broker 在到期前保存消息，到期后才投递给消费者。消费者收到后再次检查数据库中的当前封禁状态、版本和解封时间，条件仍成立才执行解封。

MQ 通常提供至少一次投递，因此消费者必须幂等，并处理重复、乱序、消费失败重试和死信。还要考虑长时间延迟是否支持、定时精度、积压、Broker 故障恢复，以及用户提前解封或修改解封时间后怎样取消旧消息。常见做法不是强行撤回旧消息，而是让消息携带 `banVersion`，旧版本到期后因条件不匹配自然失效。

### 28. 如果只使用 MySQL，怎样设计用户的临时封禁和到期解封？是否一定需要额外状态流转任务

**建议时长：60～90 秒。**

如果需求只是“当前是否被临时封禁”，可以在用户或风控状态表保存 `blocked_until`：`NULL` 表示没有临时封禁，`blocked_until > NOW()` 表示仍在封禁，`blocked_until <= NOW()` 表示已经自然失效。查询权限时直接按当前时间判断，就不需要为了把 `BLOCKED` 改成 `NORMAL` 而启动额外状态流转任务，也避免 `status` 与时间字段互相矛盾。

如果还要触发通知、审计或下游解封动作，可以建立任务表：`id`、业务主键、`ban_version`、`execute_at`、`status`、`retry_count`、`next_retry_at`，并建立 `(status, next_retry_at, id)` 联合索引。Worker 分批领取到期任务，可使用条件更新或 `SELECT ... FOR UPDATE SKIP LOCKED`，调用下游后记录成功或重试。

永久封禁、临时封禁和未封禁必须有明确语义，不能让一个 `NULL` 同时代表多种状态。若封禁历史和重复封禁很重要，单独的封禁记录表通常比不断覆盖 user 表更清晰。

### D. 字节实习项目与 Redis 并发

### 29. 字节实习中的配置化规则引擎链路是什么

**建议时长：90 秒。**

这条链路面向支付风控处罚后的商家申诉。原来部分案件完全依赖人工审核，我参与新建了一条针对特定案件类型的机审业务链路，让满足明确规则的案件自动判断并执行后续动作，不确定或异常的案件继续转人工。

规则由内部配置平台托管并下发。业务服务把上游传来的案件类型、地区、风控标签和材料结果等结构化字段绑定成规则上下文，再交给已有表达式能力求值。条件命中后，从配置中取得预先注册的动作，按受控顺序执行加白、加黑、处罚状态变更、关单或下游通知；字段缺失、规则不匹配或依赖失败时 fallback 到人工处理。

工程上还要有配置校验、版本、灰度、审计、监控和回滚。配置只能选择代码中允许的表达式字段和动作，不能让配置执行任意函数或绕过业务权限。

### 30. 你是从零搭建了整条通用规则引擎，还是基于现有能力做规则配置

**建议时长：45～60 秒。**

准确说法是：具体机审业务链路是新搭的，但通用配置平台和表达式解析能力不是我从零开发的。

我的工作边界是基于公司已有基础设施，在业务服务中定义配置结构和规则上下文，接入配置下发，实现案件筛选、动作注册与编排、异常 fallback、下游联调、测试和上线观测。它不只是“在平台上填几条规则”，因为业务执行链路需要开发；但也不能包装成“独立开发了通用规则引擎或配置中心”。

### 31. 机审链路上线后怎样观测效果？规则命中率和完全机审率应怎样定义

**建议时长：60～90 秒。**

首先固定统计口径和时间窗。可以定义：

```text
规则命中率 = 命中任一机审规则的目标案件数 / 进入该类机审评估的案件数
完全机审率 = 无需人工介入且所有自动动作成功的案件数 / 目标案件总数
```

还要监控规则未命中原因、字段缺失率、各动作成功率、fallback 人工比例、误判申诉、处理时延和节省的人工量。配置发布要带版本和区域维度，才能比较发布前后以及不同区域的效果；异常上升时能够按版本回滚。

按本场录音，候选人观察到规则命中约 20% 多、完全自动执行约 9%。这两个数字只能作为录音记录，下一次回答前必须核对分母、统计周期、是否去重、上线区域和仪表盘口径，不能把未经核验的缩写和指标写成确定事实。

### 32. 处罚查询链路为什么引入 Elasticsearch？怎样保证 ES 与 MySQL 的数据一致性

**建议时长：90 秒。**

这条链路面对多条件处罚记录查询。MySQL 仍保存权威业务数据，ES 保存为查询优化而构建的反规范化索引，用倒排索引和过滤能力降低复杂组合查询、关联或大范围检索的延迟。

一致性上，录音能确认的是公司内部数据平台通过增量消息把 MySQL 变化同步到 ES，但不能仅凭转写断言底层一定是 binlog、轮询或某种具体实现。通用的可靠设计是订阅 binlog/CDC，或者在同一 MySQL 事务中写业务数据和 Outbox，再由消费者异步更新 ES。ES 文档携带业务主键和单调版本，消费者做幂等 Upsert，拒绝旧版本覆盖新版本。

同时要有同步延迟和失败率监控、可重放的消息、死信处理、全量重建与增量水位衔接、定期对账修复。普通查询可以接受明确 SLA 内的最终一致；要求读己之写或 ES 缺失时可回源 MySQL，但要限制回源成本。

### 33. ES 未命中就回源 MySQL，是否会被恶意不存在查询穿透？应该怎样防护

**建议时长：90 秒。**

会有这种风险。攻击者或异常调用方不断查询不存在的 ID，ES 每次 miss 后都回源 MySQL，ES 就失去了保护数据库的作用。这和缓存穿透类似，但不能通过“先查另一张 MySQL 表确认存在”解决，因为那仍然把请求打到了数据库。

防护应分层：入口做身份认证、服务 ACL、参数白名单、按调用方和设备限流；对确定不存在的等值查询做短 TTL 负缓存；若合法 ID 集合可维护，可以使用本地集合或布隆过滤器做前置判断，并接受误判和更新延迟；回源链路设置并发上限、超时、熔断和降级，数据库使用只读实例、覆盖索引或专用查询表隔离核心交易库。

同时区分“确实不存在”和“ES 尚未同步”。对刚写入或一致性要求高的请求，可以携带版本或在短窗口内直接读主库；系统压力过高时宁可返回可识别的降级结果，也不能让无限回源拖垮 DB。录音说明该接口只供内部中心使用，外部攻击面较小，但内部误用、批量脚本和凭证泄露仍需要限流与审计。

### 34. Redis Pipeline 和 Lua 脚本分别解决什么问题

**建议时长：60 秒。**

Pipeline 解决网络效率问题。客户端把多条命令连续发送，再批量读取响应，减少逐条“发送一条、等待一次”的网络 RTT 和系统调用。Redis 仍按命令逐条执行，Pipeline 不保证整批命令原子，也不是事务。

Lua 解决 Redis 内多步逻辑的原子执行问题。脚本执行期间不会插入其他普通命令，适合把“读取 -> 判断 -> 修改”合在一起，例如释放分布式锁时先比较 token，相同才删除。

Lua 只能保证单个 Redis 执行边界内的原子性，不能自动保证 Redis、MySQL、MQ 和外部 RPC 的全局原子性；长脚本还会阻塞其他请求，所以脚本应短小、有界。

### 35. Redis 命令大体串行执行，为什么多个客户端仍会出现并发竞态？Lua 的核心作用是什么

**建议时长：60 秒。**

单条 Redis 命令是原子的，但一段业务逻辑通常包含多条命令。例如客户端 A 执行 `GET lock` 后、执行 `DEL lock` 前，客户端 B 的命令可以插入；如果旧锁刚好过期并被 B 重新获取，A 的直接 `DEL` 就会误删 B 的锁。

因此竞态来自“多条原子命令的组合不是原子的”，不是因为 Redis 同时在两个线程里修改同一个数据结构。Redis 6 之后引入的 I/O 多线程主要帮助网络读写，也不改变这里的业务结论。

Lua 的核心作用是把相关的读取、条件判断和写入放进一次不可被普通命令穿插的执行中。若逻辑可以用一条原生命令完成，例如 `INCR` 或 `SET key token NX PX ttl`，优先使用原子命令；只有原生命令不足以表达条件读改写时才使用 Lua。

### 36. 什么情况下使用 Pipeline，什么情况下使用 Lua？二者能否组合使用

**建议时长：45～60 秒。**

大量相互独立的命令需要减少网络往返时使用 Pipeline，例如为一批不同用户分别发送 `SET NX`，然后逐条检查返回结果。需要多步条件逻辑原子化时使用 Lua，例如校验锁 token 后删除、判断库存后扣减并记录用户。

二者可以组合，因为职责不同：Pipeline 批量发送多个独立操作，每个操作内部可以是普通命令，也可以是 Lua 脚本；但整个 Pipeline 仍然不是全有或全无。使用时要限制批次大小，处理部分失败，并在数据库层继续用唯一约束、版本条件或幂等状态机兜底。

### E. 机器人弱网通信

### 37. 机器人所处网络不稳定，怎样保证机器人与服务器之间的通信质量

**建议时长：90～120 秒。**

我会先按消息类型定义目标，而不是简单回答“全部用 TCP”。控制指令要求可靠、可鉴权、可去重并且有明确过期时间；遥测数据更关注新鲜度，旧状态晚到后可能应该丢弃；视频流通常更关注低延迟，可以容忍少量丢包。

应用协议中至少带 `deviceId`、`sessionId`、`messageId`、递增序号、创建时间、过期时间、消息类型和签名。机器人与云端保持心跳，断线后采用指数退避和随机抖动重连；双方持久化尚未确认的重要消息，重连时根据会话和序号续传。服务端返回“已接收”和“已执行”两个层次的 ACK，发送端超时后重试，接收端按 `messageId` 幂等去重并按设备维度处理顺序。

传输可以根据场景选择 TLS 上的 TCP、MQTT、WebSocket 或 QUIC，协议本身仍要补应用级确认和业务幂等。还要监控在线率、重连次数、消息成功率、端到端 P95/P99 延迟、重复率、积压和状态新鲜度。安全关键动作必须带授权、重放保护和本地安全兜底；网络中断时机器人应进入预定义安全状态，而不是无限重放过期指令。

### 38. 如果要求控制消息尽量不丢，系统怎样判断消息丢失，丢失后又怎样处理

**建议时长：60～90 秒。**

判断丢失依靠序号、ACK 和超时。发送端为每条消息分配唯一 `messageId` 和序号并保存到本地 Outbox；收到对端 ACK 后才标记完成。接收端发现序号有空洞，或者发送端在超时时间内没有收到 ACK，就认为消息可能丢失或结果未知。

处理时按指数退避重试，并设置最大次数和截止时间。因为 ACK 本身也可能丢，所以重试会产生重复消息；接收端必须用 `messageId`、设备 ID 和业务版本做幂等，不能把“至少一次投递”误说成“绝对只执行一次”。执行失败可进入重试队列或死信队列并告警，关键任务由人工介入。

还要区分接收 ACK 和执行 ACK：前者只表示服务收到了消息，后者才表示业务动作完成。过期控制指令不能在恢复网络后继续执行；状态上报如果新快照已经到达，较旧的乱序数据通常可以按序号丢弃。

### F. 候选人反问

### 39. 机器人平台方向具体做什么业务

**面试官答复整理：** 该方向面向工程机械机器人场景。岗位除了处理机器人与服务器之间的通信风险，也会做常规服务端业务，例如接收机器人状态上报、下发和追踪指令、向用户界面回显数据，以及支持具体作业流程。

从后端视角看，它仍然包含常见的接口、数据、调度和稳定性工作，只是服务对象从普通 Web 用户扩展到了处于弱网环境的实体设备。

### 40. 这个岗位是否主要负责服务端后台逻辑、稳定性治理和运维监控平台

**面试官答复整理：** 这些内容属于岗位的一部分，但不能只理解成运维监控。机器人会持续上报状态并执行指令，平台需要展示成功率等指标，也要承载面向具体业务的操作流程。

例如工程机械场景不仅需要看设备是否在线，还可能需要创建作业、分配设备、调度执行、展示进度、处理异常和完工结果。因此它是业务平台与设备管理平台的结合，而不只是监控大盘。

### 41. 这里的机器人主要是工厂流水线机器人，还是其他类型的机器人

**面试官答复整理：** 主要不是工厂流水线机器人，而是工地上的挖掘机、装载机等工程机械。设备经过嵌入式和联网改造后，可以执行无人化作业或人机协作任务，云端平台负责连接、作业调度和业务管理。

## 三、本场复盘与下一轮重点

1. **Java 基础概念需要说准。** `equals()` 不会自动调用 `hashCode()`；`volatile` 不是锁；`HashMap.Node` 保存 hash、key、value 和 next。
2. **并发工具不能只贴“乐观/悲观”标签。** 要从原子性、可见性、互斥范围、冲突率和重试成本解释 CAS、`volatile`、`synchronized` 与 `ReentrantLock`。
3. **索引结论不能绝对化。** 范围查询通常仍能使用 B+ 树；是否走索引要看联合索引顺序、选择性、覆盖情况和优化器成本。
4. **项目参数必须能推导。** 轮询周期和批大小应由延迟 SLA、吞吐与下游容量决定。先核对真实的 ZSet 扫描配置，解决“30 分钟”和“2 秒”的冲突。
5. **个人贡献边界要稳定。** 机审业务链路可以说是新建的，但公司内部配置平台、规则解析、数据同步和监控平台不能表述成个人从零开发。
6. **ES 回源方案需要保护 DB。** 前置再查一张 MySQL 表不是有效拦截，应准备限流、负缓存、布隆过滤器、回源并发隔离、熔断降级和一致性窗口的完整回答。
7. **机器人通信要讲应用级协议。** TCP 不能单独保证业务消息“恰好执行一次”；应覆盖 ID、序号、双阶段 ACK、超时重试、幂等、持久化、过期指令和本地安全状态。

## 四、面试前核验清单

1. 黑名单任务真实扫描周期、单批数量、部署实例数、锁粒度、失败后是否重新入队。
2. 黑名单业务的权威状态究竟在数据库、Redis 还是远程游戏服务；如何防止旧任务解除新一轮封禁。
3. 机审链路中本人实际新增的模块、配置结构、动作类型和 fallback 路径。

5. MySQL 到 ES 的内部同步平台到底基于 binlog/CDC、MQ 还是其他机制，最大延迟和对账方式是什么。
6. ES 回源 MySQL 的真实触发条件、是否已有调用方限流、负缓存、熔断或数据库隔离。
