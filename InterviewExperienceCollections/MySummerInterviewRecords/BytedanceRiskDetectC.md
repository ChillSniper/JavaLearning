### 2. 对于铁路票务系统，或者说秒杀系统，高并发怎么考虑？

**建议时长：90 秒。**

先给结论：高并发系统不能只靠“加 Redis、加 MQ”，而要同时解决入口流量治理、热点数据访问、库存正确性、异步削峰、失败补偿和容量评估。我的设计链路是：

1. 先明确峰值 QPS、读写比例、热点集中度和成功语义。“一千万请求”如果是全天总量和一秒内峰值，设计完全不同。
2. 在网关层完成鉴权、限流、验证码或人机校验、重复请求拦截，只让合法且容量内的请求进入核心系统。
3. 静态车站、车次基础信息放本地缓存或 Redis；动态余票也可用 Redis 承担高频查询，但 Redis 中的数据只是加速访问的派生数据。
4. 按 `车次 + 出发日期` 对热点库存分片和路由，使同一份库存尽量落在确定的处理分区。极热点车次可通过库存令牌、分段锁或按席别进一步拆热点。
5. 下单入口使用请求号保证幂等。Redis Lua 可以原子完成资格校验和预库存扣减，快速淘汰无库存请求，但最终防超卖边界仍应落在数据库条件更新、座位占用记录和唯一约束上。
6. 如果数据库不能同步承受全部写入，可以把已通过预校验的请求写入 MQ 削峰，并立即返回“排队中”，由消费者按业务键有序处理。没有完成数据库事务前，不能直接向用户返回“购票成功”。
7. 数据库事务中完成最终库存占用和待支付订单创建；支付超时后通过状态机、延时消息和幂等回补释放库存。
8. 最后补齐重试、死信、对账、降级、热点监控、容量压测和人工补偿。

铁路票务比普通秒杀更复杂，因为一张座位可以分段售卖。A-B-C-D 线路上购买 A-C，会占用 A-B、B-C，但不一定影响 C-D，因此库存模型还必须表达区间冲突，不能只维护一个简单的商品剩余数量。

### 3. 如何抗住上千万的流量，对 MySQL 的高并发读操作？

**建议时长：75 秒。**

我不会先假设“上千万流量”等于 MySQL 要承受上千万次查询，而会先确认这是总请求量还是峰值 QPS、热点是否集中、是否要求强一致。核心思路是让绝大多数请求不要直接打到 MySQL：

1. 网关限流和请求合并，先拦截异常、重复和超过系统容量的流量。
2. 多级缓存：稳定的小数据可放进程内缓存，热点业务数据放 Redis，并设置合理 TTL、随机过期时间和热点 Key 保护，避免缓存击穿和雪崩。
3. 缓存未命中时使用互斥构建、请求合并或逻辑过期，防止同一个热点数据被大量并发回源。
4. MySQL 查询只取需要的列，建立与真实查询匹配的联合索引或覆盖索引，通过 `EXPLAIN ANALYZE` 检查实际扫描行数、回表、排序和临时表。
5. 对允许短暂延迟的查询做读写分离和只读副本扩容；刚写完立即查询、库存确认等强一致读仍应走主库或采用明确的一致性路由。
6. 单库容量仍不足时，按稳定业务键水平分库分表，让请求能直接路由到一个分片，避免全分片扫描。
7. 配置有上限的数据库连接池、查询超时和熔断降级，防止应用无限建连接把数据库拖垮。

读扩容的前提是先减少无效查询、避免热点击穿并优化单次 SQL。只增加从库而不处理慢 SQL 和热点，通常只是把问题复制到更多机器。

### 4. 高并发写呢？

**建议时长：75 秒。**

高并发写的重点是保护事实数据的正确性，同时降低同一行和同一索引上的竞争：

1. 入口先做限流、资格校验和幂等去重，减少注定失败的写请求。
2. 库存扣减尽量合并为单条原子条件更新，避免“先查库存，再根据旧值修改”的竞态。
3. 对同一 `车次 + 日期` 的请求按业务键路由到固定 MQ 分区或执行单元，在可接受的场景下进行有界排队和顺序消费。异步处理时接口只能返回“处理中”。
4. 按用户、订单或车次日期进行水平分片，分散不同业务实体之间的写流量；对单个超级热点还要继续拆分库存桶或令牌桶，单纯加库无法消除同一行的锁竞争。
5. 减少不必要的二级索引、大字段和同步旁路写入。审计日志、通知等非核心动作可通过本地消息表或事务消息异步化，但订单和库存的核心状态必须有明确的事务边界。
6. 消费端使用 `requestId`、订单号或业务流水号做幂等，并建设重试、死信、积压监控和对账补偿。

批量写适合日志、统计等允许聚合的数据，但库存竞争和订单状态迁移不能为了吞吐随意批量合并，否则会增加锁范围和失败补偿复杂度。

### 5. 怎么保证票不会卖多？

**建议时长：90 秒。**

先给结论：Redis 预扣库存只能挡流量，数据库中的座位占用状态或库存记录才是最终事实源。要同时依靠原子条件更新、事务、幂等和状态机保证不超卖。

普通商品库存可以使用：

```sql
UPDATE inventory
SET remain = remain - 1
WHERE sku_id = ? AND remain > 0;
```

只有受影响行数为 1 才说明扣减成功。这样“检查库存”和“扣减库存”由一条 SQL 原子完成，不会出现两个请求都读到旧库存后同时成功。

铁路座位还要判断区间冲突。可以把一个座位经过的相邻区间编码成位图，请求区间对应 `request_mask`，然后使用类似的条件更新：

```sql
UPDATE train_seat
SET occupied_mask = occupied_mask | :requestMask
WHERE train_id = :trainId
  AND travel_date = :travelDate
  AND seat_id = :seatId
  AND (occupied_mask & :requestMask) = 0;
```

受影响行数为 1 表示这个座位在目标区间内没有冲突并被当前请求占用；为 0 则更换候选座位或返回无票。座位占用与待支付订单应在同一个数据库事务中完成，事务失败会一起回滚。

此外还要补三层保护：

- 客户端重试使用同一个 `requestId`，数据库为它建立唯一约束，防止同一请求重复扣减。
- 支付和超时取消通过条件状态迁移竞争，例如只能从 `UNPAID` 变成 `PAID` 或 `CANCELLED`，库存只能由成功取消的一方回补一次。
- Redis 预扣成功但数据库事务失败时执行幂等回补，并通过订单、库存流水和定时对账发现遗漏。

如果车站数量超过单个整数位图的表达范围，可以使用多段位图或区间占用表；具体模型要根据线路长度、查询方式和写放大成本选择。

### 6. 怎么保证数据库和缓存之间的一致性？

**建议时长：90 秒。**

先明确边界：MySQL 和 Redis 是两个独立系统，不引入分布式事务时，很难在任意故障下实现实时强一致。常见目标是以 MySQL 为事实源，让 Redis 最终一致，并对库存确认等关键读绕过缓存或做更强校验。

常见的 Cache Aside 流程是：

1. 读请求先查缓存，未命中再读数据库并回填缓存。
2. 写请求先在数据库事务中修改数据，事务提交成功后删除缓存，而不是同时更新两份数据。
3. 删除缓存失败不能只打日志，要通过事务内 Outbox、本地重试任务或订阅 Binlog/CDC 可靠地再次删除或刷新。
4. 缓存设置 TTL 作为兜底，并对空值、热点 Key 和批量失效分别处理，避免穿透、击穿和雪崩。

还要考虑一个并发窗口：读线程先查到缓存未命中，随后写线程更新数据库并删除缓存，最后读线程把旧快照回填到缓存。延迟双删只能缩小窗口，不能提供严格证明。更稳妥的做法是让 CDC 再次纠正、在缓存值中携带数据版本并拒绝旧版本覆盖，或者让强一致业务直接读主库。

因此面试中不能只说“先更新数据库再删缓存”就结束，还要补充删除失败重试、并发回填、TTL、监控和对账。

### 7. 如何保证订单号不会重复？

**建议时长：60 秒。**

需要区分两个问题：订单号全局唯一，以及同一次业务请求不能创建多个订单。

订单号可以使用 Snowflake 一类的分布式 ID，由时间戳、机房或节点编号和同一毫秒内的序列组成；也可以使用数据库号段服务。无论采用哪种生成方式，订单表的 `order_no` 都应建立唯一索引，数据库作为最后一道防重复边界。

Snowflake 方案还要处理节点编号冲突、时钟回拨、序列耗尽和多机房部署。例如节点编号由注册中心统一租约分配，检测到时钟回拨时短暂等待、切换备用节点或拒绝生成，不能默默生成重复 ID。

但订单号唯一不等于业务幂等。客户端超时重试时可能生成两个不同订单号，因此还要让客户端或网关生成 `requestId`，并在订单表上建立类似 `(user_id, request_id)` 的唯一约束。收到重复请求时返回原订单结果，而不是再次扣库存和创建订单。

### 8. 卖票系统怎么防止黄牛？

**建议时长：75 秒。**

防黄牛不能只靠 IP 限流，因为黄牛可以更换代理、账号和设备。应当把它设计成一条多层风控链路：

1. 账号与实名层：手机号、身份证、乘车人、支付工具建立关联，限制同一身份的账号数量、购票频率和乘车人数量。
2. 设备与网络层：结合设备指纹、IP、代理特征、异常地理位置和多账号共用设备识别批量操作，但共享网络不能直接作为封禁结论。
3. 行为层：检测请求频率、时间间隔、页面操作轨迹、失败重试模式和多个账号的协同行为，给请求计算风险分。
4. 流量层：网关限流、排队令牌、动态验证码、人机校验和分级挑战。风险越高，校验越严格，避免所有正常用户都承担同样成本。
5. 交易层：限制同一账号、实名主体、设备和支付工具的购票次数；订单、支付和退票链路都要检查，防止只保护下单入口。
6. 黑名单与处置层：根据证据采取限速、冷却、二次验证、限制购票或封禁，并保留规则命中原因、有效期、申诉和人工复核能力。

技术上，请求令牌应绑定用户、车次、时间和随机数，并带签名和短有效期，防止复制与重放。风控还要关注误伤率、规则可解释性、隐私保护和策略灰度，不能为了拦截率直接永久封禁所有可疑用户。

### 9. 对于拉黑用户的 ID 怎么设计？

**建议时长：75 秒。**

先给结论：不要把“是否被拉黑”编码进用户 ID。用户 ID 应是稳定的业务主键，黑名单是一条可以生效、过期、撤销和审计的独立风险记录。

可以设计：

```text
risk_blacklist
- id                 黑名单记录 ID
- subject_type       USER / DEVICE / IP / ID_CARD / PAY_ACCOUNT
- subject_key        规范化后的主体标识或其 HMAC
- scene              登录、查票、购票、支付等场景
- reason_code        拉黑原因
- risk_level         风险等级
- effective_at       生效时间
- expire_at          过期时间，永久拉黑可为空
- status             ACTIVE / EXPIRED / REVOKED
- version            并发控制版本
- rule_id / operator 规则来源或人工操作人
- created_at / updated_at
```

`id` 只标识这条处置记录，真正判断的业务键是 `subject_type + subject_key + scene`。内部用户可直接使用稳定的 `user_id`；身份证、手机号和支付账号等敏感标识不应明文作为 Redis Key，可先规范化后使用 HMAC，服务端保管密钥。

高频判断可缓存到 Redis。永久或统一过期的数据可按场景和主体类型分片存入 Set；每个成员过期时间不同可以使用 ZSet，以 `expire_at` 为 score，并通过 `ZSCORE` 精确判断。数据量很大时按主体哈希分片，避免单个大 Key。Bloom Filter 只能用于快速判断“一定不存在”，它的阳性有误判，不能直接作为拉黑用户的最终证据。

### 10. MySQL 的慢查询，解决思路？

**建议时长：75 秒。**

我的排查顺序是“发现、定位、分析、优化、验证、持续监控”：

1. 通过慢查询日志、APM 和 `performance_schema` 找到高耗时、高频或扫描行数异常的 SQL，并记录参数、调用链和发生时间。
2. 区分耗时来自 SQL 执行、锁等待、连接池等待、磁盘 I/O 还是网络，不能看到接口慢就直接加索引。
3. 在安全环境中使用 `EXPLAIN` 或 `EXPLAIN ANALYZE` 检查访问类型、实际与估算行数、使用的索引、回表次数、Join 顺序、`Using filesort` 和临时表。
4. 检查表结构、数据分布、索引选择性、统计信息和参数类型，确认问题是扫描过多、排序聚合、回表、隐式转换还是锁竞争。
5. 根据原因优化 SQL、索引、数据模型或访问架构，然后用同样的数据量和参数对比执行计划、耗时、扫描行数以及写入成本。
6. 灰度发布并监控回归，保留回滚方案。新增索引会增加写放大和存储占用，不能只验证读性能。

### 11. 怎么优化慢 SQL？

**建议时长：75 秒。**

具体优化可以按以下顺序回答：

1. 减少读取的数据：不用 `SELECT *`，只查需要的列；尽早过滤；避免一次返回无上限的大结果集。
2. 让条件可利用索引：避免对索引列做函数和不必要的类型转换，统一 Join 字段类型与字符集。
3. 根据真实查询建立联合索引。通常把常用等值过滤列放在前面，再考虑范围、排序和分组列，同时通过覆盖索引减少回表。
4. 优化分页。深分页避免 `LIMIT 100000, 20`，改用上一页最后一个唯一排序键做游标分页，例如 `WHERE (created_at, id) < (?, ?)`。
5. 优化 Join、子查询和聚合：先缩小数据集再关联，避免循环发起 N+1 查询；`EXISTS`、`IN`、Join 或拆分查询要根据语义和执行计划选择，没有固定谁更快。
6. 将无法在线高效计算的复杂统计改为预聚合、汇总表或异步计算。

最后必须重新执行 `EXPLAIN ANALYZE` 和压测。SQL 文本看起来更短，不代表执行成本更低。

### 12. 除了加索引，还有其他什么优化方案？

**建议时长：60 秒。**

除了索引，还可以从五层优化：

- SQL 层：减少返回列和行数、消除 N+1、游标分页、改写不必要的子查询和重复计算。
- 数据层：冷热分离、历史数据归档、垂直拆表、大字段单独存储、适度反范式和预聚合。
- 架构层：Redis 缓存、读写分离、只读副本、分库分表、搜索型查询迁移到更合适的检索系统。
- 事务层：缩短事务、固定加锁顺序、降低不必要的锁范围，排查锁等待和死锁，而不是把锁慢误判为扫描慢。
- 系统层：合理设置连接池、Buffer Pool、磁盘和实例资源，但参数和硬件应建立在执行计划与监控证据上。

优化目标也不只是单条 SQL 的最低延迟，还要考虑吞吐、写放大、主从延迟、系统复杂度和一致性要求。

### 13. 如何分表？按照什么维度分表？

**建议时长：90 秒。**

先给结论：不存在“单表超过固定行数就必须分表”的统一阈值。要根据数据量增长、索引高度、工作集是否能进内存、写入竞争、备份恢复时间和 SLO 判断。能通过索引、归档和读写分离解决时，不应过早引入分片复杂度。

分表方式主要有：

- 垂直拆分：按业务职责或冷热字段拆表，例如把订单主信息与低频扩展信息、大字段分开。
- 水平拆分：每张表结构相同，按某个分片键把不同记录分散到多个库表。

分片键要满足三个条件：大多数请求携带它、分布相对均匀、核心事务尽量能落在一个分片。票务场景可以这样考虑：

- 座位和库存按 `train_id + travel_date` 路由，因为库存操作天然围绕具体车次日期展开。
- 用户订单列表常按 `user_id` 查询，可按用户哈希分片；根据订单号查详情时，可让订单号携带分片位，或维护 `order_no -> shard` 的路由索引。
- 风控主体记录可按 `subject_key` 哈希分片，避免把同一主体的数据分散。

时间范围分片便于归档，但最新分片容易形成写热点；纯哈希分布均匀，但扩容迁移和范围查询更复杂。不要选状态、性别等低基数字段作为分片键，也不要让核心请求频繁广播到所有分片。

落地前还要设计全局 ID、跨分片查询、分页排序、数据迁移、扩容、跨分片事务和对账方案。

### 14. 还有什么优化 SQL 的思路？

**建议时长：60 秒。**

我会再从执行过程补充一套检查清单：

1. 访问路径：是否全表扫描，扫描行数和返回行数是否悬殊，统计信息是否过期。
2. 条件表达式：是否在列上做函数、计算或隐式转换，`LIKE` 是否以通配符开头。
3. 联合索引：列顺序是否符合过滤、范围、排序和分组需求，是否能覆盖查询。
4. Join：关联字段类型是否一致，关联列是否有索引，是否在关联前先缩小数据集。
5. 排序与聚合：能否利用索引顺序，是否出现大规模 `filesort`、临时表或磁盘落盘。
6. 分页与批处理：是否深分页，是否一次拼接过大的 `IN` 列表，是否存在逐行 N+1 查询。
7. 并发影响：是否因为长事务、热点行更新或不一致的加锁顺序造成锁等待。

优化器 Hint 和 `FORCE INDEX` 应作为充分验证后的最后手段，因为数据分布变化后，强制计划可能比优化器自动选择更差。

### 15. 联合索引中的最左匹配原则是什么意思？

**建议时长：60 秒。**

假设有联合索引 `(a, b, c)`，B+ 树中的键先按 `a` 排序，`a` 相同再按 `b` 排序，`a、b` 都相同再按 `c` 排序。因此查询通常要从最左列开始，才能快速确定连续的索引范围。

- `WHERE a = 1`：可以使用索引的 `a`。
- `WHERE a = 1 AND b = 2`：可以使用 `a、b`。
- `WHERE a = 1 AND b = 2 AND c = 3`：可以使用全部列。
- `WHERE b = 2 AND c = 3`：通常不能按这棵索引直接定位，因为缺少最左列 `a`。部分版本和特定数据分布下优化器可能选择 Skip Scan，但不能把它当成稳定设计依据。
- `WHERE a = 1 AND c = 3`：可以用 `a` 缩小扫描范围，`c` 可能通过索引下推过滤，但因为缺少 `b`，不能利用 `c` 继续形成连续的 B+ 树查找范围。

条件在 SQL 中的书写顺序不重要，优化器会重排；重要的是联合索引自身的列顺序。出现范围条件后，后续列通常不能继续缩小索引扫描边界，但仍可能用于索引下推或覆盖查询，所以不要笼统说“后面的索引全部失效”。

### 16. `SELECT *` 会导致索引失效吗？

**建议时长：45 秒。**

不会必然导致索引失效。`SELECT *` 影响的是取哪些列，不是 `WHERE` 条件本身能不能通过索引定位数据。

但是它可能带来三个问题：

1. 原本只查索引内列时可以使用覆盖索引，改成 `SELECT *` 后需要回表读取完整行。
2. 如果命中行很多，优化器估算大量随机回表比顺序全表扫描更贵，可能主动选择全表扫描。
3. 读取无用的大字段会增加磁盘 I/O、Buffer Pool 占用、网络传输和对象构造成本。

因此准确说法是：`SELECT *` 不会在语法上让索引失效，但可能失去覆盖索引，并因回表成本使优化器不选择该索引。最终应以 `EXPLAIN` 和实际执行数据为准。

### 17. 关于索引失效的原因，说得越多越好

**建议时长：90 秒。**

更准确的说法是“索引无法用于定位，或者优化器基于成本没有选择索引”。常见情况包括：

1. 联合索引缺少最左前缀，后续列无法直接形成有序查找范围。
2. 在索引列上使用函数或表达式，例如 `DATE(create_time) = ?`、`id + 1 = ?`。可改写为列与范围常量比较，或使用经过验证的函数索引。
3. 隐式类型转换或字符集、排序规则不一致，尤其是数据库需要对索引列逐行转换时。
4. `LIKE '%abc'` 或 `LIKE '%abc%'` 以通配符开头，普通 B+ 树无法根据前缀定位；`LIKE 'abc%'` 通常可以走范围索引。
5. `OR` 的某个分支没有可用索引，优化器可能选择全表扫描；不同索引之间有时可使用 Index Merge，但不一定最优。
6. 条件选择性太差、预计返回表中大部分记录，优化器认为全表扫描成本更低。例如低基数状态列、范围过大、`!=` 或 `NOT IN` 命中大量数据。
7. 范围条件后的联合索引列通常不能继续缩小扫描边界，但可能仍用于索引下推和覆盖查询。
8. 排序或分组顺序与索引顺序不一致、混用了无法匹配的方向，导致额外排序；这不一定意味着过滤索引也完全没用。
9. Join 两侧字段类型、长度、字符集或排序规则不一致，可能导致转换和低效访问。
10. 表很小、统计信息过期或数据分布严重倾斜，优化器可能不选预期索引。
11. 查询需要大量索引外字段并产生大量回表，优化器可能改走全表扫描。
12. 使用不可见索引，或索引本身没有覆盖查询所需的前导列。

`>`、`<`、`BETWEEN`、`IN`、`IS NULL`、`!=` 都不是语法上“必然使索引失效”。是否使用取决于索引结构、选择性、返回比例和优化器成本，必须结合 `EXPLAIN ANALYZE` 判断。

### 18. 条件查询可以用到索引吗？

**建议时长：45 秒。**

可以。索引最主要的用途之一就是加速 `WHERE` 条件查询，但前提是条件可搜索、与索引前缀匹配，而且命中比例值得走索引。

例如存在索引 `(user_id, status)`：

```sql
SELECT order_no, amount
FROM orders
WHERE user_id = ? AND status = ?;
```

通常可以利用联合索引快速定位。如果写成 `WHERE CAST(user_id AS CHAR) = ?`，或者只查询一个选择性很差的 `status` 且返回大部分表，索引效果会下降，优化器甚至可能选择全表扫描。

所以不能只根据“有 WHERE”或“建了索引”判断，要看条件写法、联合索引顺序、数据分布和执行计划。

### 19. `A OR B` 的判断条件会用到索引吗？

**建议时长：60 秒。**

可能会，但不是必然：

- 如果是同一索引列，例如 `status = 1 OR status = 2`，优化器可以把它当作多个索引范围处理，通常也可以改写成 `status IN (1, 2)`。
- 如果 `A` 和 `B` 分别对应不同索引，MySQL 可能使用 Index Merge，把两组主键结果求并集后再回表。
- 如果其中一个分支没有可用索引，或者两个分支命中数据很多，优化器可能直接全表扫描。

在执行计划确实较差时，可以考虑拆成 `UNION ALL`，让两个分支分别使用自己的索引，但必须处理重复数据。如果两个条件可能同时命中同一行，直接使用 `UNION ALL` 会返回重复记录；使用 `UNION` 又会增加去重成本。因此改写前要先保证语义正确，再比较执行计划。

### 20. `IN (...)` 的判断条件会用到索引吗？

**建议时长：50 秒。**

通常可以。对于有索引的列，`IN (1, 2, 3)` 可以看作多个等值查找或多个索引范围。它不会因为使用了 `IN` 就自动索引失效。

但要注意：

1. `IN` 列表过大时，范围构建、随机访问和回表成本会上升，优化器可能选择全表扫描。
2. 联合索引仍受最左前缀约束。例如索引 `(a, b)`，`a IN (...) AND b = ?` 通常可以利用两列；只有 `b IN (...)` 则通常不能稳定使用该索引定位。
3. 参数类型应与字段类型一致，避免隐式转换作用在索引列上。
4. 成千上万的 ID 不适合无限拼接 SQL，可以将数据批量写入临时表后 Join，或分批查询，并控制 SQL 长度和数据库压力。
5. `NOT IN` 还要特别注意列表中 `NULL` 带来的三值逻辑，它不是简单的“与 IN 相反”。

最终还是要根据列表规模、数据分布和 `EXPLAIN ANALYZE` 判断。

### 21. 队列一般在什么场景下使用？

**建议时长：60 秒。**

队列的核心特征是把元素按某种顺序暂存，在生产速度和消费速度不一致时建立边界。常见场景有：

- 先进先出任务处理，例如打印任务、请求排队和生产者消费者模型。
- 异步解耦，例如订单创建后异步处理通知、审计和积分。
- 流量削峰，把瞬时请求放入有界队列，由下游按稳定速率消费。
- 线程池任务调度，通过阻塞队列在提交线程和工作线程之间传递任务。
- 广度优先搜索和层序遍历，例如图的 BFS、二叉树层序遍历和岛屿搜索。
- 滑动窗口和单调队列，例如在线维护窗口最大值。
- 定时任务和超时处理，例如延迟队列。

还要补充边界：队列不是无限容量。工程上必须设计容量、超时、背压、拒绝策略和积压监控，否则“削峰”只是把故障从下游延迟成内存溢出或消息堆积。

### 22. 队列有哪些不同的类型？对应哪些使用场景？

**建议时长：75 秒。**

可以按元素取出规则和并发语义分类：

- 普通 FIFO 队列：先进先出，适合任务排队、BFS 和生产者消费者。
- 循环队列：使用固定数组首尾相接，空间可复用，适合有界缓冲区、网络收发缓冲和环形任务队列。
- 双端队列 Deque：队头队尾都能插入和删除，适合滑动窗口、回文判断，也可同时模拟栈和队列。
- 优先队列：按优先级而不是到达顺序取出，通常使用堆实现，适合 Top K、任务优先级和 Dijkstra 最短路。
- 阻塞队列：队列空时消费者等待、队列满时生产者等待或超时，适合线程池和多线程生产消费。
- 并发队列：为多线程访问提供线程安全，适合高并发任务传递；具体选择要看是否有界、是否允许阻塞和公平性要求。
- 延迟队列：元素到达指定时间后才能取出，适合超时检查、短期定时任务和缓存过期处理。
- 单调队列：队列中的值保持单调，适合在线求滑动窗口最大值或最小值。

如果讨论消息队列，还可以按发布订阅、点对点、是否保证局部顺序和消费语义分类，但那属于分布式消息系统，不应与内存中的数据结构混为一谈。

### 23. 数据结构中，除了优先队列，还有其他哪些队列？

**建议时长：45 秒。**

除了优先队列，数据结构中常见的还有普通队列、循环队列、双端队列和单调队列；进入并发编程后还会使用阻塞队列、无锁并发队列和延迟队列。

从底层实现看，普通队列可以用数组或链表实现：

- 数组队列连续存储、缓存局部性好，但普通数组出队若整体搬移成本较高，所以通常实现成循环队列。
- 链式队列通过头尾指针做到队尾入队、队头出队都是 `O(1)`，扩容灵活，但有节点和指针开销，缓存局部性较差。
- 双端队列允许两端 `O(1)` 插入删除；Java 中常用 `ArrayDeque`，通常不建议用旧的 `Stack` 来模拟栈。
- 单调队列不是为了保存所有元素，而是删除不可能成为后续答案的元素，以 `O(n)` 解决滑动窗口最值问题。

面试时应先说明分类维度，再回答类型，否则容易把“实现方式”“取出规则”和“线程安全语义”混在一起。

### 24. 算法题：统计岛屿数量

**题目口径：LeetCode 200，建议讲解时长 60 秒。**

把网格看成一张图，每个值为 `'1'` 的格子是陆地节点，上下左右相邻表示连通。遍历所有格子，每遇到一个尚未访问的陆地，岛屿数量加一，然后通过 DFS 把与它连通的整座岛屿全部标记为已访问。之后再遇到这些格子时就不会重复计数。

为了不额外创建 `visited` 数组，可以直接把访问过的 `'1'` 修改为 `'0'`。每个格子最多访问一次，时间复杂度是 `O(m * n)`；递归栈最坏为 `O(m * n)`。如果网格很大、担心递归栈溢出，可以改用显式队列做 BFS。

```cpp
class Solution {
public:
    int numIslands(std::vector<std::vector<char>>& grid) {
        if (grid.empty() || grid[0].empty()) {
            return 0;
        }

        int islands = 0;
        const int rows = static_cast<int>(grid.size());
        const int cols = static_cast<int>(grid[0].size());

        for (int row = 0; row < rows; ++row) {
            for (int col = 0; col < cols; ++col) {
                if (grid[row][col] == '1') {
                    ++islands;
                    dfs(grid, row, col);
                }
            }
        }
        return islands;
    }

private:
    void dfs(std::vector<std::vector<char>>& grid, int row, int col) {
        const int rows = static_cast<int>(grid.size());
        const int cols = static_cast<int>(grid[0].size());

        if (row < 0 || row >= rows || col < 0 || col >= cols ||
            grid[row][col] != '1') {
            return;
        }

        grid[row][col] = '0';
        dfs(grid, row - 1, col);
        dfs(grid, row + 1, col);
        dfs(grid, row, col - 1);
        dfs(grid, row, col + 1);
    }
};
```

面试讲解时要说明：一次 DFS 只负责淹没一座岛，外层循环发现多少次新的陆地起点，就有多少座岛。
