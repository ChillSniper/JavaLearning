# 实习产出分析

## 阅读口径与身份备注

这份材料用于把简历上的五项字节跳动实习产出还原成面试时可以讲清楚的项目故事。每一部分都按照业务背景、需求做了什么、上下游链路、个人思考、解决的问题、结果指标和面试追问来组织。面试回答时要把“我具体负责的内容”“团队已有能力”“依赖方提供的能力”分开说，避免把整个系统的成果都归到自己身上。

**统一表达原则：** 先讲业务问题，再讲自己负责的链路和关键取舍，最后用可核验的指标或结果收束。没有明确留痕的 QPS、延迟、节省人力等数字不要临场编造，可以说“从稳定性和可用性上解决了问题”，并补充后续会用监控或数据看板验证。

## 1. Payment CMS 风控客诉自动化审核链路建设

### 业务背景与要解决的问题

Payment CMS 面向 TikTok 三条业务线承接支付风控客诉。一个客诉进入风控处置链路后，往往需要同时看当前工单信息、历史申诉、用户是否命中名单、父子单关系以及具体业务动作。过去如果完全依靠人工判断，处理速度和口径容易受个人经验影响；如果简单把所有工单交给自动化，又可能因为证据不足、动作参数不完整或下游失败造成误处置。

这个需求的核心不是“把人工按钮改成程序按钮”，而是建立一条可配置、可灰度、可追踪的自动审核链路：对高置信度场景自动给出审核结果并执行动作，对不确定或执行失败的场景保留人工兜底，同时让每次规则命中、动作结果和回复内容都能被复盘。

### 需求做了什么与个人贡献

我参与建设了基于 TCC 和 govaluate 的配置化规则引擎。规则可以组合业务线、客诉类别、交易类型、事件信息、名单命中和申诉状态等条件，并通过规则配置维护审核结果、回复模板、自动标记和后续动作。规则加载后先做基本校验，例如动作顺序和参数合法性校验，再按配置顺序执行首个匹配规则，避免多个规则同时命中造成口径不一致。

在上下文准备上，链路会查询案件详情，读取 Payment CMS 传入的工单和用户信息；需要判断申诉资格或历史状态时调用 Appeal Center 获取申诉快照；需要判断特殊人群时查询 Rep、Arena 等名单系统。动作侧接入了 SKY 相关动作、ByteHi 工单操作以及风险支持能力，覆盖自动标记、回复、关闭、父子单结果复用、Withdraw Link 和 Forget PIN 等场景。

我重点关注了“审核通过”和“动作完成”不能混为一谈的问题。规则命中后，系统会逐个执行动作并记录每个动作的状态；动作失败时停止后续动作并保留人工处理入口；最终把规则名、审核结果、回复模板、动作明细和 action_succeeded 持久化到案件参数中。对于已经关闭或转交的终态案件，以及已经成功处理过的案件，链路会跳过重复执行，保证重试不会重复发起下游动作。

### 上下游链路

可以按下面的顺序讲：支付客诉系统或 CSP 产生客诉，Adapter 整理案件信息并创建或更新 Conan 案件；NRT 查询案件详情，读取 TCC 规则并通过 govaluate 计算；规则计算过程中按需调用 Appeal Center、Rep 名单和 Arena 名单；命中规则后调用风险支持动作、SKY 相关能力或 ByteHi 工单接口；执行结果回写 Conan 案件参数和案件状态，同时通过日志和 metrics 供运营、研发和后续复盘使用。

其中，TCC 是规则和回复模板的配置来源，不能把它理解成业务动作本身；Appeal Center、Rep、Arena 是决策依赖；风险支持、SKY 和 ByteHi 是动作执行方；Conan 是案件状态和结果的承载方。把这些角色讲清楚，面试官就能判断你理解的是完整链路，而不是只记住了一个规则表达式。

### 我的思考与关键取舍

**把决策和执行拆开。** 规则只负责回答“这个案件是否满足某个自动审核条件、应该执行哪些动作”，动作执行层负责参数校验、调用下游和记录结果。这样规则变化不会直接侵入动作代码，动作失败也不会被错误地记录成审核成功。

**把安全边界放在执行前。** 例如 Withdraw Link 需要合法的用户标识和地区信息，Forget PIN 还需要从客诉描述中提取并校验手机号；参数缺失或格式不合法时转人工，不为了追求自动化比例而强行执行。

**灰度必须稳定且可回溯。** 自动动作按 merchant uid 做稳定分桶，同一个用户在灰度期间不会因为随机数变化而反复切换。规则结果和动作结果分开持久化，便于回答“为什么命中”“命中后到底有没有执行成功”两个不同问题。父子单复用也需要明确来源案件，避免把一个父单的结果无条件复制给不相关的子单。

### 解决的问题与结果

这条链路把分散在运营经验、名单查询、申诉历史和多个动作系统中的判断收敛成了可配置的自动审核流程，减少了重复人工检查，也降低了同类客诉处理口径不一致的风险。简历中记录的结果包括：自动化审核占比约 28%；线上近 7 天观察到父子单结果复用 115 次；有效规则命中约 36 次。面试时要说明这些指标的统计时间窗和口径，不能把“规则命中”直接等同于“动作全部成功”。

### 面试官可能追问与回答策略

1. **问题：** 为什么要用 TCC 加表达式引擎，而不是把规则直接写死在代码里？

    **回答策略：** 先说业务规则变化频繁且需要按业务线灰度，配置化可以降低发布成本；再补充表达式只是条件计算，真正的动作仍由代码控制并做参数校验，避免把高风险操作完全交给配置。

2. **问题：** 多个规则都满足时怎么处理？

    **回答策略：** 说明采用明确的规则顺序和首个匹配策略，并在加载阶段校验规则格式。这样结果可预测；如果未来规则数量继续增长，还可以增加优先级、命中原因和规则冲突检测。

3. **问题：** 规则命中但关闭工单失败，最终审核结果应该是什么？

    **回答策略：** 把“decision result”和“action status”分开回答：前者表示规则判断，后者表示执行结果。动作失败时记录逐动作失败状态、保留人工兜底，并让重试具备幂等性，不能只看规则命中就说自动化成功。

4. **问题：** 如何保证重试不会重复执行 Withdraw Link 或 Forget PIN？

    **回答策略：** 先读取案件中已有的动作状态，已成功的动作跳过；再结合案件终态判断和结果持久化，只有未完成动作才继续。若下游本身支持幂等键，还应把 case id 或 request id 作为幂等依据。

5. **问题：** 为什么需要 Appeal Center 的历史快照？

    **回答策略：** 因为同一用户可能重复申诉，当前案件不能脱离历史判断。历史快照用于判断是否可申诉、是否已经处理过以及是否需要复用父单结果，同时只把必要信息转换成规则输入，避免规则直接依赖复杂 RPC 返回结构。

6. **问题：** 灰度为什么按 merchant uid 分桶，而不是每次随机 28%？

    **回答策略：** 稳定分桶能保证同一用户在观察期内保持一致，方便复现和排查；随机灰度虽然简单，但同一用户可能在不同重试中走不同分支，增加数据和客服解释成本。灰度比例变化时还要关注历史桶边界和回滚行为。

7. **问题：** 自动化审核占比 28% 说明系统效果好吗？

    **回答策略：** 不要只用覆盖率下结论。需要同时看规则命中率、动作成功率、人工回退率、误处置率、重复处理率和人工处理时长；28% 只能说明当前规则覆盖了一部分场景，不能替代质量指标。

8. **问题：** 如果让你继续优化，你会做什么？

    **回答策略：** 优先补充规则命中解释、动作级失败告警和离线回放能力，再建设规则冲突检测与样本评估。对于高风险动作，增加双重校验或更严格的白名单条件，而不是单纯扩大自动化比例。

## 2. 风控客诉智能 Agent 决策链路建设

### 业务背景与要解决的问题

ROW 地区三条业务线的客诉中，有一类案件需要根据用户提交的证件或银行卡图片，结合 KYC、PI、Email、Address 等已有信息判断材料是否匹配。人工逐张查看图片并核对多个字段成本较高，而且不同审核人员对边界情况的判断可能不一致。单纯依赖大模型又会带来输出格式不稳定、理由不可追踪和规则口径漂移的问题。

因此这个需求的目标是把 Agent 的识别能力和确定性规则结合起来：Agent 负责从图片中提取身份信息并给出结构化匹配结果，确定性规则负责定义什么条件才能通过，案件系统负责持久化证据和最终决策。

### 需求做了什么与个人贡献

链路先按 case id 查询案件详情，获取 merchant uid、工单信息和附件；再从用户服务查询 KYC 姓名和状态，从规则数据服务读取支付相关邮箱等字段，并通过图片资源服务把附件对象转换成可供 Agent 访问的图片 URL。之后把图片 URL、KYC、PI、Email、Address 等参考信息按结构化 JSON 传入 Agent 工作流。

Agent 输出包含图片识别结果和匹配结果。程序对输出进行 JSON 解析和字段校验，判断证件是否过期，以及 KYC、PI、Email、Address 中是否至少有一个有效匹配信号；多张图片则按图片 URL 和原附件对象一一对应，把每张图片的识别结果回填到 attachment_list。最终结果、审核明细和附件识别结果会写回 agent_review_result、cybs_channel_id 和案件附件参数，供案件查询和后续规则审核使用。

我的核心思考是不要让 Agent 直接决定所有业务动作。Agent 的职责边界是“看懂材料并输出结构化证据”，TCC 确定性规则的职责是“根据证据做业务判定”，后面的动作仍由自动审核链路控制。Agent 超时、输出无法解析、输入信息为空、身份信息缺失或匹配结果缺失时，不应该猜测通过，而应进入 manual review。

### 上下游链路

上游是 Payment CMS 或 CSP 客诉案件和用户上传的图片；Adapter 或任务入口读取 Conan 案件详情，调用钱包用户服务获取 KYC，调用规则数据服务获取 Email 等业务字段，调用 IES Kefu Security 获取图片 URL；中间层调用 Ops Agent Service 的同步工作流；下游把结构化结果写回 Conan 案件参数，NRT 的确定性规则读取 agent_review_result.audit_result，并据此决定后续是否进入自动审核、回复、关闭或人工处理。

面试中可以明确区分三个结果：Agent 原始输出、程序校验后的结构化审核结果、案件最终动作结果。这样可以解释为什么模型“说 approved”不代表工单已经关闭，也能说明后续追踪和回滚应该看哪个字段。

### 我的思考与关键取舍

**让模型做擅长的事，让规则做必须稳定的事。** 图片理解和字段比对交给 Agent，是否通过、何时转人工等政策条件放在 TCC 或代码中。这样模型替换不会直接改变业务规则，规则审计也有清晰入口。

**把非结构化输出变成可验证证据。** 对 Agent 返回的 JSON 做字段级校验，记录 identity name、过期状态和各类 match 结果；多图片场景按对象标识回填，避免结果错贴到另一张图片上。输入或输出不完整时明确给出 manual review 原因。

**保留兼容写入。** 同时写入 agent_review_result 和历史兼容字段，是为了让旧消费者不中断；但新链路应明确唯一事实来源和字段演进计划，避免长期双写后两个字段产生不一致。

### 解决的问题与结果

这条链路减少了人工逐图核对的工作量，把审核证据、模型输出和最终案件结果串了起来，同时保留了异常转人工的安全边界。简历中记录的 Agent 决策结果准确率为 92%。面试时要准备说明样本来源、人工复核基准、统计时间窗和“准确率”具体定义，不能把它泛化成所有客诉场景的模型准确率。

### 面试官可能追问与回答策略

1. **问题：** 为什么不让大模型直接输出最终审核结论并执行动作？

    **回答策略：** 强调高风险支付客诉需要确定性、可解释和可回放。Agent 负责提取证据，规则负责判定，动作层负责执行和落库，三层拆开可以降低幻觉和不可审计风险。

2. **问题：** 92% 的准确率是怎么来的？

    **回答策略：** 先明确真实统计口径：样本范围、人工标签来源、正负样本分布、是否按 case 还是图片统计。回答时只引用已有材料能证明的数字，并主动说误判样本如何回流和继续优化。

3. **问题：** 多张图片的结果怎么合并？一张通过就整体通过吗？

    **回答策略：** 先讲图片级结果按附件标识回填，再讲当前业务规则的聚合条件。若当前口径是任一张有效图片存在 KYC、PI、Email 或 Address 匹配即可形成 approved，要明确这是业务规则，不是模型自由决定；同时要考虑证件过期、图片归属和冲突结果。

4. **问题：** Agent 返回乱码、缺字段或超时怎么办？

    **回答策略：** 把异常分成调用失败、JSON 解析失败、字段语义不完整三类，分别打点和记录原因；默认转 manual review，不把异常降级成通过。重试需要有超时上限，避免拖长案件处理时间。

5. **问题：** 为什么既写 agent_review_result 又写 cybs_channel_id？

    **回答策略：** 说明这是兼容既有消费者的双写方案，不能简单说两个字段永久等价。后续应明确新旧字段的 owner、校验和迁移计划，并通过监控发现双写不一致，最终收敛到单一事实来源。

6. **问题：** 如何防止 Agent 的输入数据和图片泄露？

    **回答策略：** 回答数据最小化、服务鉴权、图片 URL 有效期、日志脱敏和结果权限控制；不要在普通日志中打印证件图片、完整卡号或不必要的个人信息。对原始图片和识别结果还要明确保留期限。

7. **问题：** 这个链路的瓶颈在哪里？

    **回答策略：** 通常是图片资源分发和 Agent 同步调用延迟。可以从并发上限、单 case 图片数、超时、缓存可复用的用户字段和异步化拆分回答，同时说明不能为了延迟牺牲结果校验和人工兜底。

8. **问题：** 如果让你继续优化 Agent 审核，你会做什么？

    **回答策略：** 建设结构化评测集和离线回放，按 KYC、PI、Email、Address 分维度分析错误；增加证据引用和置信度分层，高置信度才进入自动动作，边界样本进入人工或二次审核。

## 3. 处罚查询链路性能与稳定性治理

### 业务背景与要解决的问题

处罚中心的 restriction 和 restriction_reference 两张核心表数据增长后，运营查询、范围查询和定时任务查询出现速度慢甚至 DB 超时。处罚记录又是风控和合规处置的基础数据，查询失败会影响运营判断、任务处理和后续解除动作，因此问题不只是“接口慢”，还涉及数据可用性和处置链路稳定性。

业务上需要一个更适合检索的读模型，同时不能因为迁移到 ES 就放弃原有数据库的可靠性。我的理解是：RDS 继续作为相对权威的数据源，ES 作为查询加速层，通过全量加增量同步建立索引，并为同步异常准备一致性校验、修复和回退方案。

### 需求做了什么与个人贡献

设计并参与将 restriction 和 restriction_reference 从 RDS 同步到 ES。存量数据通过 dsyncer 做全量同步；增量数据经过现有 DRC 或消息链路进入 risk_restriction_rds_to_es，再由 ES 侧流式任务写入对应索引。查询接口改为优先查询 ES，遇到 ES 调用异常或结果为空时回退原 DB 查询，避免一次迁移把查询能力变成单点依赖。

为了控制异构数据长期漂移，配套使用 DataEyes 对 RDS 和 ES 做一致性对比，并在 restriction_center_faas 中提供 HTTP 触发的对比和修复能力。索引字段按业务查询特点区分 keyword、date、long 和 text，保证状态、业务线、对象和时间范围等条件能够被正确检索，而不是只把数据库字段机械搬过去。

### 上下游链路

写入侧是 RDS 中的处罚和引用记录，经 dsyncer 或 DRC 产生全量和增量消息，消息进入同步 Topic，再由 ES 流式任务写入 restriction 和 restriction_reference 索引。读取侧是处罚中心 QueryRestriction 以及运营和定时任务调用方，后端优先查 ES，异常或空结果时回退 RDS。DataEyes 负责发现差异，FaaS 负责按需对比和修复，监控系统负责观察消息堆积、同步延迟、ES 查询错误和回退比例。

面试时不要把 dsyncer、消息队列、ES、DataEyes 和 FaaS 都说成“数据库”。它们分别承担数据迁移、传输、检索、校验和修复职责；把职责拆开讲，能体现你理解的是一条数据链路。

### 我的思考与关键取舍

**先明确数据源和读模型的关系。** RDS 作为业务写入和最终核对依据，ES 只负责高效查询。这样即使 ES 暂时不可用，也可以通过回退保证基本可用；同时不能把“ES 返回空”简单理解为真实无数据，生产上还要结合同步状态、查询条件和回退比例判断是否发生了数据延迟。

**全量同步和增量同步必须一起设计。** 只有全量会在上线后逐渐过期，只有增量又无法覆盖历史数据。需要关注消息重复、乱序、失败重试、索引幂等和历史字段兼容，并用数据校验任务发现遗漏，而不是假设消息链路天然可靠。

**降级要可观测。** 回退 DB 是可用性保护，不应该成为长期静默降级。需要统计 ES 查询错误、空结果回退、DB 回退耗时、同步延迟和数据修复量，按机房灰度观察，达到阈值后可以关闭 ES 优先路径或暂停放量。

### 解决的问题与结果

该治理把高频、复杂和范围型处罚查询从单一 DB 查询迁移到 ES 读模型，降低了数据库查询压力，并通过回退和一致性修复保留了可用性。来源材料没有给出可直接引用的具体延迟或 QPS 数字，因此面试中建议使用“查询效率和运营体验改善、查询超时问题得到治理”的定性结果；如果之后准备了监控截图，再补充上线前后的 P50、P95 和回退比例。

### 面试官可能追问与回答策略

1. **问题：** 为什么不直接给 RDS 建索引，而要引入 ES？

    **回答策略：** 从查询模式回答：既有范围查询、组合条件和数据增长压力，关系库在当前形态下已经出现超时；ES 更适合作为检索读模型。但要承认它带来最终一致性和运维成本，所以必须配套回退和校验。

2. **问题：** ES 和 RDS 数据不一致时谁是准的？

    **回答策略：** 明确 RDS 是业务写入和核对依据，ES 是查询副本。通过全量加增量同步、DataEyes 差异发现和 FaaS 修复降低不一致；在强一致性要求的场景不能只依赖 ES。

3. **问题：** ES 查询返回空，为什么要回退 DB？空结果可能就是没有数据。

    **回答策略：** 承认空结果与同步延迟难区分，因此回退是兼容策略而不是绝对正确性证明。可以按查询条件、索引同步水位或版本信息进一步判断，并监控空结果回退比例，避免把所有正常空查询都打到 DB。

4. **问题：** 全量和增量同步如何避免重复写入？

    **回答策略：** 使用稳定的 restriction_id 或 reference_id 作为文档标识，更新采用幂等 upsert；对消息重试和乱序要有版本或更新时间判断。回答时说明需要结合实际同步平台能力，不能笼统说“MQ 自带 exactly once”。

5. **问题：** 如果 ES 集群不可用，接口会不会整体不可用？

    **回答策略：** 正常查询路径回退 DB，并对超时设置上限；同时通过开关关闭 ES 优先或降低流量。还要说明 DB 也有容量边界，不能把回退当作无限容量，必须配合告警和限流。

6. **问题：** DataEyes 和 FaaS 分别解决什么问题？

    **回答策略：** DataEyes 负责发现 RDS 与 ES 的差异，FaaS 承载按表对比和修复逻辑。前者偏数据质量检测，后者偏可执行修复动作，二者不是重复建设。

7. **问题：** 索引字段为什么要区分 keyword、date 和 text？

    **回答策略：** keyword 适合精确过滤和聚合，date 和 long 适合时间或数值范围，text 适合全文检索。字段类型要从真实查询条件倒推，不能只追求和数据库类型一一对应。

8. **问题：** 上线时怎么灰度和回滚？

    **回答策略：** 先完成索引、同步任务和监控，再按机房逐步放量；观察查询错误、P95、回退比例、消息延迟和数据差异。异常时关闭 ES 优先或回滚代码开关，保留 RDS 查询路径，并继续排查同步和索引问题。

## 4. 处罚平台能力与合规建设

### 业务背景与要解决的问题

处罚中心既要满足风控对账户、卡片和支付对象的处置需求，也要满足不同市场的监管和合规约束。ID 市场需要拆分支付主体和金融主体的数据，交易冻结或解冻时可能要根据机房和主体切换不同下游；PCI 合规要求不能继续在链路中传递明文 instrument_id，而要使用映射后的 PipoCardId。与此同时，UK Visa 虚拟卡、TTPay 等项目需要处罚中心提供可以复用的冻结、解冻和止入止出能力。

### 需求做了什么与个人贡献

合规侧重点是调整处罚中心的交易冻结和解冻链路，在不同市场、支付主体和金融主体之间选择正确的下游；对 PCI 场景把明文卡标识转换为 PipoCardId，减少敏感信息在服务间传递。能力侧接入卡维度冻结和解冻、TTPay 账户止入止出、会员户冻结和解冻等原子能力，为 UK Visa 虚拟卡发放和 TTPay kill switch 提供后端支撑。

此外，处罚中心新增了指定对象的实时处罚特征接口，返回当前处罚或解除状态、最近处罚或解除时间以及操作人等信息，让上游策略在决定下一步动作前能够感知当前状态。这里的重点不是增加一个查询接口，而是把处罚结果转成可以被策略稳定消费的实时决策数据。

### 上下游链路

上游包括风控策略、运营平台、发卡项目和合规流程，它们提出冻结、解冻、止入止出或查询状态的请求；处罚中心负责识别市场、对象类型、动作类型和必要的身份映射，再调用卡、账户、会员或支付主体相关下游；下游返回动作结果后，处罚中心记录状态和操作信息，并通过实时特征接口提供给策略或其他查询方。

可以把链路讲成“**业务请求进入处罚中心，处罚中心做合规路由和原子动作编排，下游执行具体限制，处罚中心沉淀状态，再向策略提供实时特征**”。如果面试官继续问细节，再补充 ID 主体拆分和 PCI 映射分别是路由问题和敏感标识问题，不能混成一个改造点。

### 我的思考与关键取舍

**用原子能力承接业务差异。** UK Visa、TTPay 和不同市场的业务规则会变化，但卡冻结、账户止入止出、会员户冻结等动作可以抽象成稳定的原子能力。这样上游按业务场景编排，处罚中心按能力执行，避免每接入一个项目就复制一套处置代码。

**把合规要求前置到数据边界。** instrument_id 到 PipoCardId 的映射不是简单改字段名，而是要明确谁负责映射、哪些服务可以接触明文、日志和错误信息如何脱敏、映射失败时是否允许继续执行。面试中要主动讲这些边界，体现对支付敏感数据的敬畏。

**实时特征必须带上时间和操作者。** 只返回一个当前状态无法支撑审计和策略判断；最近处罚或解除时间、操作人等字段可以帮助上游判断状态新鲜度、解释决策来源，也便于排查重复处罚和异常解除。

### 解决的问题与结果

这组改造支持了 ID 市场和 PCI 合规要求，补齐了 UK Visa 虚拟卡和 TTPay 等项目需要的处罚原子能力，并把处罚状态和操作信息沉淀成上游可消费的实时特征。来源材料没有提供统一的量化收益指标，面试中可以围绕“支持项目上线、减少业务方重复建设、降低敏感信息传递风险、提升策略决策可见性”来讲，不要自行补充资损或耗时数字。

### 面试官可能追问与回答策略

1. **问题：** ID 市场为什么需要拆分支付主体和金融主体？

    **回答策略：** 从监管和数据边界出发：不同主体承担不同职责，冻结或解冻时必须调用对应主体的能力。回答重点是路由依据、数据隔离和错误回退，而不是只说“新增一个 if”。

2. **问题：** 为什么要把 instrument_id 转成 PipoCardId？

    **回答策略：** 因为 instrument_id 可能是明文卡号，PCI 要求降低敏感信息暴露面。需要说明映射服务、传递边界、日志脱敏和映射失败策略，不能只回答“为了合规”。

3. **问题：** 冻结和解冻能力如何设计成原子能力？

    **回答策略：** 定义统一的对象、动作、参数、状态和错误模型，上游业务只负责场景编排，处罚中心负责能力调用和结果落库。对不同对象类型的必填参数和幂等键要有明确校验。

4. **问题：** 下游冻结成功但本地落库失败怎么办？

    **回答策略：** 这是典型的分布式一致性问题，不能假设本地事务覆盖 RPC。需要用请求号和幂等查询重试，记录处理中状态，提供对账或补偿任务，并让查询接口能区分成功、失败和未知状态。

5. **问题：** 实时处罚特征为什么不让策略直接查数据库？

    **回答策略：** 通过稳定接口隔离存储实现，统一字段口径、权限和性能边界；策略不需要知道处罚表结构，也不应该绕过服务直接读库。实时接口还可以补充最近时间和操作人，形成可解释的决策输入。

6. **问题：** 多市场、多机房下怎么保证路由正确？

    **回答策略：** 先确定市场、业务线、主体和 IDC 的来源优先级，再把路由配置集中管理并做默认拒绝；上线按机房灰度，监控下游调用量、错误码和状态分布。不要把市场差异散落在多个动作函数里。

7. **问题：** TCC 配置放了哪些内容，代码放了哪些内容？

    **回答策略：** 变化频繁且可由业务控制的名单、路由和开关放配置；安全边界、参数校验、状态机和不可绕过的合规逻辑放代码。配置必须有校验、版本和回滚方案，不能把核心安全规则全部外置。

8. **问题：** 你会如何证明这个能力建设确实解决了问题？

    **回答策略：** 从项目接入数量、动作成功率、下游错误率、重复处置率、敏感字段暴露检查和策略调用稳定性验证；合规类需求还要有审计记录和安全评估结果。没有现成数字时，明确说当前能确认的是能力和链路，量化指标需要再查看板。

## 5. 自动化处置与申诉链路建设

### 业务背景与要解决的问题

这一部分包含两类相互关联的工作。第一类是 Fraud Chargeback 发生后自动解除协议购：过去需要人工查询事件和订阅关系，再手动解除，处理延迟可能带来资损。第二类是申诉链路治理：用户上传的银行卡图片如果暴露 CVV，案件可能直接被拒绝；同时申诉中心缺少完整的 reopen、complete 生命周期和行为事件，既影响合规处理，也不利于策略和运营分析。

### 需求做了什么与个人贡献

在 Chargeback 场景，处罚中心消费 Fraud Chargeback MQ，收到事件后查询关联信息得到协议购 id，再复用已有处罚能力解除协议购，把原来依赖人工串联的步骤改成事件驱动的自动处置。面试时要强调“**消费事件、查询业务关系、复用已有原子能力**”三步，而不是把它说成新增了一套完全独立的解除系统。

在申诉场景，增加 mask_image 类型的 case action，由有资质的员工提交打码后的 new_file_id。主流程先校验参数并用打码图替换 AppealInfo 中的原图引用，再异步删除原图；同时补充 mask 操作日志。原图删除连续失败时需要重试、记录错误和打点，避免主流程因为清理动作失败而阻塞，也避免把删除失败静默吞掉。

为支持运营和策略，申诉历史增加 reopen time 和 complete time，并将最新申诉记录中的两个时间回填到案件查询结果和 ES 检索字段；同时补充材料上传方式、证件或银行卡是否复用及复用来源等信息。用户申诉行为则以异步风控事件形式提供给策略，供后续风险判断使用。

### 上下游链路

Chargeback 链路是 Fraud Chargeback 事件生产方发布 MQ，处罚中心消费后查询协议购关系，再调用已有解除协议购能力，结果写回处罚或业务状态并通过监控跟踪。申诉链路是用户或客服上传材料到 Appeal Center，运营人员触发 mask action，申诉中心更新案件材料和生命周期字段，再调用文件服务异步删除旧图，同时把行为事件发送给风控策略；ES 和案件查询接口为运营检索和分析提供结果。

这条链路的关键上下游关系是：MQ 负责解耦事件来源与处置动作，处罚中心复用已有能力，申诉中心负责材料和生命周期，文件服务负责敏感原图清理，策略消费异步事件。每一方的职责不同，排障时要根据事件 id、case id、action log 和下游响应逐段定位。

### 我的思考与关键取舍

**先替换引用，再异步清理原图。** 如果先删原图再更新案件，更新失败会让案件指向不存在的材料；先写入打码图引用可以保证业务继续可查，再异步删除旧图。异步删除必须有重试和告警，否则“异步”会变成不可追踪的风险。

**事件驱动适合跨系统自动处置。** Chargeback 和申诉行为都来自外部事件，MQ 可以把生产方和处理方解耦，允许独立重试和扩容。但消费端必须按事件 id 或业务主键做幂等，不能因为消息重复而重复解除协议购或重复处理申诉动作。

**生命周期字段要有清晰语义。** reopen time 和 complete time 是案件生命周期事实，不能只依赖一个含义模糊的 latest update；材料上传方式和复用来源则用于解释证据质量。字段新增时要考虑老数据、ES 映射、接口兼容和前端展示，不能只改后端结构体。

### 解决的问题与结果

Chargeback 自动处置减少了人工查询和解除协议购的步骤，降低了因处理延迟产生资损的风险；CVV 打码让符合条件的案件有机会进入正常申诉流程，降低了因原图敏感信息导致的直接拒绝；申诉生命周期和异步行为事件增强了运营检索、策略决策和问题排查能力。来源材料没有提供统一的量化指标，面试中重点讲清安全顺序、幂等、重试和状态追踪即可。

### 面试官可能追问与回答策略

1. **问题：** 为什么 Chargeback 要通过 MQ，而不是同步调用解除协议购？

    **回答策略：** Chargeback 是外部事件，MQ 可以解耦事件生产和处置、吸收突发流量并支持重试；同步接口仍适合需要即时反馈的交互场景。回答时补充消费端幂等、积压监控和失败补偿。

2. **问题：** 如何保证重复消费不会重复解除？

    **回答策略：** 以 chargeback event id、协议购 id 或业务请求号建立幂等键，先查已有处置状态，再决定是否调用下游；状态写入要能区分处理中、成功、失败和未知，不能只依赖 MQ 的投递语义。

3. **问题：** CVV 打码为什么不直接删除原图并上传新图？

    **回答策略：** 先校验并替换案件引用，再异步删除旧图，能够避免删除成功但引用更新失败造成材料丢失。异步删除失败需要重试和告警，并限制有权限的人员和服务访问旧图。

4. **问题：** 原图删除连续失败会不会造成安全问题？

    **回答策略：** 会，因此要把删除失败当成可观测的安全事件，而不是普通业务错误。设置有限次数重试、间隔、告警和人工补偿；同时通过访问控制、短期 URL 和存储生命周期策略降低暴露窗口。

5. **问题：** 为什么要增加 reopen time 和 complete time，而不是复用 latest update？

    **回答策略：** latest update 无法表达生命周期中的关键节点，名称也容易产生歧义。新增语义明确的字段可以支持检索、统计和审计，但要同步考虑 ES 映射、老数据兼容和前端展示。

6. **问题：** 申诉行为异步发送给策略后，策略没收到怎么办？

    **回答策略：** 从生产失败、消息积压、消费失败和业务处理失败四层排查；配置 producer 和 consumer 监控，按事件 id 重试或补发。策略侧也要设计事件幂等和缺失事件的补偿查询。

7. **问题：** 如何判断一个上传材料是复用的？

    **回答策略：** 由上游传入复用信息和来源，后端在组装 AppealMaterial 时解析并持久化，查询接口返回给运营。关键是区分“是否复用”和“从哪里复用”，不要只存一个布尔值而丢失审计信息。

8. **问题：** 如果让你继续优化这条链路，你会做什么？

    **回答策略：** 补充统一事件 id、动作状态机和补偿任务，把 MQ、action log、文件删除任务和最终案件状态串起来；对敏感材料增加生命周期策略和访问审计；对策略事件增加回放能力，便于线上问题复现。

## 统一面试答题策略

**推荐的 90 秒结构：** 先用两句话说明业务背景和痛点，再用一条链路说明输入、核心处理、下游和结果；接着讲一个自己做的关键取舍，最后用指标或定性结果收束。每个项目都要能回答“为什么做、我改了什么、依赖谁、失败怎么办、怎么证明有效”。

**回答个人贡献：** 可以使用“我负责规则/接口/链路改造，和同学一起完成联调和上线；下游能力由对应团队提供，我负责协议适配、异常处理和结果落库”的表述。这样既能体现 ownership，也不会把团队工作误说成个人独立完成。

**回答技术深度：** 优先讲状态、幂等、降级、灰度、数据一致性、敏感信息和监控，这些是风控、支付和申诉系统最容易被追问的地方。不要只罗列 Redis、ES、MQ、TCC 或 Agent 名称，要说明每个组件在链路中解决什么问题。
